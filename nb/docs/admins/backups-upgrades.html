Sikkerhetskopier og oppgraderinger

Hva du skal sikkerhetskopiere, hvordan du gjenoppretter det på en ny vert, hvordan du oppgraderer, og hvordan du flytter en Mattermost-tjener eller et enkelt samfunn til Antimatter.

Hva du skal sikkerhetskopiere

HvaMed stedets compose-filMed et utgavearkiv
Databasen: meldinger, brukere, samfunn, kanaler og, med stedets compose-fil, konfigurasjonenvolumet antimatter_postgres, via pg_dumpdin PostgreSQL-database
Opplastede filer, bilder og installerte appervolumet antimatter_files (S3-opplagringen)FileSettings.Directory, ./data/ som standard
Konfigurasjonsfilen(i databasen)config/config.json
GIF-er og klistermerkervolumet antimatter_gifsdatakatalogen til GIF-tjenesten

Databasen og filene hører sammen: sikkerhetskopier dem samtidig, og hold kopiene unna tjeneren. Volumnavnene starter med compose-prosjektnavnet, antimatter (docker volume ls viser dem).

Sikkerhetskopier

Fra katalogen til compose.yaml. Hvis du stopper Antimatter først, får du en fullstendig konsistent kopi; en sikkerhetskopi tatt mens den kjører er vanligvis i orden, men filer som lastes opp under sikkerhetskopieringen kan mangle.

stamp=$(date +%Y%m%d-%H%M%S)
mkdir -p backups
docker compose stop antimatter
# Database
docker compose exec -T postgres pg_dump -U antimatter -d antimatter -Fc \
    > "backups/antimatter-db-$stamp.dump"
# File storage and GIF service
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data:ro" -v "$PWD/backups:/backup" \
        alpine tar -czf "/backup/antimatter-$v-$stamp.tar.gz" -C /data .
done
docker compose start antimatter
# Secrets
cp .env "backups/env-$stamp"

Kjør den fra cron for daglige sikkerhetskopier, og kopier backups/-katalogen til en annen maskin. Hold kopiene av .env like sikre som tjeneren: de inneholder passordene.

Hvis du i stedet vil kopiere de opplastede filene objekt for objekt (for eksempel til en annen S3-opplagring), bruk AWS-kommandolinjeverktøyet til bucket-tjenesten:

docker compose run --rm -v "$PWD/backups/files:/backup" bucket \
    "aws --endpoint-url http://files:9000 s3 sync s3://antimatter /backup"

Med et utgavearkiv, sikkerhetskopier databasen med pg_dump -Fc, og data/- og config/-katalogene med dine vanlige verktøy.

Gjenopprett på en ny vert

Legg compose.yaml, den lagrede .env-filen og sikkerhetskopiene i en ny katalog, deretter:

stamp=20261016-030000          # the backup to restore
docker compose create           # creates the volumes, starts nothing
docker compose up -d postgres
docker compose exec -T postgres pg_restore -U antimatter -d antimatter --no-owner \
    < "backups/antimatter-db-$stamp.dump"
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data" -v "$PWD/backups:/backup" \
        alpine tar -xzf "/backup/antimatter-$v-$stamp.tar.gz" -C /data
done
docker compose up -d

Bruk den samme .env-filen: lagringen og databasen må beholde passordene de hadde. Hvis den nye verten har en annen adresse, oppdater SITE_URL (og DOMAIN).

Test sikkerhetskopiene ved å gjenopprette dem på en annen maskin fra tid til annen.

Oppgrader

  1. Ta en sikkerhetskopi.
  2. Endre bildeetiketten i .env (ANTIMATTER_IMAGE), hvis du fester en, som anbefalt.
  3. Hent og start på nytt: 
    docker compose pull
docker compose up -d
docker compose logs -f antimatter

Ved oppstart oppgraderer serveren databasestrukturen (du kan følge med i loggen; en stor server kan ta flere minutter) og installerer de nyere versjonene av de medfølgende appene fra bildet. Med et utgavearkiv: stopp serveren, erstatt alt bortsett fra config/, data/, logs/, plugins/ og client/plugins/ med innholdet fra det nye arkivet, og start den på nytt.

Oppgraderinger går kun fremover. Når en nyere server har oppgradert databasen, kan en eldre versjon ikke lenger bruke den: for å gå tilbake, gjenopprett sikkerhetskopien som ble tatt før oppgraderingen. Det samme gjelder å gå tilbake fra antimatter-next til antimatter.

Versjoner

Antimatters server rapporterer versjonen av Mattermost-linjen den er basert på (for tiden 12.0.0). Bildene bygges på nytt fra main-greinene: antimatter-next hver natt (tags nightly-<YYYYMMDD>), og begge bildene ved hver endring (tags sha-<commit>). Fest deg til én av disse taggene, oppgrader med hensikt, og merk deg den forrige taggen slik at du vet hvilken sikkerhetskopi som hører til den.

PostgreSQL-hovedversjoner

Compose-filen bruker postgres:17-alpine. Antimatter krever PostgreSQL 15 eller nyere. En ny hovedversjon av PostgreSQL kan ikke lese datakataloget til den forrige: for å flytte til en ny, dump databasen, start den nye versjonen på et nytt volum og gjenopprett dumpen der.

Flytting fra Mattermost

Antimatter bruker Mattermosts databasestruktur og legger til sine egne tabeller, så den kan ta over en Mattermost-servers PostgreSQL-database og filer. Prøv det først på en kopi:

  1. Sikkerhetskopier Mattermost-databasen, filopplagringen (data/ eller S3-bucketen) og config.json, og stopp deretter Mattermost.
  2. Gjenopprett databasen i Antimatters PostgreSQL, eller pekk Antimatter mot en kopi av den (AM_SQLSETTINGS_DATASOURCE).
  3. Kopiér filene til Antimatters lagring, og behold stiene deres: til antimatter-bucketen med et S3-verktøy, eller til data/ med et utgavearkiv.
  4. Gjenbruk innstillingene dine: kopiér config.json, eller flytt den til databasen med amctl --local config migrate (se Konfigurasjon). Miljøvariablene dine med prefikset MM_ fortsetter å fungere; endre navnet til AM_ når det passer.
  5. Start Antimatter og følg loggen mens den oppgraderer databasen. Deretter sjekker du Systemkonsoll › Plugins › Pluginhåndtering. Antimatter installerer sine egne bygg av Calls, Playbooks, Kanban (Boards), Agents og integrasjonene når de er nyere enn den installerte versjonen. Hvis Mattermost hadde en nyere versjon av én av dem, fjerner du appen og starter Antimatter på nytt, slik at Antimatters eget bygg blir installert.
  6. Sett opp push-varsler på nytt med din egen push-proxy: Antimatter sender aldri varsler til Mattermosts push-tjenester, verken test- eller vertstjenester, som kun leverer til Mattermosts egne apper. Inntil du endrer Push-varselserver, sender serveren ingen push-varsler (se Push-varsler).

Antimatter kontakter ingen tjenester drevet av Mattermost, Inc. (se Connections to outside services), selv om konfigurasjonen din fortsatt nevner én:

  • en push-varselserver hos Mattermost beholdes i innstillingene, men brukes aldri;
  • Mattermosts adresser for appmarkedet (Markeds-URL) og for produktmeldinger blir tomme;
  • Calls-appen bruker Cloudflares offentlige STUN-server i stedet for Mattermosts, uten å endre den lagrede innstillingen (se Calls);
  • sjekken for sikkerhetsoppdateringer og rapportering av krassh er borte, og med dem også innstillingene i Systemkonsollen (Slå på sikkerhetsvarsel, Slå på diagnostikk og feilrapportering) og siden Meldinger.

Sokkelen for lokal modus er nå /var/tmp/antimatter_local.socket; amctl prøver også den gamle /var/tmp/mattermost_local.socket. Mattermost støtter kun PostgreSQL i sine nyere versjoner, og det gjør Antimatter også: flytt en MySQL-database til PostgreSQL først. Å gå tilbake til Mattermost etter at Antimatter har oppgradert databasen innebærer at du gjenoppretter sikkerhetskopien din av Mattermost.

Eksport og import av data

Formatet for masseeksport flytter data mellom servere: hele serveren, noen samfunn eller noen kanaler, med vedlegg, profilbilder og egne emoji hvis du ønsker det.

# on the source server
amctl export create --team-name design --include-profile-pictures
amctl export list
amctl export download <export file> design.zip
# on the destination server
amctl import upload design.zip
amctl import list available
amctl import process <uploaded file> --imported-users active

Følg jobbene med amctl export job list og amctl import job list. For eksport av et team eller en kanal er --imported-users påkrevd: active når personene flytter til denne serveren, inactive når du importerer til en server der de allerede har kontoer, slik at kontoer opprettet fra usikre treff forblir inaktive inntil en administrator har kontrollert dem. --destination-team-name importerer til et eksisterende team. Eksporter og importer beholdes på serverens lagringsplass (ExportSettings.Directory, ImportSettings.Directory) i 30 dager som standard.

På selve serveren gjør antimatter export bulk og antimatter import bulk --apply det samme fra filer, uten API-et.
