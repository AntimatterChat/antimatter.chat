L'API REST

Tot el que fan les aplicacions d'Antimatter passa per la mateixa API HTTP, de manera que els vostres scripts també ho poden fer. Aquesta pàgina explica com autenticar-se, els recursos que utilitzareu més, com són les respostes i els errors, i com seguir els esdeveniments en directe mitjançant WebSocket.

Bases

  • URL base: https://chat.example.com/api/v4. Tots els punts d'accés següents són relatius a aquesta URL.
  • Format: JSON a l'entrada i a la sortida, excepte les pujades de fitxers (multipart). Envieu Content-Type: application/json.
  • Identificadors: cada objecte té un id de 26 caràcters. Els temps són mil·lisegons des de l'època Unix (create_at, update_at, delete_at; 0 significa «no suprimit»).
  • Les comunitats són equips: l'API els anomena teams, amb un team_id.
  • Tu mateix/a: en qualsevol ruta que accepti un user_id, me fa referència a l’usuari iniciat, com en GET /users/me.

La llista completa de punts d'accés es troba al codi del servidor: les rutes es declaren a server/channels/api4/*.go i els tipus a server/public/model. La descripció OpenAPI de la carpeta api/v4/source del repositori cobreix els punts d'accés heretats de Mattermost i algunes de les afegides d'Antimatter: moure fils, connexions de models i accions de missatges. Les altres només es troben al codi.

Autenticació

Totes les peticions, excepte l'inici de sessió i alguns punts d'accés públics, requereixen un token a la capçalera Authorization:

curl -H "Authorization: Bearer $TOKEN" https://chat.example.com/api/v4/users/me

S'accepten tres tipus de token: tokens d'accés personals, tokens de sessió i tokens d'accés OAuth. També s'accepta Authorization: Token …. Els tokens a la cadena de consulta (?access_token=) només s'accepten per a tokens d'accés OAuth.

Tokens d'accés personals (recomanats per a scripts)

Un token d'accés personal actua com a vosaltres, no caduca llevat que li assigneu una data de caducitat, i es pot revocar en qualsevol moment. Els tokens d'accés personals estan desactivats per defecte:

  1. Un administrador del sistema habilita Habilita els tokens d’accés personals a Consola del sistema › Integracions › Gestió d'integracions (ServiceSettings.EnableUserAccessTokens, AM_SERVICESETTINGS_ENABLEUSERACCESSTOKENS).
  2. Per a cada persona que pugui crear fitxes d'accés, un administrador del sistema obre Consola del sistema › Gestió d'usuaris › Usuaris, tria Gestiona els rols al menú de la persona i marca Permet que aquest compte generi fitxes d'accés personals. Els administradors del sistema sempre poden crear-les.
  3. La persona obre el seu avatar a la part superior dreta i després Perfil i configuració › Seguretat. Sota Tokens d'accés personals, descriu per a què servirà el token i tria Crea un token. El token es mostra només una vegada: copia’l.

Mitjançant l'API: POST /users/{user_id}/tokens amb {"description": "backup script", "expires_at": 0} (expires_at en mil·lisegons; 0 si no n'hi ha). El camp token de la resposta és el secret; el seu id és el que s'usa per revocar-lo (POST /users/tokens/revoke amb {"token_id": "…"}). Des de la línia d'ordres: amctl token generate <user> <description>.

Un administrador del sistema pot establir un límit de durada per als tokens mitjançant Durada màxima dels tokens d’accés personals (dies) a la mateixa pàgina de la Consola del sistema.

Fitxes de sessió

Iniciar sessió amb una contrasenya retorna una fitxa de sessió a la capçalera de resposta Token, el mateix tipus de sessió que utilitzen les aplicacions:

curl -i -X POST https://chat.example.com/api/v4/users/login \
  -H 'Content-Type: application/json' \
  -d '{"login_id": "maya", "password": "…"}'

Afegeix "token": "123456" per a un compte amb autenticació multifactor. Les sessions expiren segons els paràmetres de sessió del servidor, i el punt d'entrada d'inici de sessió té un límit de freqüència (5 sol·licituds per segon). POST /users/logout finalitza la sessió.

Els navegadors s'autenticen amb una galeta en lloc d'una fitxa. Una sol·licitut autenticada per la galeta també ha d'enviar la capçalera X-CSRF-Token per a qualsevol cosa que no sigui GET; una fitxa a la capçalera Authorization no necessita capçalera CSRF.

Aplicacions OAuth 2.0

Per permetre que les persones iniciïn sessió a la vostra aplicació amb el seu compte d'Antimatter, registreu una aplicació OAuth 2.0. Antimatter serà llavors el proveïdor OAuth:

  1. Habilita el proveïdor de serveis OAuth 2.0 ha d’estar activat (Consola del sistema › Integracions › Gestió d'integracions, ServiceSettings.EnableOAuthServiceProvider, activat per defecte).
  2. Alguien amb el dret de gestionar aplicacions OAuth (els administradors del sistema per defecte) obre el seu avatar, després Integracions › Aplicacions OAuth 2.0, i afegeix l'aplicació amb les seves URL de callback. Rep un ID de client i un secret de client.
  3. La vostra aplicació envia les persones a https://chat.example.com/oauth/authorize amb response_type=code, client_id, redirect_uri i state. Es suporta PKCE amb code_challenge_method=S256.
  4. Intercanvia el codi a POST https://chat.example.com/oauth/access_token (grant_type=authorization_code, i després refresh_token per renovar-lo) i crida la API amb Authorization: Bearer <access token>.

Les persones veuen les aplicacions que han autoritzat a Perfil i configuració › Seguretat › Aplicacions que has autoritzat.

Publicar un missatge

curl -X POST https://chat.example.com/api/v4/posts \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"channel_id": "'$CHANNEL_ID'", "message": "Backup finished: **42 GB** in 3 min"}'

Els missatges són Markdown. Afegiu "root_id" (el primer missatge d'un fil) per respondre en un fil, "file_ids" per als fitxers i "props" per als adjunts i altres elements addicionals (vegeu Adjunts).

Trobar l'ID d'un canal

curl -H "Authorization: Bearer $TOKEN" \
  https://chat.example.com/api/v4/teams/name/lumen-labs/channels/name/ops-alerts

Els noms són els del vincle del canal: /lumen-labs/channels/ops-alerts.

Paginació

Els punts finals de llistes accepten page (des de 0) i per_page (60 per defecte, com a màxim 200). Seguiu demanant la pàgina següent fins que una pàgina torni més curta que per_page.

Els missatges d'un canal (GET /channels/{channel_id}/posts) també accepten since (un temps: tot el que ha canviat des d'aleshores), o before i after (un ID de publicació). Torna com una llista de publicacions: {"order": [IDs, newest first], "posts": {ID: post}, "next_post_id", "prev_post_id"}.

Errors

Els errors utilitzen els codis d'estat HTTP habituals (400 entrada incorrecta, 401 no autenticat, 403 no permès, 404 no trobat, 501 funció desactivada) i un cos JSON:

{
  "id": "api.context.permissions.app_error",
  "message": "You do not have the appropriate permissions.",
  "detailed_error": "",
  "request_id": "jz8zm5nunpbt8f3gpqsz5dq6so",
  "status_code": 403
}

Utilitzeu id al vostre codi: message es tradueix a la llengua de l'usuari. detailed_error queda buit, llevat que el servidor s'executi en mode de desenvolupament (ServiceSettings.EnableDeveloper). Citeu request_id a l'administrador del servidor: es troba als registres.

Límits de freqüència

La limitació de freqüència està desactivada per defecte. Quan un administrador del sistema l’activa (Consola del sistema › Entorn › Limitació de freqüència), cada client rep 10 sol·licituds per segon amb pics de 100 per defecte, comptades per adreça IP o per usuari. Les respostes inclouen X-RateLimit-Limit, X-RateLimit-Remaining i X-RateLimit-Reset; si es supera el límit, el servidor respon 429 amb una capçalera Retry-After en segons. Alguns punts d’accés, com ara l’inici de sessió, tenen el seu propi límit independentment de la configuració.

Escriveu scripts que esperin i tornin a provar en cas de 429, i eviteu la sondeja: seguiu el WebSocket en lloc d'això.

El flux d'esdeveniments del WebSocket

Connecteu-vos a wss://chat.example.com/api/v4/websocket. Autentiqueu-vos amb la capçalera Authorization: Bearer a la petició de connexió, o bé enviant això com a primer missatge:

{"seq": 1, "action": "authentication_challenge", "data": {"token": "…"}}

El servidor envia un esdeveniment hello i, a continuació, un esdeveniment per a tot el que esteu autoritzats a veure:

{
  "event": "posted",
  "data": {"channel_id": "…", "channel_type": "O", "post": "{\"id\":\"…\",\"message\":\"Hello\",…}"},
  "broadcast": {"channel_id": "…", "team_id": "", "user_id": "", "omit_users": null},
  "seq": 4
}

Ateneu-vos que data.post és el missatge com a cadena JSON. Esdeveniments habituals: posted, post_edited, post_deleted, reaction_added, reaction_removed, typing, status_change, user_added, direct_added. Les aplicacions envien els seus propis esdeveniments, anomenats custom_<app id>_<event>.

També podeu enviar accions, cadascuna amb un seq creixent: user_typing amb {"channel_id", "parent_id"}, o get_statuses. Reconnecteu-vos quan la connexió es trenqui i recupereu el que heu perdut amb since (vegeu Paginació).

Antimatter afegeix aquests esdeveniments: community_attributes_updated, member_timeouts_updated, post_put_on_top, post_removed_from_top, server_categories_updated, channel_overrides_updated i category_overrides_updated.

Biblioteques de client

  • Vés: model.Client4 a server/public/model (importa github.com/mattermost/mattermost/server/public/model). model.NewAPIv4Client(url), després client.SetToken(token); model.NewWebSocketClient4(wsURL, token) segueix els esdeveniments. La còpia d’Antimatter afegeix mètodes per als seus propis punts d’accés, com ara UpdateMessageRequest, PutPostOnTop i ExportChannel.
  • TypeScript: la classe Client4 de @mattermost/client, a webapp/platform/client, amb els seus tipus a webapp/platform/types. La còpia al repositori d'Antimatter inclou els punts d'accés d'Antimatter; el paquet publicat a npm per Mattermost no els inclou.
package main

import (
	"context"
	"log"

	"github.com/mattermost/mattermost/server/public/model"
)

func main() {
	client := model.NewAPIv4Client("https://chat.example.com")
	client.SetToken("…")
	post, _, err := client.CreatePost(context.Background(), &model.Post{
		ChannelId: "…",
		Message:   "Hello from Go",
	})
	if err != nil {
		log.Fatal(err)
	}
	log.Println("posted", post.Id)
}

Nous camps

  • Comunitats (Team, i PUT /teams/{team_id}/patch): all_channels_membership (tots els membres estan en tots els canals que poden veure), default_channel_id (on aterren els nous membres; si està buit, és el canal General), kind (community o workplace: en un lloc de treball, els administradors de canal també poden arxivar els seus canals; les noves comunitats reben el TeamSettings.DefaultCommunityKind del servidor, community per defecte), member_list_view (com s'agrupen els membres a la llista de membres: choice, l'opció per defecte, permet a cada membre triar; roles o teams fixa l'agrupació), hide_role_colors, require_team_badges, onboarding i autolinks (tots dos cadenes JSON).
  • El canal per defecte d'una nova comunitat és general (General), no town-square. La actualització a la 0.9.0 canvia el nom de town-square de cada comunitat a general, mantenint-ne l'ID, llevat que la comunitat ja tingui un canal general. Els noms antics continuen funcionant: GET /teams/{team_id}/channels/name/town-square, GET /teams/name/{team}/channels/name/town-square i el channel d'un webhook entrant donen el canal per defecte de la comunitat quan cap canal té aquest nom. Utilitzeu default_channel_id, o el nom general, en el codi nou.
  • Enllaços de canals: els enllaços #channel-name enllacen un canal, com fan els ~channel-name. La propietat channel_mentions de la publicació llista els canals enllaçats de qualsevol manera; un #word que no correspon a cap canal es manté com a hashtag. La interfície web i l'aplicació mòbil d'Antimatter escriuen #name.
  • Els canals arxivats encara accepten nous membres (POST /channels/{channel_id}/members), que poden llegir-ne l'historial. Ningú no pot publicar-hi, reaccionar-hi, fixar-hi res, posar-hi un missatge a la part superior, canviar-ne el nom ni modificar-hi els rols dels membres.
  • Respostes en línia: una publicació amb "props": {"reply_to": "<post id>"} cita aquest missatge del mateix canal. Afegeix "reply_to_mention": false per no notificar-ne l'autor. El servidor omple metadata.reply_to amb una descripció breu del missatge citat.
  • Alertes de contingut: "props": {"spoiler": true} amaga el text i els fitxers d'una publicació fins que el lector decideixi veure'ls.
  • Ignorar i bloquejar són preferències: categoria user_block, anomenada segons el ID de l'altra persona, amb el valor ignore o block. Si un missatge directe espera com a sol·licitud, es troba al notify_props.dm_request del teu membre del canal (pending, accepted o dismissed).
  • Els adjunts de missatge poden portar stages i un chart: consulta Targetes.

Mou un fil

POST /posts/{post_id}/move_to_channel mou un fil, el seu primer missatge i totes les seves respostes, a un altre canal de la mateixa comunitat. post_id pot ser el primer missatge o qualsevol resposta.

curl -X POST https://chat.example.com/api/v4/posts/$POST_ID/move_to_channel \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"channel_id": "'$TARGET_CHANNEL_ID'", "flatten": false}'
  • channel_id (obligatori): el canal on es mou el fil.
  • flatten (per defecte false): true converteix les respostes en missatges del canal de destinació en lloc d'un fil. La funció Fes-ne un canal de Fusion l'utilitza.

Els missatges mantenen els seus autors, hores, reaccions i fitxers. Les seves còpies porten la propietat silent_notification, de manera que no notifiquen ningú. Els missatges originals s'eliminen. La resposta és el primer missatge mogut, amb el seu nou ID.

Qui pot moure un fil

  • Heu de poder llegir el fil i publicar al canal de destinació.
  • Els administradors del canal, els administradors de la comunitat, les persones amb Gestiona els missatges (delete_others_posts) al canal i els administradors del sistema poden moure qualsevol fil.
  • L'autor del fil el pot moure quan tots dos canals són públics, o quan tots els missatges del fil són seus. En cas contrari, la resposta és 403 amb l'ID api.post.move_thread.private_needs_moderator.app_error.
  • Ambdós canals han de pertànyer a la mateixa comunitat (no missatges directes ni de grup), ser diferents i no estar arxivats. No es poden moure missatges de sistema ni missatges que s'eliminen en llegir-los.
  • Un fil amb més de WranglerSettings.MoveThreadMaxCount missatges (100 per defecte; 0 per sense límit) es rebutja.

El punter i la nota

El moviment deixa dos missatges de sistema de tipus system_wrangler: un punter al canal d'origen («Un fil amb 13 missatges s'ha mogut a #target») i una nota al destí («Aquest fil s'ha mogut des de #source»), sota el fil mogut o, amb flatten, després dels seus missatges. A més del text del missatge, les seves propietats permeten a un client dibuixar el nom del canal com un enllaç:

  • El punter: MovedThreadPermalink, NumMessages, MovedThreadChannelId, MovedThreadTeamName, MovedThreadPostId i, per a un destí públic, MovedThreadChannelName i MovedThreadChannelDisplayName.
  • La nota: MovedFromChannelId, MovedFromTeamName, MovedFromPostId (el punter), MovedFromPermalink i, per a un origen públic, MovedFromChannelName i MovedFromChannelDisplayName.

Ambdós tenen també un TranslationID. El nom d'un canal privat s'ometeix: els lectors veuen «un altre canal». L'endpoint POST /posts/{post_id}/move de Mattermost queda desactivat a Antimatter; utilitza aquest endpoint.

Connexions de models

Una connexió de model és l'adreça i la clau d'un proveïdor d'IA, configurada per un administrador. Les funcions d'IA del servidor i les aplicacions que criden el servei d'IA les utilitzen. Els administradors de sistema gestionen les connexions de tot el servidor (manage_ai_connections); els administradors d'una comunitat gestionen les de la seva comunitat (manage_team_ai_connections). Les claus són només d'escriptura: cap resposta les conté, només api_key_set i api_key_last4.

Punt d'accésQuè fa
GET /ai/connections?scope=Les connexions que gestiones. scope és server o l'ID d'una comunitat; sense ell, tots els àmbits que gestiones.
POST /ai/connectionsAfegeix una connexió (respon 201).
POST /ai/connections/test, POST /ai/connections/modelsProva una connexió, o n'enumera els models, abans de desar-la. Mateix cos que per afegir-ne una; no es desa res.
GET, PATCH (o PUT), DELETE /ai/connections/{connection_id}Llegeix, canvia o elimina una connexió. Un patch porta només els camps a canviar; deixa fora api_key per mantenir la clau.
POST /ai/connections/{connection_id}/testProva una connexió desada: {"ok", "error", "status_code", "latency_ms", "model_count"}.
GET /ai/connections/{connection_id}/modelsEls models que ofereix el proveïdor.
GET /ai/connections/{connection_id}/usageLes sol·licituds i els tokens d'aquest mes.
GET /ai/connections/usable?channel_id=&team_id=Per a qualsevol usuari iniciat: les connexions que hi podeu utilitzar, amb els seus models i capacitats, mai les seves claus o adreces.

El cos d'una connexió nova:

{
  "name": "Local models",
  "scope": "server",
  "provider": "openai_compatible",
  "base_url": "http://llm.internal:8000/v1",
  "api_key": "…",
  "extra_headers": {},
  "models": {"chat": "qwen3-32b", "embeddings": "", "transcription": "", "decisions": ""},
  "limits": {"requests_per_minute": 0, "monthly_token_budget": 0, "per_user_requests_per_minute": 0, "per_user_monthly_token_budget": 0},
  "sharing": {"all_teams": true, "team_ids": []},
  "audience": {"everyone": true, "group_ids": [], "roles": [], "allow_guests": false}
}

provider és openai_compatible o anthropic. scope per defecte és server; l'ID d'una comunitat la converteix en la connexió d'aquesta comunitat. A limits, 0 significa sense límit; les sol·licituds per minut es compten a cada servidor, i els pressupostos de tokens per mes calendàric (UTC) són per a tot el clúster. sharing indica quines comunitats poden utilitzar una connexió de tot el servidor (els missatges directes i de grup requereixen all_teams), i audience qui pot utilitzar-la; els invitats només amb allow_guests. Els canvis s'escriuen al registre d'auditoria. La guia d'administració explica la configuració: vegeu IA.
