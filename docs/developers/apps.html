Writing apps (plugins)

Apps add features to Antimatter from the inside: a server part in Go that hooks into the server, and a web app part in React that adds menus, panels, message types and pages. This page shows how an app is laid out, using the bundled Polls app as the example, and what changes in Antimatter's Fusion interface.

How an app works

  • The server part is a Go program. The server starts it as a separate process and talks to it over RPC: it calls the app's hooks (a message is about to be posted, a command was run…), and the app calls the server's plugin API (create a post, read a user, store data…). It can also serve HTTP routes under /plugins/<app id>/.
  • The web app part is a JavaScript bundle loaded into the browser with the web app. It registers React components and callbacks with the registry: a button in a menu, a panel, a way to draw a message type.
  • Either part is optional. An app is installed as a .tar.gz bundle, and system admins enable, disable and configure it.
The server part runs with full access to the server's data. Treat an app like code you deploy to the server.

Antimatter runs apps written for Mattermost, and the other way round, as long as an app only uses hooks both have. See Hooks only Antimatter has.

The bundle layout

There is no separate starter template: start from a small bundled app such as antimatter-plugin-polls or antimatter-plugin-todo, and change its ID and code. Polls is laid out like this:

antimatter-plugin-polls/
├── plugin.json            the manifest
├── Makefile               build, test, bundle, deploy
├── build/                 the manifest and pluginctl helper tools (Go), setup.mk
├── assets/icon.svg        files shipped with the bundle
├── go.mod
├── server/
│   ├── main.go            plugin.ClientMain(&Plugin{})
│   ├── plugin.go          the Plugin type, OnActivate, ServeHTTP
│   ├── manifest.go        generated from plugin.json
│   ├── api.go, command.go, hooks.go, store.go …
│   └── dist/              compiled binaries, one per platform
└── webapp/
    ├── package.json, webpack.config.js, tsconfig.json
    ├── i18n/              en.json and one file per language
    ├── src/index.tsx      registers the app with the web app
    ├── src/manifest.ts    generated from plugin.json
    ├── src/translations.ts
    └── dist/main.js       the bundle

Optional: a public/ folder, served as is at /plugins/<app id>/public/.

plugin.json

{
  "id": "com.example.weather",
  "name": "Weather",
  "description": "Forecasts in the chat.",
  "homepage_url": "https://github.com/example/weather",
  "support_url": "https://github.com/example/weather/issues",
  "icon_path": "assets/icon.svg",
  "version": "1.0.0",
  "min_server_version": "12.0.0",
  "server": {
    "executables": {
      "linux-amd64": "server/dist/plugin-linux-amd64",
      "linux-arm64": "server/dist/plugin-linux-arm64",
      "darwin-amd64": "server/dist/plugin-darwin-amd64",
      "darwin-arm64": "server/dist/plugin-darwin-arm64",
      "windows-amd64": "server/dist/plugin-windows-amd64.exe"
    }
  },
  "webapp": {"bundle_path": "webapp/dist/main.js"},
  "settings_schema": {"settings": []}
}
  • id: unique and permanent; a reverse domain name is usual. It names the routes, the stored settings and the WebSocket events.
  • version: semantic version. The bundled apps leave it out of plugin.json; their build tool takes it from the latest v* git tag.
  • min_server_version: Antimatter reports 12.0.0.
  • settings_schema: the app's settings page in the System Console (see Settings).

make apply copies the manifest into server/manifest.go and webapp/src/manifest.ts; make manifest-check validates it.

The server part

The server part imports the same Go module as Mattermost apps, github.com/mattermost/mattermost/server/public, from the Go module proxy. Its main only starts the app:

package main

import "github.com/mattermost/mattermost/server/public/plugin"

func main() {
	plugin.ClientMain(&Plugin{})
}

The Plugin type embeds plugin.MattermostPlugin, which gives it p.API, and implements the hooks it needs:

type Plugin struct {
	plugin.MattermostPlugin
	router *mux.Router
}

func (p *Plugin) OnActivate() error {
	p.router = p.newRouter()
	return p.API.RegisterCommand(&model.Command{
		Trigger:          "weather",
		AutoComplete:     true,
		AutoCompleteDesc: "Show the forecast",
		AutoCompleteHint: "[city]",
	})
}

func (p *Plugin) ExecuteCommand(c *plugin.Context, args *model.CommandArgs) (*model.CommandResponse, *model.AppError) {
	city := strings.TrimSpace(strings.TrimPrefix(args.Command, "/weather"))
	return &model.CommandResponse{
		ResponseType: model.CommandResponseTypeEphemeral,
		Text:         "Forecast for " + city + ": sunny",
	}, nil
}

func (p *Plugin) ServeHTTP(c *plugin.Context, w http.ResponseWriter, r *http.Request) {
	p.router.ServeHTTP(w, r)
}

Common hooks

HookWhen it runs
OnActivate, OnDeactivateWhen the app is enabled or disabled, and when the server starts and stops. Register commands and bots in OnActivate.
OnConfigurationChangeWhen its settings change; load them with p.API.LoadPluginConfiguration(&cfg).
ServeHTTPRequests to /plugins/<app id>/…. The server sets the Mattermost-User-Id header when the request comes from a signed-in user; refuse requests without it unless they are meant to be public.
ExecuteCommandA command the app registered was run.
MessageWillBePosted, MessageWillBeUpdatedBefore a message is saved: return a changed post, or a reason to reject it.
MessageHasBeenPosted, MessageHasBeenUpdated, MessageHasBeenDeletedAfter the fact, for side effects.
ReactionHasBeenAdded, ReactionHasBeenRemovedReactions.
UserHasJoinedChannel, UserHasLeftChannel, UserHasJoinedTeam, UserHasLeftTeam, ChannelHasBeenCreatedMembership and channel changes. A team is a community.
FileWillBeUploadedBefore a file is stored: change it or reject it.
OnPluginClusterEventA message from the same app on another server of a cluster.

The full list, with the exact signatures, is in server/public/plugin/hooks.go; the API is in server/public/plugin/api.go. The pluginapi package (server/public/pluginapi) wraps the API in friendlier helpers.

Useful API calls

  • CreatePost, UpdatePost, SendEphemeralPost: post as the app's bot or as a user.
  • EnsureBotUser(&model.Bot{Username, DisplayName}): create the app's bot once and get its ID.
  • PublishWebSocketEvent("poll_updated", payload, &model.WebsocketBroadcast{ChannelId: id}): send an event to the web app. It arrives as custom_<app id>_poll_updated.
  • OpenInteractiveDialog: open a dialog.
  • LogInfo, LogError and friends: write to the server log, tagged with the app's ID.
  • GetUser, GetChannel, HasPermissionToChannel: check who may do what before acting for a user.

An app runs on every server of a cluster. Keep state in the key-value store or the database, not only in memory.

Storing data

Each app has its own key-value store in the server's database:

  • KVSet(key, value), KVGet(key), KVDelete(key): values are bytes, usually JSON. Keys are at most 150 characters.
  • KVSetWithExpiry(key, value, seconds): the value disappears after that time.
  • KVCompareAndSet(key, old, new) and KVSetWithOptions with Atomic: safe updates when several requests or servers write the same key. Polls saves every vote this way and retries on conflict.
  • KVList(page, perPage): the keys, page by page.

The web app part

The bundle registers a class with window.registerPlugin. Its initialize receives the registry and the Redux store:

import manifest from './manifest';

class Plugin {
    initialize(registry, store) {
        registry.registerTranslations((locale) => translationsFor(locale));
        registry.registerPostTypeComponent('custom_poll', PollPost);
        registry.registerWebSocketEventHandler(`custom_${manifest.id}_poll_updated`, (msg) => {
            store.dispatch(pollUpdated(JSON.parse(msg.data.poll)));
        });
        registry.registerReconnectHandler(() => store.dispatch(reloadPolls()));
    }
}

window.registerPlugin(manifest.id, new Plugin());
  • Shared libraries. The web app provides React, ReactDOM, Redux, React Redux and React Intl: list them as webpack externals (React, ReactDOM, Redux, ReactRedux, ReactIntl) rather than bundling your own copies. See Polls' webpack.config.js.
  • Calling your server part. Fetch ${window.basename}/plugins/<app id>/… with the options from Client4.getOptions() (from mattermost-redux/client): they carry the headers the server needs to accept a request from the browser.
  • Your own state. registerReducer adds a reducer, stored under state['plugins-<app id>'].
  • Types. Antimatter's extra registry methods aren't in Mattermost's published types: Polls declares the registry it uses in webapp/src/types/host.ts.

The registry's methods and their parameters are documented in the code, in webapp/fusion/src/plugins/registry.ts (Fusion) and webapp/channels/src/plugins/registry.ts (classic).

Supporting the Fusion interface

Antimatter has two web interfaces: Fusion, the default, and the classic one. Both load the same app bundles and have the same registry, but Fusion draws many things itself and places plugin components in its own way. Test your app in both.

Detect the interface

Before any app loads, both interfaces set window.antimatterWebUI to 'fusion' or 'classic', and the same value on the page's root element as data-am-web-ui. On Mattermost, neither is set.

export function isFusionUI(): boolean {
    return window.antimatterWebUI === 'fusion' || document.documentElement.dataset.amWebUi === 'fusion';
}

The bundled apps use this to draw differently. Polls draws its poll cards and its creation dialog in Fusion's style, and opens its own dialog for /poll in Fusion. Calls and Voice channels leave out the sidebar and toast components that Fusion replaces with its own call interface. The Agents app puts its AI actions in a submenu of the message menu instead of the hover toolbar. Fusion's own CSS classes (prefixed am-) and its dialog layer (the am-layer element) are what these apps use to match the interface; they are not a documented, stable API.

What Fusion doesn't show or run

  • registerPostDropdownMenuComponent (a component in the message menu), registerPostCardTypeComponent (a post's card in the right-hand panel) and registerProductSwitcherMenuItem are not shown in Fusion's main views. Use registerPostDropdownMenuAction instead of the first.
  • registerMessageWillBeUpdatedHook doesn't run when a message is edited in Fusion. Check edits on the server with the MessageWillBeUpdated hook instead.
  • registerActionAfterChannelCreation only runs from the classic channel creation dialog, which Fusion opens from More options… in its Create channel dialog.
  • App bar components are shown whatever their supportedProductIds.
  • Routes from registerNeedsTeamRoute and registerCustomRoute keep the classic page frame, like products.

Hooks only Antimatter has

These registry methods don't exist on Mattermost. Check that a method exists before calling it, so the app also works there:

if (typeof registry.registerComposerMenuItem === 'function') {
    registry.registerComposerMenuItem({
        text: 'Create a poll',
        icon: <i className='icon icon-chart-bar'/>,
        fusionIcon: 'poll',
        action: ({channelId, rootId}) => openPollCreation(channelId, rootId),
    });
} else {
    registry.registerChannelHeaderButtonAction(icon, (channel) => openPollCreation(channel.id), 'Create a poll', 'Create a poll');
}
MethodWhat it adds
registerComposerMenuItem({text, icon, fusionIcon, action, shouldRender})An item in the message box's + menu, in both interfaces. action receives {channelId, rootId}.
registerEmojiPickerTab({id, label, icon, fusionIcon, order, component, shouldRender, replacesGifPicker})A tab of the message box's emoji picker, such as GIFs or stickers. In Fusion, tabs with an order below 10 come before the Emoji tab. The component receives channelId, rootId, filter, onFilterChange, onSelectDone, insertText and isFusion.
registerChannelViewPanel({matcher, component})A panel between the channel header and the messages, for the channels matcher(state, channel) selects. It can hide the messages and the composer (setMessagesVisible), as voice channels do.
registerSidebarChannelFooterComponent(component)A line under a channel in the sidebar, such as the people in its call. It receives the channel.
registerIntegrationsOption({title, description, fusionIcon, action, shouldRender})Fusion only: an entry on the Integrations pages, next to custom emoji. The GIFs app adds its custom GIFs and stickers there.

Settings

settings_schema in plugin.json describes the app's page in System Console › Plugins:

"settings_schema": {
  "header": "Forecasts come from the weather service below.",
  "settings": [
    {"key": "ServiceURL", "display_name": "Service URL", "type": "text", "default": "https://api.example.com"},
    {"key": "Units", "display_name": "Units", "type": "dropdown", "default": "metric",
     "options": [{"display_name": "Celsius", "value": "metric"}, {"display_name": "Fahrenheit", "value": "imperial"}]},
    {"key": "EnableAlerts", "display_name": "Severe weather alerts", "type": "bool", "default": false,
     "help_text": "Post alerts in the channels that follow a city."}
  ]
}

Setting types: bool, text, longtext, number, dropdown, radio, generated (a random secret), username, and custom (drawn by a component the web app part registers with registerAdminConsoleCustomSetting). Settings can be grouped in sections.

The server part reads them into a struct whose fields match the keys:

type configuration struct {
	ServiceURL   string
	Units        string
	EnableAlerts bool
}

func (p *Plugin) OnConfigurationChange() error {
	var cfg configuration
	if err := p.API.LoadPluginConfiguration(&cfg); err != nil {
		return err
	}
	p.setConfiguration(&cfg)
	return nil
}

Admins can also set them in the configuration, under PluginSettings.Plugins.<app id>, with keys in lower case (see the admin guide).

Translations

Antimatter is translated into 37 languages, and the bundled apps are too. The web app part does it like this:

  1. Write every string with React Intl, with an ID and its English text: <FormattedMessage id='polls.create' defaultMessage='Create a poll'/> or defineMessages. Prefix the IDs with your app's name.
  2. Extract the English strings into webapp/i18n/en.json (the bundled apps use formatjs extract).
  3. Add one file per language next to it, with the same IDs: fr.json, de.json, pt-BR.json, zh-CN.json…
  4. Give them to the web app, which asks for the user's language: 
    import fr from '../i18n/fr.json';
import ptBR from '../i18n/pt-BR.json';

const catalogs = {fr, 'pt-BR': ptBR};

export function translationsFor(locale) {
    return catalogs[locale] || catalogs[locale.split('-')[0]] || {};
}

registry.registerTranslations(translationsFor);

A missing string falls back to its English defaultMessage. For strings the server part sends (command answers, bot messages), the pluginapi/i18n package loads translation files shipped in the bundle (for example assets/i18n) and gives a localizer in each user's language.

Build, install and debug

You need Go and Node.js (the version in the app's .nvmrc). In the app's folder:

CommandWhat it does
make distBuilds the server part for every platform and the web app part, and writes the bundle to dist/<app id>-<version>.tar.gz.
make testRuns the Go and JavaScript tests.
make check-styleLints the code (golangci-lint, ESLint) and checks the TypeScript types.
make deployBuilds, then installs and enables the bundle on a server.
make watch, make deploy-from-watchThe first rebuilds the web app part each time you save; the second bundles what it built and installs it on the server.
make enable, make disable, make resetEnable, disable, or restart the app on the server.
make logs, make logs-watchShow the app's lines of the server log.
make attachAttaches the Delve debugger to the running server part (build with AM_DEBUG=1 first).

make deploy and the other server commands use a local mode socket when they find one (/var/tmp/antimatter_local.socket, or AM_LOCALSOCKETPATH): run them on the server's machine with local mode on. Otherwise they sign in to the server given by MM_SERVICESETTINGS_SITEURL with AM_ADMIN_TOKEN, or AM_ADMIN_USERNAME and AM_ADMIN_PASSWORD. The build tools don't read an AM_ name for the site URL yet.

Install a bundle by hand

  • A system admin allows uploads with AM_PLUGINSETTINGS_ENABLEUPLOADS=true (off by default; there is no System Console switch).
  • Then System Console › Plugins › Plugin Management › Upload Plugin, or amctl plugin add weather.tar.gz followed by amctl plugin enable com.example.weather.
  • If the server has Require Plugin Signature on, it only accepts bundles signed with a key it trusts; see Installing other apps.
For quick iterations on a development server, set AM_SERVICESETTINGS_ENABLEDEVELOPER=true on the server: errors then carry their details. The bundled apps' Makefiles build the server part for your platform only when MM_SERVICESETTINGS_ENABLEDEVELOPER is set in your shell.
