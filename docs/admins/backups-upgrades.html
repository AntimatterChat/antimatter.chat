Backups and upgrades

What to back up, how to restore it on a new host, how to upgrade, and how to move a Mattermost server or a single community to Antimatter.

What to back up

Uploaded files, images, and installed appsvolume antimatter_files (the S3 storage)FileSettings.Directory, ./data/ by default/var/lib/antimatter

GIFs and stickersvolume antimatter_gifsthe GIF service's data directory/var/lib/gifs-server

Without the AI encryption key, a restored server can't read the API keys of its model connections, and each one has to be typed again. Keep a copy of the key apart from the database backups, so that one stolen backup doesn't hold both. See The encryption key.

The database and the files belong together: back them up at the same time, and keep copies off the server. Volume names start with the compose project name, antimatter (docker volume ls lists them).

Back up

From the directory of compose.yaml. Stopping Antimatter first gives a fully consistent copy; a backup taken while it runs is usually fine, but files uploaded during the backup may be missing from it.

stamp=$(date +%Y%m%d-%H%M%S)
mkdir -p backups
docker compose stop antimatter
# Database
docker compose exec -T postgres pg_dump -U antimatter -d antimatter -Fc \
    > "backups/antimatter-db-$stamp.dump"
# File storage and GIF service
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data:ro" -v "$PWD/backups:/backup" \
        alpine tar -czf "/backup/antimatter-$v-$stamp.tar.gz" -C /data .
done
docker compose start antimatter
# Secrets
cp .env "backups/env-$stamp"

If you haven't set AM_AI_ENCRYPTION_KEY and the server has created its key file, copy the file too (once is enough: it doesn't change): docker compose cp antimatter:/antimatter/data/ai-encryption.key "backups/ai-encryption.key". Better, put its content in .env as The encryption key explains: the backup of .env then holds it.

Run it from cron for daily backups, and copy the backups/ directory to another machine. Keep the copies of .env as safe as the server: they hold its passwords.

To copy the uploaded files object by object instead (for example to another S3 storage), use the AWS command-line tool of the bucket service:

docker compose run --rm -v "$PWD/backups/files:/backup" bucket \
    "aws --endpoint-url http://files:9000 s3 sync s3://antimatter /backup"

With a release archive, back up the database with pg_dump -Fc, and the data/ and config/ directories with your usual tools (data/ holds the AI key file). With the packages, back up the database the same way, and /etc/antimatter, /var/lib/antimatter, /etc/gifs-server and /var/lib/gifs-server.

Restore on a new host

Put compose.yaml, the saved .env and the backups in a new directory, then:

stamp=20261016-030000          # the backup to restore
docker compose create           # creates the volumes, starts nothing
docker compose up -d postgres
docker compose exec -T postgres pg_restore -U antimatter -d antimatter --no-owner \
    < "backups/antimatter-db-$stamp.dump"
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data" -v "$PWD/backups:/backup" \
        alpine tar -xzf "/backup/antimatter-$v-$stamp.tar.gz" -C /data
done
docker compose up -d

Use the same .env: the storage and the database must keep the passwords they had, and the model connections need the same AI encryption key. If the new host has another address, update SITE_URL (and DOMAIN).

Test your backups by restoring them on another machine from time to time.

Upgrade

  1. Take a backup.
  2. Change the image tag in .env (ANTIMATTER_IMAGE), if you pin one, as recommended.
  3. Pull and restart: 
    docker compose pull
docker compose up -d
docker compose logs -f antimatter

On start, the server upgrades the database schema (follow it in the log; a large server can take several minutes) and installs the newer versions of the bundled apps from the image. With a release archive: stop the server, replace everything except config/, data/, logs/, plugins/ and client/plugins/ with the new archive's content, and start it again. With the .deb or .rpm package, install the new package as Upgrade a package explains.

Upgrades only go forward. Once a newer server has upgraded the database, an older version can't use it: to go back, restore the backup taken before the upgrade. The same applies to moving from antimatter-next back to antimatter.

Versions

Antimatter's server reports the version of the Mattermost line it is based on (currently 12.0.0). The releases on GitHub, with their archives and packages, have their own version numbers, in the 0.9.0 series during the beta: antimatter version shows it as Build Number. The images are rebuilt from the main branches: antimatter-next every night (tags nightly-<YYYYMMDD>), and both images on each change (tags sha-<commit>). Pin one of these tags, upgrade on purpose, and keep the previous tag noted so you know which backup goes with it.

PostgreSQL major versions

The compose file uses postgres:17-alpine. Antimatter needs PostgreSQL 15 or newer. A new major version of PostgreSQL can't read the previous one's data directory: to move to one, dump the database, start the new version on a new volume and restore the dump into it.

Upgrading to 0.9.0

The first start of version 0.9.0 (or of an image built from 17 October 2026 on) makes a few one-time changes to the data. Each runs once, and is recorded in the database. They bring what was left at an old default to the new one, and leave alone what an administrator chose. Follow them in the log.

If Antimatter is for a company or an organisation, set Kind of new communities to Workplace before you upgrade: AM_TEAMSETTINGS_DEFAULTCOMMUNITYKIND=workplace. The upgrade gives every community the kind this setting has at that moment, and calls are off by default in the channels of communities of the Community kind. See Workplace or community.
WhatThe change
Kinds of communityEvery community gets a kind, Community or Workplace: the value of Kind of new communities (TeamSettings.DefaultCommunityKind) at the first start. A kind already set is kept. Community admins can change their community's kind afterwards, in Community settings › Channels › Kind of community.
Who archives channelsChannel members no longer archive the channels they are in: community admins do. In a workplace, the channel's admins (whoever created it, and those they made admins) also archive it. This changes the roles of the system scheme; the permission schemes a system administrator made for some communities are left as they are.
The Moderators role of the layout presetsThe Moderators role that communities got from a layout preset gets Remove people, which timing people out and removing them need. Only roles still exactly as the preset made them change; a role someone edited is left alone.
Roles with AdministratorA community role with the Administrator switch on now holds everything the community's admins can do, as the switch says, not only the community's settings.
The member limitMax Members Per Community (TeamSettings.MaxUsersPerTeam) goes from 50, the old default, to 0 (no limit). Any other value is kept, and so is a limit set with AM_TEAMSETTINGS_MAXUSERSPERTEAM.
Model connectionsSystem administrators get the management of model connections, and community admins (and roles with Administrator) that of their community's own. The AI services of the Agents app become server-wide model connections, see below.
Town Square becomes GeneralEvery community's default channel is renamed from town-square (Town Square) to general (General). It keeps its ID, members, messages and settings, and a display name the admins chose. Old links and lookups by town-square still lead to it. A community that already has a channel named general, even archived, keeps its town-square as its default channel, and so does a community whose town-square is archived: the log names them, and their admins may rename the channels.
FavouritesEveryone's Favorites sidebar category is renamed Favourites, as the interface now says. Categories people created with that name are left alone.

The Agents app's services

The upgrade copies each AI service of the Agents app into a server-wide model connection, shared with every community and usable by everyone but guests (turn on Guests too to let them). The keys are encrypted on the way, so the server needs its AI encryption key: on a cluster whose files are in S3, set AM_AI_ENCRYPTION_KEY first, or the copy waits for the next start. Then check System Console › AI › Model connections:

  • Each connection keeps the ID of its service, so the app's agents and an auto-translation set to an Agents service still find it.
  • OpenAI, OpenAI-compatible, Anthropic, Mistral, Cohere and Gemini services become connections to their OpenAI-compatible (or Anthropic) endpoint. An Azure service becomes a connection to the resource's OpenAI-compatible endpoint: test it.
  • AWS Bedrock, Google Vertex AI and Cohere North services, and unknown types, are marked Needs attention, with the reason. Their cloud credentials aren't copied: point them at the provider's OpenAI-compatible endpoint or a gateway such as LiteLLM, then save.
  • The embedding service becomes the Embeddings model of the connection with the same address and key, or a connection of its own. The transcription service gets the whisper-1 model.
  • When the rewrite and recaps have no connection yet, they get the service and model of the app's default agent.

The Agents app's own settings and data are left as they were: its agents keep using its services.

Other changes of defaults

  • Calls: Test mode is off and Enable video is on by default. A choice saved in the configuration is kept. Calls also follow the kind of community (see Calls and voice).
  • Putting messages on top is for the channel's admins, the community's admins and moderators (with Manage messages); members of a direct or group message still can.
  • Archived channels can take new members, who read their history. Nobody posts, reacts or changes anything in them.

Moving from Mattermost

Antimatter uses Mattermost's database schema and adds its own tables, so it can take over a Mattermost server's PostgreSQL database and files. Try it on a copy first:

  1. Back up the Mattermost database, its file storage (data/ or S3 bucket) and config.json, then stop Mattermost.
  2. Restore the database into Antimatter's PostgreSQL, or point Antimatter at a copy of it (AM_SQLSETTINGS_DATASOURCE).
  3. Copy the files into Antimatter's storage, keeping their paths: to the antimatter bucket with an S3 tool, or to data/ with a release archive.
  4. Reuse your settings: copy config.json, or move it into the database with amctl --local config migrate (see Configuration). Your MM_ environment variables keep working; rename them to AM_ when convenient.
  5. Start Antimatter and follow the log while it upgrades the database. Then check System Console › Plugins › Plugin Management. Antimatter installs its own builds of Calls, Playbooks, Kanban (Boards), Agents and the integrations when they are newer than the installed version. If Mattermost had a newer version of one of them, remove that app and restart Antimatter, so that its own build is installed.
  6. Set up push notifications again, with your own push proxy: Antimatter never sends notifications to Mattermost's push services, test or hosted, which only deliver to Mattermost's own apps. Until you change Push Notification Server, the server sends no push notifications (see Push notifications).

Antimatter contacts no service run by Mattermost, Inc. (see Connections to outside services), even when your configuration still names one:

  • a push notification server at Mattermost is kept in the settings but never used;
  • Mattermost's addresses for the app marketplace (Marketplace URL) and for product notices are emptied;
  • the app download links that were Mattermost's defaults (Antimatter Apps Download Page Link, Android App Download Link and iOS App Download Link) are replaced by the download pages of Antimatter's apps on GitHub; links you set yourself are kept;
  • the Calls app uses Cloudflare's public STUN server instead of Mattermost's, without changing the saved setting (see Calls);
  • the security update check and crash reporting are gone, and so are their System Console settings (Enable Security Alerts, Enable Diagnostics and Error Reporting) and the Notices page.

The local mode socket is now /var/tmp/antimatter_local.socket; amctl also tries the old /var/tmp/mattermost_local.socket. Mattermost only supports PostgreSQL in its recent versions, and so does Antimatter: move a MySQL database to PostgreSQL first. Going back to Mattermost after Antimatter has upgraded the database means restoring your Mattermost backup.

Export and import data

The bulk export format moves data between servers: the whole server, some communities, or some channels, with attachments, profile pictures and custom emoji if you want them.

# on the source server
amctl export create --team-name design --include-profile-pictures
amctl export list
amctl export download <export file> design.zip
# on the destination server
amctl import upload design.zip
amctl import list available
amctl import process <uploaded file> --imported-users active

Watch the jobs with amctl export job list and amctl import job list. For a community or channel export, --imported-users is required: active when the people move to this server, inactive when importing into a server where they already have accounts, so accounts created from uncertain matches stay off until an administrator checks them. --destination-team-name imports into an existing community. Exports and imports are kept on the server's storage (ExportSettings.Directory, ImportSettings.Directory) for 30 days by default.

On the server itself, antimatter export bulk and antimatter import bulk --apply do the same from files, without the API.
