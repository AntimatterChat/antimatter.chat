Backups and upgrades

What to back up, how to restore it on a new host, how to upgrade, and how to move a Mattermost server or a single community to Antimatter.

What to back up

WhatWith the site's compose fileWith a release archive
The database: messages, users, communities, channels and, with the site's compose file, the configurationvolume antimatter_postgres, through pg_dumpyour PostgreSQL database
Uploaded files, images, and installed appsvolume antimatter_files (the S3 storage)FileSettings.Directory, ./data/ by default
The configuration file(in the database)config/config.json
GIFs and stickersvolume antimatter_gifsthe GIF service's data directory
Secrets.env (and compose.override.yaml)your environment file

The database and the files belong together: back them up at the same time, and keep copies off the server. Volume names start with the compose project name, antimatter (docker volume ls lists them).

Back up

From the directory of compose.yaml. Stopping Antimatter first gives a fully consistent copy; a backup taken while it runs is usually fine, but files uploaded during the backup may be missing from it.

stamp=$(date +%Y%m%d-%H%M%S)
mkdir -p backups
docker compose stop antimatter
# Database
docker compose exec -T postgres pg_dump -U antimatter -d antimatter -Fc \
    > "backups/antimatter-db-$stamp.dump"
# File storage and GIF service
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data:ro" -v "$PWD/backups:/backup" \
        alpine tar -czf "/backup/antimatter-$v-$stamp.tar.gz" -C /data .
done
docker compose start antimatter
# Secrets
cp .env "backups/env-$stamp"

Run it from cron for daily backups, and copy the backups/ directory to another machine. Keep the copies of .env as safe as the server: they hold its passwords.

To copy the uploaded files object by object instead (for example to another S3 storage), use the AWS command-line tool of the bucket service:

docker compose run --rm -v "$PWD/backups/files:/backup" bucket \
    "aws --endpoint-url http://files:9000 s3 sync s3://antimatter /backup"

With a release archive, back up the database with pg_dump -Fc, and the data/ and config/ directories with your usual tools.

Restore on a new host

Put compose.yaml, the saved .env and the backups in a new directory, then:

stamp=20261016-030000          # the backup to restore
docker compose create           # creates the volumes, starts nothing
docker compose up -d postgres
docker compose exec -T postgres pg_restore -U antimatter -d antimatter --no-owner \
    < "backups/antimatter-db-$stamp.dump"
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data" -v "$PWD/backups:/backup" \
        alpine tar -xzf "/backup/antimatter-$v-$stamp.tar.gz" -C /data
done
docker compose up -d

Use the same .env: the storage and the database must keep the passwords they had. If the new host has another address, update SITE_URL (and DOMAIN).

Test your backups by restoring them on another machine from time to time.

Upgrade

  1. Take a backup.
  2. Change the image tag in .env (ANTIMATTER_IMAGE), if you pin one, as recommended.
  3. Pull and restart: 
    docker compose pull
docker compose up -d
docker compose logs -f antimatter

On start, the server upgrades the database schema (follow it in the log; a large server can take several minutes) and installs the newer versions of the bundled apps from the image. With a release archive: stop the server, replace everything except config/, data/, logs/, plugins/ and client/plugins/ with the new archive's content, and start it again.

Upgrades only go forward. Once a newer server has upgraded the database, an older version can't use it: to go back, restore the backup taken before the upgrade. The same applies to moving from antimatter-next back to antimatter.

Versions

Antimatter's server reports the version of the Mattermost line it is based on (currently 12.0.0). The images are rebuilt from the main branches: antimatter-next every night (tags nightly-<YYYYMMDD>), and both images on each change (tags sha-<commit>). Pin one of these tags, upgrade on purpose, and keep the previous tag noted so you know which backup goes with it.

PostgreSQL major versions

The compose file uses postgres:17-alpine. Antimatter needs PostgreSQL 15 or newer. A new major version of PostgreSQL can't read the previous one's data directory: to move to one, dump the database, start the new version on a new volume and restore the dump into it.

Moving from Mattermost

Antimatter uses Mattermost's database schema and adds its own tables, so it can take over a Mattermost server's PostgreSQL database and files. Try it on a copy first:

  1. Back up the Mattermost database, its file storage (data/ or S3 bucket) and config.json, then stop Mattermost.
  2. Restore the database into Antimatter's PostgreSQL, or point Antimatter at a copy of it (AM_SQLSETTINGS_DATASOURCE).
  3. Copy the files into Antimatter's storage, keeping their paths: to the antimatter bucket with an S3 tool, or to data/ with a release archive.
  4. Reuse your settings: copy config.json, or move it into the database with amctl --local config migrate (see Configuration). Your MM_ environment variables keep working; rename them to AM_ when convenient.
  5. Start Antimatter and follow the log while it upgrades the database. Then check System Console › Plugins › Plugin Management. Antimatter installs its own builds of Calls, Playbooks, Kanban (Boards), Agents and the integrations when they are newer than the installed version. If Mattermost had a newer version of one of them, remove that app and restart Antimatter, so that its own build is installed.
  6. Set up push notifications again, with your own push proxy: Antimatter never sends notifications to Mattermost's push services, test or hosted, which only deliver to Mattermost's own apps. Until you change Push Notification Server, the server sends no push notifications (see Push notifications).

Antimatter contacts no service run by Mattermost, Inc. (see Connections to outside services), even when your configuration still names one:

  • a push notification server at Mattermost is kept in the settings but never used;
  • Mattermost's addresses for the app marketplace (Marketplace URL) and for product notices are emptied;
  • the Calls app uses Cloudflare's public STUN server instead of Mattermost's, without changing the saved setting (see Calls);
  • the security update check and crash reporting are gone, and so are their System Console settings (Enable Security Alerts, Enable Diagnostics and Error Reporting) and the Notices page.

The local mode socket is now /var/tmp/antimatter_local.socket; amctl also tries the old /var/tmp/mattermost_local.socket. Mattermost only supports PostgreSQL in its recent versions, and so does Antimatter: move a MySQL database to PostgreSQL first. Going back to Mattermost after Antimatter has upgraded the database means restoring your Mattermost backup.

Export and import data

The bulk export format moves data between servers: the whole server, some communities, or some channels, with attachments, profile pictures and custom emoji if you want them.

# on the source server
amctl export create --team-name design --include-profile-pictures
amctl export list
amctl export download <export file> design.zip
# on the destination server
amctl import upload design.zip
amctl import list available
amctl import process <uploaded file> --imported-users active

Watch the jobs with amctl export job list and amctl import job list. For a community or channel export, --imported-users is required: active when the people move to this server, inactive when importing into a server where they already have accounts, so accounts created from uncertain matches stay off until an administrator checks them. --destination-team-name imports into an existing community. Exports and imports are kept on the server's storage (ExportSettings.Directory, ImportSettings.Directory) for 30 days by default.

On the server itself, antimatter export bulk and antimatter import bulk --apply do the same from files, without the API.
