Резервне копіювання та оновлення

Що резервувати, як відновити на новому хості, як оновити, а також як перенести сервер Mattermost або окрему спільноту на Antimatter.

Що резервувати

ЩоЗ файлом compose сайтуЗ архівом релізу
База даних: повідомлення, користувачі, спільноти, канали та, у разі використання compose-файлу сайту, конфігураціятом antimatter_postgres, за допомогою pg_dumpваша база даних PostgreSQL
Завантажені файли, зображення та встановлені додаткитом antimatter_files (S3-сховище)FileSettings.Directory, за замовчуванням ./data/
Файл конфігурації(у базі даних)config/config.json
GIF та наклейкитом antimatter_gifsкаталог даних GIF-сервісу
Секрети.env (та compose.override.yaml)ваш файл середовища

База даних і файли належать одне до одного: резервуйте їх одночасно та зберігайте копії поза сервером. Назви томів починаються з назви compose-проєкту, antimatter (список томів можна отримати командою docker volume ls).

Резервне копіювання

Виконуйте з каталогу, де розташований compose.yaml. Зупинення Antimatter перед резервним копіюванням дає повністю послідовну копію; копія, зроблена під час роботи, зазвичай теж підходить, але файли, завантажені під час резервного копіювання, можуть у ній відсутнівати.

stamp=$(date +%Y%m%d-%H%M%S)
mkdir -p backups
docker compose stop antimatter
# Database
docker compose exec -T postgres pg_dump -U antimatter -d antimatter -Fc \
    > "backups/antimatter-db-$stamp.dump"
# File storage and GIF service
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data:ro" -v "$PWD/backups:/backup" \
        alpine tar -czf "/backup/antimatter-$v-$stamp.tar.gz" -C /data .
done
docker compose start antimatter
# Secrets
cp .env "backups/env-$stamp"

Заплануйте виконання через cron для щоденного резервного копіювання та копіюйте каталог backups/ на інший комп’ютер. Зберігайте копії .env так само безпечно, як і сам сервер: вони містять його паролі.

Щоб копіювати завантажені файли по одному об’єкту (наприклад, в інше S3-сховище), скористайтеся командним інструментом AWS сервісу bucket:

docker compose run --rm -v "$PWD/backups/files:/backup" bucket \
    "aws --endpoint-url http://files:9000 s3 sync s3://antimatter /backup"

Якщо використовуєте архів релізу, резервуйте базу даних за допомогою pg_dump -Fc, а каталоги data/ та config/ — звичними для вас інструментами.

Відновлення на новому хості

Помістіть compose.yaml, збережений .env та резервні копії в новий каталог, потім:

stamp=20261016-030000          # the backup to restore
docker compose create           # creates the volumes, starts nothing
docker compose up -d postgres
docker compose exec -T postgres pg_restore -U antimatter -d antimatter --no-owner \
    < "backups/antimatter-db-$stamp.dump"
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data" -v "$PWD/backups:/backup" \
        alpine tar -xzf "/backup/antimatter-$v-$stamp.tar.gz" -C /data
done
docker compose up -d

Використовуйте той самий .env: сховище та база даних мають зберегти свої паролі. Якщо у нового хоста інша адреса, оновіть SITE_URL (та DOMAIN).

Періодично перевіряйте резервні копії, відновлюючи їх на іншому комп’ютері.

Оновлення

  1. Зробіть резервну копію.
  2. Змініть тег образу в .env (ANTIMATTER_IMAGE), якщо ви фіксуєте версію, як рекомендовано.
  3. Отримайте образ і перезапустіть: 
    docker compose pull
docker compose up -d
docker compose logs -f antimatter

Під час запуску сервер оновлює схему бази даних (процес можна відстежити в журналі; на великому сервері це може тривати кілька хвилин) та встановлює новіші версії додатків, що входять до образу. Якщо використовується архів релізу: зупиніть сервер, замініть усе, крім config/, data/, logs/, plugins/ та client/plugins/, вмістом нового архіву, а потім запустіть сервер знову.

Оновлення можливі лише в напрямку до новіших версій. Щойно новіший сервер оновить базу даних, старіша версія не зможе її використовувати: щоб повернутися до попередньої версії, відновіть резервну копію, зроблену перед оновленням. Те саме стосується переходу з antimatter-next назад на antimatter.

Версії

Сервер Antimatter повідомляє версію рядка Mattermost, на основі якого він побудований (наразі 12.0.0). Образи збираються з гілок main: antimatter-next щовечора (теги nightly-<YYYYMMDD>), а обидва образи — при кожній зміні (теги sha-<commit>). Закріпіть один із цих тегів, оновлюйте навмисно та тримайте на увазі попередній тег, щоб знати, яка резервна копія йому відповідає.

Головні версії PostgreSQL

Файл compose використовує postgres:17-alpine. Antimatter потребує PostgreSQL 15 або новішу версію. Нова головна версія PostgreSQL не може читати каталог даних попередньої: щоб перейти на нову, зробіть дамп бази даних, запустіть нову версію на новому томі та відновіть дамп у неї.

Перехід з Mattermost

Antimatter використовує схему бази даних Mattermost та додає власні таблиці, тому може взяти під контроль базу даних PostgreSQL та файли сервера Mattermost. Спочатку спробуйте це на копії:

  1. Зробіть резервну копію бази даних Mattermost, сховища файлів (data/ або S3-бакета) та config.json, а потім зупиніть Mattermost.
  2. Відновіть базу даних у PostgreSQL Antimatter або вкажіть Antimatter на копію бази (AM_SQLSETTINGS_DATASOURCE).
  3. Скопіюйте файли до сховища Antimatter, зберігаючи їхні шляхи: у бакет antimatter за допомогою S3-інструменту або до data/ за допомогою архіву релізу.
  4. Повторно використовуйте свої налаштування: скопіюйте config.json або перенесіть його до бази даних за допомогою amctl --local config migrate (див. Налаштування). Ваші змінні середовища MM_ продовжують працювати; перейменуйте їх на AM_, коли буде зручно.
  5. Запустіть Antimatter і стежте за журналом під час оновлення бази даних. Потім перевірте Системна консоль › Плагіни › Керування плагінами. Antimatter встановлює власні збірки додатків Дзвінки, Плейбуки, Канбан (Дошки), Агенти та інтеграцій, якщо вони новіші за встановлену версію. Якщо в Mattermost була новіша версія одного з цих додатків, видаліть його та перезапустіть Antimatter, щоб встановилася його власна збірка.
  6. Знову налаштуйте push-повідомлення, використовуючи власний push-проксі: Antimatter ніколи не надсилає сповіщення на push-сервіси Mattermost, будь то тестові чи хостовані, оскільки вони доставляють сповіщення лише у власні додатки Mattermost. Доки ви не зміните Сервер push-повідомлень, сервер не надсилає жодних push-сповіщень (див. Push-сповіщення).

Antimatter не встановлює з’єднання з жодним сервісом, який працює під управлінням Mattermost, Inc. (див. З’єднання з зовнішніми сервісами), навіть якщо у вашій конфігурації все ще вказано такий сервіс:

  • push-сервер Mattermost зберігається в налаштуваннях, але ніколи не використовується;
  • адреси Mattermost для магазину додатків (URL-адреса магазину плагінів) та для продуктових оголошень очищуються;
  • додаток Дзвінки використовує публічний STUN-сервер Cloudflare замість сервера Mattermost, не змінюючи збережене налаштування (див. Дзвінки);
  • перевірка оновлень безпеки та звіт про аварії прибрано, а разом із ними й їхні налаштування в Системній консолі (Увімкнути сповіщення про безпеку, Увімкнути діагностику та звіт про помилки) і сторінку Оголошення.

Сокет локального режиму тепер /var/tmp/antimatter_local.socket; amctl також намагається скористатися старим /var/tmp/mattermost_local.socket. Mattermost підтримує лише PostgreSQL у своїх останніх версіях, і Antimatter теж: спочатку перенесіть базу даних MySQL на PostgreSQL. Повернення до Mattermost після того, як Antimatter оновив базу даних, означає відновлення вашої резервної копії Mattermost.

Експорт і імпорт даних

Формат пакетного експорту переносить дані між серверами: увесь сервер, окремі спільноти або окремі канали, разом із вкладеннями, профільними фото та власними емодзі, якщо ви цього хочете.

# on the source server
amctl export create --team-name design --include-profile-pictures
amctl export list
amctl export download <export file> design.zip
# on the destination server
amctl import upload design.zip
amctl import list available
amctl import process <uploaded file> --imported-users active

Спостерігайте за завданнями за допомогою команд amctl export job list та amctl import job list. Для експортування спільноти або каналу параметр --imported-users є обов’язковим: active, якщо користувачі переміщуються на цей сервер, або inactive, якщо імпорт виконується на сервері, де у них вже є акаунти, щоб акаунти, створені з невизначених збігів, залишалися неактивними, доки адміністратор не перевірить їх. Параметр --destination-team-name імпортує дані в існуючу спільноту. Файли експорту та імпорту зберігаються на сховищі сервера (ExportSettings.Directory, ImportSettings.Directory) протягом 30 днів за замовчуванням.

На самому сервері команди antimatter export bulk та antimatter import bulk --apply виконують ті самі дії з файлів, без використання API.
