Back-ups en upgrades

Wat u moet back-uppen, hoe u het herstelt op een nieuwe host, hoe u een upgrade uitvoert en hoe u een Mattermost-server of een enkele community verplaatst naar Antimatter.

Wat u moet back-uppen

WatMet het compose-bestand van de siteMet een releasearchief
De database: berichten, gebruikers, communities, kanalen en, met het compose-bestand van de site, de configuratievolume antimatter_postgres, via pg_dumpuw PostgreSQL-database
Geüploade bestanden, afbeeldingen en geïnstalleerde appsvolume antimatter_files (de S3-opslag)FileSettings.Directory, standaard ./data/
Het configuratiebestand(in de database)config/config.json
GIF’s en stickersvolume antimatter_gifsde gegevensmap van de GIF-service

De database en de bestanden horen bij elkaar: back-up ze tegelijk en bewaar kopieën op een andere locatie dan de server. Volume-namen beginnen met de projectnaam van compose, antimatter (docker volume ls toont ze).

Back-uppen

Voer dit uit vanuit de map van compose.yaml. Als u Antimatter eerst stopt, krijgt u een volledig consistente kopie; een back-up die wordt gemaakt terwijl het draait, is meestal prima, maar bestanden die tijdens de back-up worden geüpload, kunnen er ontbreken.

stamp=$(date +%Y%m%d-%H%M%S)
mkdir -p backups
docker compose stop antimatter
# Database
docker compose exec -T postgres pg_dump -U antimatter -d antimatter -Fc \
    > "backups/antimatter-db-$stamp.dump"
# File storage and GIF service
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data:ro" -v "$PWD/backups:/backup" \
        alpine tar -czf "/backup/antimatter-$v-$stamp.tar.gz" -C /data .
done
docker compose start antimatter
# Secrets
cp .env "backups/env-$stamp"

Voer dit via cron uit voor dagelijkse back-ups en kopieer de backups/-map naar een andere machine. Bewaar de kopieën van .env net zo veilig als de server: ze bevatten de wachtwoorden ervan.

Wilt u de geüploade bestanden object voor object kopiëren (bijvoorbeeld naar een andere S3-opslag), gebruik dan het AWS command-line tool van de bucket-service:

docker compose run --rm -v "$PWD/backups/files:/backup" bucket \
    "aws --endpoint-url http://files:9000 s3 sync s3://antimatter /backup"

Met een releasearchief back-upt u de database met pg_dump -Fc en de data/- en config/-mappen met uw gebruikelijke tools.

Herstellen op een nieuwe host

Plaats compose.yaml, het bewaarde .env en de back-ups in een nieuwe map, en:

stamp=20261016-030000          # the backup to restore
docker compose create           # creates the volumes, starts nothing
docker compose up -d postgres
docker compose exec -T postgres pg_restore -U antimatter -d antimatter --no-owner \
    < "backups/antimatter-db-$stamp.dump"
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data" -v "$PWD/backups:/backup" \
        alpine tar -xzf "/backup/antimatter-$v-$stamp.tar.gz" -C /data
done
docker compose up -d

Gebruik dezelfde .env: de opslag en de database moeten de wachtwoorden behouden die ze hadden. Als de nieuwe host een ander adres heeft, werk dan SITE_URL (en DOMAIN) bij.

Test uw back-ups door ze af en toe te herstellen op een andere machine.

Upgrade

  1. Maak een back-up.
  2. Wijzig de imagetag in .env (ANTIMATTER_IMAGE), als u er een vastzet, zoals aanbevolen.
  3. Haal op en herstart: 
    docker compose pull
docker compose up -d
docker compose logs -f antimatter

Bij het starten verhoogt de server het databasisschema (volg dit in het logboek; bij een grote server kan dit enkele minuten duren) en installeert de nieuwere versies van de ingebouwde apps uit het image. Bij een releasearchief: stop de server, vervang alles behalve config/, data/, logs/, plugins/ en client/plugins/ door de inhoud van het nieuwe archief, en start de server opnieuw.

Upgrades gaan alleen vooruit. Zodra een nieuwere server de database heeft geüpgraded, kan een oudere versie deze niet meer gebruiken: om terug te gaan, herstel de back-up die vóór de upgrade is gemaakt. Hetzelfde geldt voor het terugkeren van antimatter-next naar antimatter.

Versies

De server van Antimatter rapporteert de versie van de Mattermost-lijn waaraan het is gebaseerd (momenteel 12.0.0). De images worden opnieuw gebouwd vanuit de main-takken: antimatter-next elke nacht (tags nightly-<YYYYMMDD>) en beide images bij elke wijziging (tags sha-<commit>). Kies een van deze tags, upgrade bewust en houd de vorige tag bij zodat u weet welke back-up daarbij hoort.

Hoofdversies van PostgreSQL

Het compose-bestand gebruikt postgres:17-alpine. Antimatter vereist PostgreSQL 15 of nieuwer. Een nieuwe hoofdversie van PostgreSQL kan de datamap van de vorige versie niet lezen: om over te stappen, dump de database, start de nieuwe versie op een nieuwe volume en herstel de dump daarin.

Overstappen van Mattermost

Antimatter gebruikt het databasisschema van Mattermost en voegt eigen tabellen toe, waardoor het de PostgreSQL-database en bestanden van een Mattermost-server kan overnemen. Probeer dit eerst op een kopie:

  1. Maak een back-up van de Mattermost-database, de opslag van de bestanden (data/ of S3-bak) en config.json, en stop daarna Mattermost.
  2. Herstel de database in de PostgreSQL van Antimatter, of wijs Antimatter naar een kopie ervan (AM_SQLSETTINGS_DATASOURCE).
  3. Kopieer de bestanden naar de opslag van Antimatter, waarbij u de paden behoudt: naar de antimatter-bak met een S3-hulpmiddel, of naar data/ met een releasearchief.
  4. Herbruik uw instellingen: kopieer config.json, of verplaats het naar de database met amctl --local config migrate (zie Configuratie). Uw MM_-omgevingsvariabelen blijven werken; hernoem ze naar AM_ wanneer het handig is.
  5. Start Antimatter en volg de logboekmeldingen terwijl de database wordt bijgewerkt. Controleer vervolgens Systeemconsole › Plugins › Plugin Beheer. Antimatter installeert eigen versies van Calls, Playbooks, Kanban (Borden), Agents en integraties wanneer deze nieuwer zijn dan de geïnstalleerde versie. Als Mattermost een nieuwere versie van een van deze apps had, verwijder die app en herstart Antimatter, zodat de eigen build wordt geïnstalleerd.
  6. Stel pushmeldingen opnieuw in met uw eigen push-proxy: Antimatter stuurt nooit meldingen naar de pushdiensten van Mattermost, of het nu test- of gehoste diensten zijn, omdat deze alleen worden bezorgd aan de eigen apps van Mattermost. Zolang u Push Notificatie Server niet wijzigt, stuurt de server geen pushmeldingen (zie Pushmeldingen).

Antimatter maakt geen verbinding met services die door Mattermost, Inc. worden beheerd (zie Verbindingen met externe services), zelfs als uw configuratie er nog steeds naar verwijst:

  • een pushmeldingsserver bij Mattermost blijft in de instellingen staan, maar wordt nooit gebruikt;
  • De adressen van Mattermost voor de appmarktplaats (Marktplaats URL) en voor productmededelingen worden geleegd;
  • de Calls-app gebruikt de publieke STUN-server van Cloudflare in plaats van die van Mattermost, zonder de opgeslagen instelling te wijzigen (zie Calls);
  • de controle op beveiligingsupdates en het crashrapport zijn verwijderd, evenals de bijbehorende instellingen in de Systeemconsole (Beveiligingsmeldingen inschakelen, Diagnostiek en foutrapportage inschakelen) en de pagina Mededelingen.

De socket voor de lokale modus is nu /var/tmp/antimatter_local.socket; amctl probeert ook de oude /var/tmp/mattermost_local.socket. Mattermost ondersteunt alleen nog PostgreSQL in de recente versies, en dat geldt ook voor Antimatter: verplaats eerst een MySQL-database naar PostgreSQL. Als u na het upgraden van de database door Antimatter terugkeert naar Mattermost, moet u uw Mattermost-backup herstellen.

Data exporteren en importeren

Het bulkexportformaat verplaatst data tussen servers: de hele server, bepaalde communities of bepaalde kanalen, inclusief bijlagen, profielfoto's en aangepaste emoji's, indien gewenst.

# on the source server
amctl export create --team-name design --include-profile-pictures
amctl export list
amctl export download <export file> design.zip
# on the destination server
amctl import upload design.zip
amctl import list available
amctl import process <uploaded file> --imported-users active

Volg de taken met amctl export job list en amctl import job list. Voor een export van een community of kanaal is --imported-users verplicht: active als de gebruikers naar deze server verhuizen, inactive bij een import naar een server waar ze al een account hebben, zodat accounts die zijn aangemaakt op basis van onzekere matches uitgeschakeld blijven totdat een beheerder ze controleert. --destination-team-name importeert naar een bestaande community. Exporten en importen worden standaard 30 dagen bewaard in de opslag van de server (ExportSettings.Directory, ImportSettings.Directory).

Op de server zelf doen antimatter export bulk en antimatter import bulk --apply hetzelfde vanuit bestanden, zonder de API.
