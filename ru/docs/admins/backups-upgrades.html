Резервные копии и обновления

Что нужно резервировать, как восстановить данные на новом хосте, как обновить систему и как перенести сервер Mattermost или отдельное сообщество на Antimatter.

Что нужно резервировать

ЧтоС файлом compose сайтаС архивом релиза
База данных: сообщения, пользователи, сообщества, каналы и, при использовании файла compose сайта, конфигурациятом antimatter_postgres, через pg_dumpваша база данных PostgreSQL
Загруженные файлы, изображения и установленные приложениятом antimatter_files (хранилище S3)FileSettings.Directory, по умолчанию ./data/
Файл конфигурации(в базе данных)config/config.json
GIF и стикерытом antimatter_gifsкаталог данных службы GIF
Секретные данные.env (и compose.override.yaml)ваш файл переменных окружения

База данных и файлы неразделимы: резервируйте их одновременно и храните копии вне сервера. Имена томов начинаются с имени проекта compose, antimatter (список можно получить командой docker volume ls).

Резервное копирование

Выполняйте из каталога с compose.yaml. Предварительная остановка Antimatter обеспечивает полностью согласованную копию; резервная копия, сделанная во время работы, обычно тоже подходит, но файлы, загруженные в процессе резервного копирования, могут в ней отсутствовать.

stamp=$(date +%Y%m%d-%H%M%S)
mkdir -p backups
docker compose stop antimatter
# Database
docker compose exec -T postgres pg_dump -U antimatter -d antimatter -Fc \
    > "backups/antimatter-db-$stamp.dump"
# File storage and GIF service
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data:ro" -v "$PWD/backups:/backup" \
        alpine tar -czf "/backup/antimatter-$v-$stamp.tar.gz" -C /data .
done
docker compose start antimatter
# Secrets
cp .env "backups/env-$stamp"

Запускайте из cron для ежедневного резервного копирования и копируйте каталог backups/ на другой компьютер. Храните копии .env так же безопасно, как и сам сервер: в них содержатся пароли.

Чтобы копировать загруженные файлы по одному (например, в другое хранилище S3), используйте командную утилиту AWS службы bucket:

docker compose run --rm -v "$PWD/backups/files:/backup" bucket \
    "aws --endpoint-url http://files:9000 s3 sync s3://antimatter /backup"

При использовании архива релиза резервируйте базу данных с помощью pg_dump -Fc, а каталоги data/ и config/ — с помощью обычных средств.

Восстановление на новом хосте

Поместите compose.yaml, сохранённый .env и резервные копии в новый каталог, затем:

stamp=20261016-030000          # the backup to restore
docker compose create           # creates the volumes, starts nothing
docker compose up -d postgres
docker compose exec -T postgres pg_restore -U antimatter -d antimatter --no-owner \
    < "backups/antimatter-db-$stamp.dump"
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data" -v "$PWD/backups:/backup" \
        alpine tar -xzf "/backup/antimatter-$v-$stamp.tar.gz" -C /data
done
docker compose up -d

Используйте тот же .env: хранилище и база данных должны сохранить прежние пароли. Если у нового хоста другой адрес, обновите SITE_URL (и DOMAIN).

Периодически проверяйте резервные копии, восстанавливая их на другом компьютере.

Обновление

  1. Сделайте резервную копию.
  2. Измените тег образа в .env (ANTIMATTER_IMAGE), если вы фиксируете версию, как рекомендуется.
  3. Загрузите и перезапустите: 
    docker compose pull
docker compose up -d
docker compose logs -f antimatter

При запуске сервер обновляет схему базы данных (процесс можно отслеживать в журнале; на большом сервере это может занять несколько минут) и устанавливает более новые версии встроенных приложений из образа. При использовании архива релиза: остановите сервер, замените всё, кроме config/, data/, logs/, plugins/ и client/plugins/, содержимым нового архива, а затем запустите сервер снова.

Обновления выполняются только вперёд. Как только более новая версия сервера обновит базу данных, старая версия не сможет её использовать: чтобы откатиться, восстановите резервную копию, сделанную перед обновлением. То же самое относится к переходу с antimatter-next обратно на antimatter.

Версии

Сервер Antimatter сообщает версию линии Mattermost, на которой он основан (в настоящее время 12.0.0). Образы пересобираются из веток main: antimatter-next — каждую ночь (теги nightly-<YYYYMMDD>), а оба образа — при каждом изменении (теги sha-<commit>). Закрепите один из этих тегов, обновляйте осознанно и записывайте предыдущий тег, чтобы знать, какая резервная копия ему соответствует.

Основные версии PostgreSQL

Файл compose использует postgres:17-alpine. Antimatter требует PostgreSQL 15 или новее. Новая основная версия PostgreSQL не может читать каталог данных предыдущей версии: чтобы перейти на неё, сделайте дамп базы данных, запустите новую версию на новом томе и восстановите дамп в неё.

Переход с Mattermost

Antimatter использует схему базы данных Mattermost и добавляет собственные таблицы, поэтому он может взять на себя PostgreSQL-базу данных и файлы сервера Mattermost. Сначала попробуйте это на копии:

  1. Сделайте резервную копию базы данных Mattermost, его хранилища файлов (data/ или S3-бакета) и config.json, затем остановите Mattermost.
  2. Восстановите базу данных в PostgreSQL Antimatter или укажите Antimatter на её копию (AM_SQLSETTINGS_DATASOURCE).
  3. Скопируйте файлы в хранилище Antimatter, сохранив их пути: в бакет antimatter с помощью S3-инструмента или в data/ с помощью архива релиза.
  4. Переиспользуйте свои настройки: скопируйте config.json или перенесите его в базу данных с помощью amctl --local config migrate (см. Конфигурация). Ваши переменные окружения MM_ продолжают работать; переименуйте их в AM_, когда будет удобно.
  5. Запустите Antimatter и следите за журналом во время обновления базы данных. Затем откройте Системная консоль › Плагины › Управление плагинами. Antimatter устанавливает собственные сборки Calls, Playbooks, Kanban (Boards), Agents и интеграций, если они новее установленных версий. Если в Mattermost была более новая версия одного из этих приложений, удалите его и перезапустите Antimatter, чтобы установилась его собственная сборка.
  6. Настройте push-уведомления заново, используя собственный push-прокси: Antimatter никогда не отправляет уведомления в push-сервисы Mattermost, будь то тестовые или хостинговые, поскольку они доставляются только в собственные приложения Mattermost. Пока вы не измените Сервер push уведомлений, сервер не отправляет push-уведомления (см. Push-уведомления).

Antimatter не связывается ни с одним сервисом, управляемым Mattermost, Inc. (см. Соединения с внешними сервисами), даже если в вашей конфигурации они все еще указаны:

  • push-сервер Mattermost сохраняется в настройках, но никогда не используется;
  • адреса Mattermost для магазина приложений (URL магазина плагинов) и для продуктовых объявлений очищены;
  • приложение Calls использует публичный STUN-сервер Cloudflare вместо сервера Mattermost, не изменяя сохраненную настройку (см. Calls);
  • проверка обновлений безопасности и отчёт о сбоях удалены, а вместе с ними — параметры Системной консоли (Включить уведомления о безопасности, Включить диагностику и отчёт об ошибках) и страница Объявления.

Сокет локального режима теперь /var/tmp/antimatter_local.socket; amctl также пытается использовать старый /var/tmp/mattermost_local.socket. Mattermost поддерживает только PostgreSQL в последних версиях, и Antimatter делает то же самое: сначала перенесите базу данных MySQL в PostgreSQL. Возврат к Mattermost после обновления базы данных Antimatter означает восстановление резервной копии Mattermost.

Экспорт и импорт данных

Формат пакетного экспорта переносит данные между серверами: весь сервер, некоторые сообщества или некоторые каналы, включая вложения, аватары и пользовательские эмодзи, если вы этого хотите.

# on the source server
amctl export create --team-name design --include-profile-pictures
amctl export list
amctl export download <export file> design.zip
# on the destination server
amctl import upload design.zip
amctl import list available
amctl import process <uploaded file> --imported-users active

Следите за выполнением задач с помощью команд amctl export job list и amctl import job list. Для экспорта сообщества или канала требуется параметр --imported-users: active, если пользователи переезжают на этот сервер, и inactive, если импорт выполняется на сервер, где у них уже есть аккаунты, чтобы аккаунты, созданные из неоднозначных совпадений, оставались неактивными до проверки администратором. Параметр --destination-team-name позволяет импортировать данные в существующее сообщество. Файлы экспорта и импорта хранятся на диске сервера (ExportSettings.Directory, ImportSettings.Directory) в течение 30 дней по умолчанию.

На самом сервере команды antimatter export bulk и antimatter import bulk --apply выполняют те же операции из файлов, минуя API.
