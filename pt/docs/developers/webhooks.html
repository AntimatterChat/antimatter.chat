Webhooks

Um webhook de entrada permite que outro sistema publique num canal, enviando JSON para uma URL secreta. Um webhook de saída faz o oposto: envia as mensagens que começam com uma palavra de gatilho para a sua URL e publica aquilo que responder.

Onde gerir webhooks

Abra o seu avatar no canto superior direito e, em seguida, Integrações. As páginas de integrações da comunidade atual listam Webhooks de entrada e Webhooks de saída. Cada webhook pertence a uma única comunidade.

Por omissão, os administradores da comunidade e os administradores do sistema podem criar webhooks. Um administrador do sistema pode conceder esse direito a outros papéis nas definições de permissões do Consola do sistema. Um administrador do sistema também pode desativar cada tipo em Consola do sistema › Integrações › Gestão de integrações: Ativar webhooks de entrada e Ativar webhooks de saída estão ambos ativados por omissão.

Criar um webhook de entrada

  1. Em Integrações, escolha Webhooks de entrada e, em seguida, Adicionar webhook de entrada.
  2. Preencha um Título e uma Descrição: estes apenas aparecem nas páginas de integrações.
  3. Escolha o Canal para onde as mensagens são enviadas por omissão. Para um canal privado, tem de ser membro dele.
  4. Ative Fixar a este canal se os remetentes não puderem publicar noutros canais.
  5. Defina, opcionalmente, um Nome de utilizador e uma URL de Imagem do perfil para as suas mensagens (ver Nome e ícone).
  6. Escolha Guardar. Copie a URL apresentada: https://chat.example.com/hooks/<key>.
A URL é o único segredo: qualquer pessoa que a tenha pode publicar no canal. Mantenha-a fora de repositórios públicos e elimine o webhook se for exposta.

Com a API: POST /api/v4/hooks/incoming com {"channel_id", "display_name", "description", "username", "icon_url", "channel_locked"}; o id da resposta é a chave. A partir da linha de comandos: amctl webhook create-incoming --channel <channel id> --user <user> --display-name "CI".

Enviar uma mensagem para um webhook de entrada

curl -X POST https://chat.example.com/hooks/xgh5ycrx1jf7mbs9w8z4c8e7ho \
  -H 'Content-Type: application/json' \
  -d '{"text": "Deploy of **api 2.4.0** finished :white_check_mark:"}'

O servidor responde com 200 e o corpo ok. Também aceita application/x-www-form-urlencoded com o JSON num campo payload, tal como os webhooks do Slack, pelo que as ferramentas feitas para o Slack geralmente funcionam sem alterações.

CampoSignificado
textA mensagem, em Markdown. Obrigatório, a menos que existam attachments. Um texto mais longo que o limite de mensagem do servidor é dividido em várias mensagens.
channelOutro canal da comunidade do webhook, pelo nome (ops-alerts ou #ops-alerts), ou @username para uma mensagem direta do proprietário do webhook. Recusado quando o webhook está bloqueado no seu canal.
username, icon_url, icon_emojiO nome e a imagem a mostrar, quando o servidor permite substituições.
attachmentsAnexos da mensagem, apresentados como cartões (abaixo).
propsPropriedades adicionais guardadas na mensagem, para aplicações que as leem.
typeUm tipo de mensagem personalizado, como custom_poll, para uma aplicação que o apresenta. Os tipos que começam com system_ são recusados.
root_idO ID da primeira mensagem de um tópico, para responder nesse tópico.
priorityPrioridade da mensagem, por exemplo {"priority": "urgent"}.
silenttrue envia a mensagem sem notificações push.

As mensagens apresentadas com um nome substituído têm uma etiqueta BOT ao lado, para que as pessoas as possam distinguir de contas reais. As mensagens de webhook nunca ativam webhooks de saída.

Nome e ícone

Um webhook publica como a pessoa que o criou, a menos que o servidor permita substituições. Duas definições em Consola do sistema › Integrações › Gestão de integrações, ambas desativadas por predefinição, alteram isso:

  • Ativar integrações para substituir nomes de utilizador (ServiceSettings.EnablePostUsernameOverride): o Nome de utilizador do webhook ou o username da solicitação são apresentados; na ausência de ambos, o nome é webhook.
  • Permitir que as integrações substituam os ícones das fotos de perfil (ServiceSettings.EnablePostIconOverride): a Imagem do perfil do webhook, ou o icon_url ou icon_emoji da solicitação, são apresentados.

Um valor na solicitação tem prioridade sobre o guardado no webhook.

Anexos

Os anexos adicionam conteúdo estruturado abaixo do texto. Seguem o formato de anexos de mensagem do Slack:

{
  "text": "Build failed on `main`",
  "attachments": [{
    "fallback": "main #1902 failed",
    "color": "#d24b4e",
    "author_name": "GitHub Actions",
    "author_icon": "https://chat.example.com/static/ci.png",
    "title": "main #1902 failed",
    "title_link": "https://ci.example.com/runs/1902",
    "text": "Commit `0f4d8e2` by Jonas Weber",
    "fields": [
      {"title": "Branch", "value": "zephyr-3.7", "short": true},
      {"title": "Duration", "value": "3m 40s", "short": true}
    ],
    "footer": "Lumen CI",
    "ts": 1760000000
  }]
}
CampoSignificado
fallbackTexto simples para locais que não podem mostrar o cartão, como notificações.
colorA barra de cor: uma cor em hexadecimal, ou good, warning, danger.
pretextTexto acima do cartão.
author_name, author_link, author_iconUma linha de cabeçalho pequena.
title, title_linkO título do cartão, opcionalmente um link.
textO corpo do cartão, em Markdown.
fieldsUma lista de {"title", "value", "short"}; os campos short ficam lado a lado.
image_url, thumb_urlUma imagem grande abaixo, ou uma pequena ao lado.
footer, footer_icon, tsUma linha de rodapé e um tempo (segundos Unix).
actionsBotões e menus: ver Mensagens interativas.

Cartões: etapas e gráficos

O Antimatter adiciona dois campos aos anexos, desenhados pela interface predefinida:

  • stages: as etapas de um pipeline, apresentadas como pílulas, até 20. Cada uma é {"name", "status"}, com um estado de passed, failed, running, pending, skipped ou canceled.
  • chart: um pequeno gráfico de linha com os valores mais recentes, {"values": [2 to 200 numbers], "threshold": number, "label": "…"}. O limite é representado por uma linha tracejada, que corresponde ao limite de alerta.
{
  "attachments": [{
    "color": "danger",
    "title": "main #1902 failed",
    "stages": [
      {"name": "build", "status": "failed"},
      {"name": "unit", "status": "skipped"},
      {"name": "publish", "status": "skipped"}
    ]
  }, {
    "color": "warning",
    "title": "API latency above 400 ms",
    "chart": {"values": [210, 230, 260, 390, 450, 470], "threshold": 400, "label": "p95 latency, ms"}
  }]
}

A interface clássica e outros clientes ignoram estes dois campos, por isso coloque também o essencial em text ou fields.

Criar um webhook de saída

Um webhook de saída vigia os canais públicos de uma comunidade. Quando a primeira palavra de uma mensagem corresponde a uma das suas palavras de gatilho, o Antimatter envia a mensagem para o seu URL.

  1. Em Integrações, escolha Webhooks de saída e, em seguida, Adicionar webhook de saída.
  2. Preencha o Título e a Descrição.
  3. Escolha o Tipo de conteúdo da solicitação: application/x-www-form-urlencoded ou application/json.
  4. Escolha um Canal, insira Palavras de gatilho (uma por linha) ou ambos. Com um canal e sem palavras de gatilho, todas as mensagens desse canal são enviadas. Com ambos, a mensagem tem de corresponder a ambos.
  5. Em Gatilhar quando, escolha A primeira palavra corresponde exatamente a uma palavra de ativação ou A primeira palavra começa com uma palavra de ativação.
  6. Insira as URLs de callback (uma por linha). Cada URL recebe todas as mensagens correspondentes.
  7. Defina, opcionalmente, o Nome de utilizador e a Imagem do perfil usados para as respostas.
  8. Escolha Guardar e copie o token apresentado. O seu serviço usa-o para verificar que as solicitações provêm do seu servidor.

Com a API: POST /api/v4/hooks/outgoing com {"team_id", "channel_id", "trigger_words", "trigger_when", "callback_urls", "content_type", "display_name"} (trigger_when: 0 para uma correspondência exata, 1 para "starts with").

Se o seu serviço estiver numa rede privada, um administrador do sistema tem de permitir o seu endereço em Permitir ligações internas não fiáveis a (ServiceSettings.AllowedUntrustedInternalConnections). O servidor não chama endereços privados caso contrário.

O pedido de saída

O Antimatter envia um POST com estes campos, como JSON ou codificado em formulário, consoante o tipo de conteúdo:

{
  "token": "6kd1ofo5ojr5zgu5ipfipybgnc",
  "team_id": "…",
  "team_domain": "lumen-labs",
  "channel_id": "…",
  "channel_name": "ops-alerts",
  "timestamp": 1760010000000,
  "user_id": "…",
  "user_name": "priya",
  "post_id": "…",
  "text": "deploy api 2.4.0",
  "trigger_word": "deploy",
  "file_ids": ""
}

Compare token com o token do webhook antes de fazer qualquer coisa. Na versão codificada em formulário, timestamp está em segundos, não em milissegundos. O servidor aguarda a sua resposta pelo tempo que Tempo limite de pedido de integração permitir (30 segundos por omissão, ServiceSettings.OutgoingIntegrationRequestsTimeout).

Responder a um webhook de saída

Para publicar uma resposta, responda com JSON. Para não publicar nada, responda com um corpo vazio.

{
  "text": "Deploying **api 2.4.0** to staging…",
  "response_type": "comment",
  "username": "deploy-bot",
  "icon_url": "https://chat.example.com/static/deploy.png"
}
  • text e attachments: a resposta. Sem nenhum dos dois, nada é publicado.
  • response_type: comment publica a resposta no tópico da mensagem que a desencadeou; caso contrário, vai para o canal.
  • username, icon_url: mostrados quando o servidor permite substituições; caso contrário, são usados os próprios valores do webhook.
  • props, type, priority: como nos webhooks de entrada.

A resposta é publicada como o criador do webhook, com o nome substituído, quando houver. Para qualquer coisa mais longa do que uma resposta rápida, responda de imediato e publique mais tarde com um webhook de entrada ou com a API.

Quando um webhook não funciona

  • 501 do URL do hook: os webhooks de entrada estão desativados no servidor.
  • 400 "Failed to decode the payload…": o JSON é inválido, ou o campo do formulário não se chama payload. "No text specified." significa que o pedido não tem nem text nem attachments.
  • 403: o webhook está bloqueado para outro canal, ou o seu proprietário já não pode ler o canal.
  • Um webhook de saída nunca é disparado: o canal é privado, o gatilho não é a primeira palavra, ou a mensagem veio de um webhook.
  • Registos: com Ativar depuração de webhooks ligado (LogSettings.EnableWebhookDebugging) e o nível de registo em DEBUG, o servidor regista os payloads dos pedidos de entrada com falha. As chamadas de saída com falha são registadas como Outgoing Webhook POST failed.
