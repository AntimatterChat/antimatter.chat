Cópias de segurança e atualizações

O que fazer em cópia de segurança, como o restaurar num novo host, como atualizar e como migrar um servidor Mattermost ou uma única comunidade para o Antimatter.

O que fazer em cópia de segurança

O quêCom o ficheiro compose do siteCom um arquivo de libertação
A base de dados: mensagens, utilizadores, comunidades, canais e, com o ficheiro compose do site, a configuraçãovolume antimatter_postgres, através de pg_dumpa sua base de dados PostgreSQL
Ficheiros, imagens e aplicações instaladas enviadosvolume antimatter_files (o armazenamento S3)FileSettings.Directory, por omissão ./data/
O ficheiro de configuração(na base de dados)config/config.json
GIFs e figurinhasvolume antimatter_gifso diretório de dados do serviço de GIFs
Segredos.env (e compose.override.yaml)o seu ficheiro de ambiente

A base de dados e os ficheiros pertencem juntos: faça cópias de segurança ao mesmo tempo e mantenha cópias fora do servidor. Os nomes dos volumes começam com o nome do projeto compose, antimatter (docker volume ls lista-os).

Fazer cópia de segurança

A partir do diretório de compose.yaml. Parar o Antimatter primeiro dá uma cópia totalmente consistente; uma cópia de segurança feita enquanto ele está a executar é geralmente suficiente, mas os ficheiros enviados durante a cópia de segurança podem estar ausentes dela.

stamp=$(date +%Y%m%d-%H%M%S)
mkdir -p backups
docker compose stop antimatter
# Database
docker compose exec -T postgres pg_dump -U antimatter -d antimatter -Fc \
    > "backups/antimatter-db-$stamp.dump"
# File storage and GIF service
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data:ro" -v "$PWD/backups:/backup" \
        alpine tar -czf "/backup/antimatter-$v-$stamp.tar.gz" -C /data .
done
docker compose start antimatter
# Secrets
cp .env "backups/env-$stamp"

Execute-a a partir do cron para cópias de segurança diárias e copie o diretório backups/ para outra máquina. Mantenha as cópias de .env tão seguras como o servidor: contêm as suas palavras-passe.

Para copiar os ficheiros enviados objeto a objeto (por exemplo, para outro armazenamento S3), utilize a ferramenta de linha de comandos da AWS do serviço bucket:

docker compose run --rm -v "$PWD/backups/files:/backup" bucket \
    "aws --endpoint-url http://files:9000 s3 sync s3://antimatter /backup"

Com um arquivo de libertação, faça uma cópia de segurança da base de dados com pg_dump -Fc e dos diretórios data/ e config/ com as suas ferramentas habituais.

Restaurar num novo host

Coloque compose.yaml, o .env guardado e as cópias de segurança num novo diretório, depois:

stamp=20261016-030000          # the backup to restore
docker compose create           # creates the volumes, starts nothing
docker compose up -d postgres
docker compose exec -T postgres pg_restore -U antimatter -d antimatter --no-owner \
    < "backups/antimatter-db-$stamp.dump"
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data" -v "$PWD/backups:/backup" \
        alpine tar -xzf "/backup/antimatter-$v-$stamp.tar.gz" -C /data
done
docker compose up -d

Use o mesmo .env: o armazenamento e a base de dados devem manter as palavras-passe que tinham. Se o novo host tiver outro endereço, atualize SITE_URL (e DOMAIN).

Teste as suas cópias de segurança, restaurando-as de vez em quando, noutra máquina.

Atualizar

  1. Faça uma cópia de segurança.
  2. Altere a etiqueta da imagem em .env (ANTIMATTER_IMAGE), se fixar uma, como recomendado.
  3. Obtenha e reinicie: 
    docker compose pull
docker compose up -d
docker compose logs -f antimatter

Ao iniciar, o servidor atualiza o esquema da base de dados (pode acompanhá-lo no registo; num servidor grande, o processo pode demorar vários minutos) e instala as versões mais recentes das aplicações incluídas na imagem. No caso de um arquivo de lançamento: detenha o servidor, substitua tudo, exceto config/, data/, logs/, plugins/ e client/plugins/, pelo conteúdo do novo arquivo e inicie-o novamente.

As atualizações só avançam. Uma vez que um servidor mais recente tenha atualizado a base de dados, uma versão anterior não a pode utilizar: para reverter, restaure a cópia de segurança efetuada antes da atualização. O mesmo se aplica à transição de antimatter-next para antimatter.

Versões

O servidor do Antimatter informa a versão da linha Mattermost em que se baseia (atualmente 12.0.0). As imagens são reconstruídas a partir dos ramos main: antimatter-next todas as noites (etiquetas nightly-<YYYYMMDD>) e ambas as imagens a cada alteração (etiquetas sha-<commit>). Fixe uma destas etiquetas, atualize de forma intencional e anote a etiqueta anterior para saber com que cópia de segurança corresponde.

Versões principais do PostgreSQL

O ficheiro compose utiliza postgres:17-alpine. O Antimatter requer PostgreSQL 15 ou mais recente. Uma nova versão principal do PostgreSQL não consegue ler o diretório de dados da versão anterior: para migrar, exporte a base de dados, inicie a nova versão num volume novo e restaure a exportação nela.

Migração do Mattermost

O Antimatter utiliza o esquema de base de dados do Mattermost e adiciona as suas próprias tabelas, pelo que pode assumir a base de dados PostgreSQL e os ficheiros de um servidor Mattermost. Experimente primeiro numa cópia:

  1. Faça uma cópia de segurança da base de dados do Mattermost, do seu armazenamento de ficheiros (data/ ou balde S3) e do config.json, e depois detenha o Mattermost.
  2. Restaure a base de dados no PostgreSQL do Antimatter, ou aponte o Antimatter para uma cópia dela (AM_SQLSETTINGS_DATASOURCE).
  3. Copie os ficheiros para o armazenamento do Antimatter, mantendo os respetivos caminhos: para o balde antimatter com uma ferramenta S3, ou para data/ com um arquivo de lançamento.
  4. Reutilize as suas definições: copie o config.json ou mova-o para a base de dados com amctl --local config migrate (veja Definições). As suas variáveis de ambiente MM_ continuam a funcionar; renomeie-as para AM_ quando for conveniente.
  5. Inicie o Antimatter e acompanhe o registo enquanto atualiza a base de dados. Em seguida, verifique Consola do sistema › Plugins › Gestão de plugins. O Antimatter instala as suas próprias compilações de Chamadas, Playbooks, Kanban (Quadros), Agentes e integrações quando estas são mais recentes do que a versão instalada. Se o Mattermost tiver uma versão mais recente de uma delas, remova essa aplicação e reinicie o Antimatter, para que a sua própria compilação seja instalada.
  6. Configure novamente as notificações push, com o seu próprio proxy de notificações: o Antimatter nunca envia notificações para os serviços de push do Mattermost, de teste ou alojados, que apenas entregam às aplicações próprias do Mattermost. Até alterar o Servidor de notificações push, o servidor não envia notificações push (ver Notificações push).

O Antimatter não contacta nenhum serviço executado pela Mattermost, Inc. (ver Ligações a serviços externos), mesmo quando a sua configuração ainda nomeia um:

  • um servidor de notificações push no Mattermost é mantido nas definições, mas nunca é utilizado;
  • Os endereços do Mattermost para o marketplace de aplicações (URL do Marketplace) e para os avisos de produto ficam vazios;
  • a aplicação Chamadas utiliza o servidor STUN público da Cloudflare em vez do do Mattermost, sem alterar a definição guardada (ver Chamadas);
  • a verificação de atualizações de segurança e a notificação de falhas são removidas, bem como as respetivas definições da Consola do sistema (Ativar alertas de segurança, Ativar diagnóstico e notificação de erros) e a página Avisos.

O socket do modo local é agora /var/tmp/antimatter_local.socket; o amctl também tenta o antigo /var/tmp/mattermost_local.socket. O Mattermost apenas suporta PostgreSQL nas suas versões mais recentes, e o Antimatter também: transfira primeiro uma base de dados MySQL para PostgreSQL. Voltar ao Mattermost depois de o Antimatter ter atualizado a base de dados implica restaurar a sua cópia de segurança do Mattermost.

Exportar e importar dados

O formato de exportação em massa transfere dados entre servidores: o servidor inteiro, algumas comunidades ou alguns canais, com anexos, fotografias de perfil e emojis personalizados, se os pretender.

# on the source server
amctl export create --team-name design --include-profile-pictures
amctl export list
amctl export download <export file> design.zip
# on the destination server
amctl import upload design.zip
amctl import list available
amctl import process <uploaded file> --imported-users active

Acompanhe as tarefas com amctl export job list e amctl import job list. Para uma exportação de comunidade ou canal, --imported-users é obrigatório: active quando as pessoas se transferem para este servidor, inactive quando se importa para um servidor onde já têm contas, de modo a que as contas criadas a partir de correspondências incertas fiquem desativadas até um administrador as verificar. --destination-team-name importa para uma comunidade existente. As exportações e importações são mantidas no armazenamento do servidor (ExportSettings.Directory, ImportSettings.Directory) durante 30 dias por omissão.

No próprio servidor, antimatter export bulk e antimatter import bulk --apply fazem o mesmo a partir de ficheiros, sem a API.
