מסד הנתונים והקבצים שייכים זה לזה: גיבו אותם בו-זמנית, ושמרו עותקים מחוץ לשרת. שמות הנפחים מתחילים בשם פרויקט compose, antimatter (docker volume ls מציג אותם).

גיבוי

מספריית compose.yaml. עצירת Antimatter קודם נותנת עותק עקבי לחלוטין; גיבוי שנלקח בזמן שהשרת רץ בדרך כלל תקין, אך קבצים שהועלו במהלך הגיבוי עשויים להיעדר ממנו.

stamp=$(date +%Y%m%d-%H%M%S)
mkdir -p backups
docker compose stop antimatter
# Database
docker compose exec -T postgres pg_dump -U antimatter -d antimatter -Fc \
    > "backups/antimatter-db-$stamp.dump"
# File storage and GIF service
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data:ro" -v "$PWD/backups:/backup" \
        alpine tar -czf "/backup/antimatter-$v-$stamp.tar.gz" -C /data .
done
docker compose start antimatter
# Secrets
cp .env "backups/env-$stamp"

הריצו אותו מ-cron לגיבויים יומיים, והעתיקו את ספריית backups/ למכונה אחרת. שמרו את העותקים של .env באותה מידה של אבטחה כמו השרת: הם מכילים את סיסמאותיו.

כדי להעתיק את הקבצים שהועלו אובייקט-אחר-אובייקט (למשל לאחסון S3 אחר), השתמשו בכלי שורת הפקודה של AWS של שירות bucket:

docker compose run --rm -v "$PWD/backups/files:/backup" bucket \
    "aws --endpoint-url http://files:9000 s3 sync s3://antimatter /backup"

עם ארכיון גרסה, גיבו את מסד הנתונים עם pg_dump -Fc, ואת ספריות data/ ו-config/ עם הכלים הרגילים שלכם.

שחזור על מארח חדש

שמו את compose.yaml, את .env ששמרתם ואת הגיבויים בספרייה חדשה, ואז:

stamp=20261016-030000          # the backup to restore
docker compose create           # creates the volumes, starts nothing
docker compose up -d postgres
docker compose exec -T postgres pg_restore -U antimatter -d antimatter --no-owner \
    < "backups/antimatter-db-$stamp.dump"
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data" -v "$PWD/backups:/backup" \
        alpine tar -xzf "/backup/antimatter-$v-$stamp.tar.gz" -C /data
done
docker compose up -d

השתמשו באותו .env: האחסון ומסד הנתונים חייבים לשמור על הסיסמאות שהיו להם. אם למארח החדש יש כתובת אחרת, עדכנו את SITE_URL (וגם DOMAIN).

בדקו את הגיבויים שלכם על ידי שחזורם על מכונה אחרת מעת לעת.

שדרוג

  1. עשו גיבוי.
  2. שנו את תג התמונה ב-.env (ANTIMATTER_IMAGE), אם אתם נועלים גרסה, כפי שמומלץ.
  3. שכו ואתחלו מחדש: 
    docker compose pull
docker compose up -d
docker compose logs -f antimatter

בהפעלה, השרת מעלה את תבנית המסד הנתונים (עקבו אחרי התהליך ביומן; שרת גדול יכול לקחת כמה דקות) ומתקין את הגרסאות החדשות יותר של האפליקציות המצורפות מהדמות. בארכיון שחרור: עצרו את השרת, החליפו את כל התוכן מלבד config/, data/, logs/, plugins/ ו-client/plugins/ בתוכן הארכיון החדש, והפעילו שוב.

שדרוגים מתבצעים רק קדימה. לאחר ששרת חדש יותר העלה את המסד הנתונים, גרסה ישנה יותר לא יכולה להשתמש בו: כדי לחזור אחורה, שחזרו את הגיבוי שנלקח לפני השדרוג. הדבר נכון גם לגבי מעבר מ-antimatter-next חזרה ל-antimatter.

גרסאות

שרת Antimatter מדווח על גרסת שורת Mattermost שהוא מבוסס עליה (כיום 12.0.0). הדמות נבנית מחדש מהענפים main: antimatter-next כל לילה (תגיות nightly-<YYYYMMDD>), ושתי הדמות בכל שינוי (תגיות sha-<commit>). נעצו אחת מתגיות אלו, בצעו שדרוג בכוונה, ושמרו תיעוד של התגיה הקודמת כדי לדעת איזה גיבוי תואם לה.

גרסאות ראשיות של PostgreSQL

קובץ compose משתמש ב-postgres:17-alpine. Antimatter דורש PostgreSQL 15 או חדש יותר. גרסה ראשית חדשה של PostgreSQL לא יכולה לקרוא את תיקיית הנתונים של הגרסה הקודמת: כדי לעבור אליה, בצעו dump של המסד הנתונים, הפעילו את הגרסה החדשה על נפח חדש ושחזרו את ה-dump אליו.

מעבר מ-Mattermost

Antimatter משתמש בתבנית מסד הנתונים של Mattermost ומוסיף לו שדות משלו, ולכן הוא יכול לקחת על עצמו את מסד הנתונים PostgreSQL והקבצים של שרת Mattermost. נסו זאת תחילה על העתק:

  1. בצעו גיבוי של מסד הנתונים של Mattermost, של אחסון הקבצים שלו (data/ או סל S3) ושל config.json, ואז עצרו את Mattermost.
  2. שחזרו את מסד הנתונים אל PostgreSQL של Antimatter, או ציינו ל-Antimatter העתק שלו (AM_SQLSETTINGS_DATASOURCE).
  3. העתיקו את הקבצים לאחסון של Antimatter, תוך שמירת הנתיבים שלהם: לסל antimatter באמצעות כלי S3, או ל-data/ באמצעות ארכיון שחרור.
  4. שבו ונצלו את ההגדרות שלכם: העתיקו את config.json, או העבירו אותו אל המסד הנתונים באמצעות amctl --local config migrate (ראו הגדרות). משתני הסביבה MM_ שלכם ממשיכים לפעול; שנו את שמם ל-AM_ כשיהיה לכם נוח.
  5. הפעילו את Antimatter ועקבו אחר הלוג בזמן שהמערכת שודרגת. לאחר מכן, בדקו בקונסולת מערכת › תוספים › ניהול פלאגינים. Antimatter מתקינה את הבנייה שלה של Calls, Playbooks, Kanban (Boards), Agents והאינטגרציות, כאשר גרסת הבנייה שלה חדשה יותר מהגרסה המותקנת. אם Mattermost מכיל גרסה חדשה יותר של אחד מהתוספים, הסירו אותו והפעילו מחדש את Antimatter כדי שהבנייה שלה תותקן.
  6. הגדירו שוב את התראות Push באמצעות שרת ייצוג (proxy) משלכם: Antimatter nie שולחת התראות לשירותי Push של Mattermost, בין אם הם שירותי בדיקה ובין אם הם שירותים מנוהלים, שכן הם משלחים התראות רק לאפליקציות של Mattermost עצמה. עד שתשנו את שרת התראות Push, השרת לא ישלח התראות Push (ראו התראות Push).

Antimatter אינה מתקשרת עם שום שירות שמופעל על ידי Mattermost, Inc. (ראו חיבורים לשירותים חיצוניים), גם אם ההגדרות שלכם עדיין מציינות שירות כזה:

  • שרת התראות דחיפה של Mattermost נשמר בהגדרות, אך אינו נעשה שימוש בו;
  • כתובות Mattermost לשוק התוספים (כתובת (URL) של שוק התוספים) ולעדכוני מוצר נמחקות;
  • אפליקציית השיחות (Calls) משתמשת בשרת STUN הציבורי של Cloudflare במקום בשרת של Mattermost, ללא שינוי בהגדרה השמורה (ראו שיחות);
  • בדיקת עדכוני אבטחה ודיווח על תקלות מוסרים, יחד עם הגדרות קונסולת המערכת המתאימות (הפעלת התראות אבטחה, הפעלת אבחון ודיווח על שגיאות) ועמוד הודעות מערכת.

גרב (Socket) של מצב מקומי הוא כעת /var/tmp/antimatter_local.socket; amctl מנסה גם את /var/tmp/mattermost_local.socket הישן. Mattermost תומך רק ב-PostgreSQL בגרסאות האחרונות, וכך גם Antimatter: יש להעביר תחילה בסיס נתונים MySQL ל-PostgreSQL. חזרה ל-Mattermost לאחר ש-Antimatter שגררה את בסיס הנתונים דורשת שחזור גיבוי של Mattermost.

ייצוא וייבוא נתונים

פורמט הייצוא המוני מאפשר העברת נתונים בין שרתים: השרת כולו, קהילות מסוימות או ערוצים מסוימים, כולל קבצים מצורפים, תמונות פרופיל ואמוג'י מותאמים אישית, אם רוצים.

# on the source server
amctl export create --team-name design --include-profile-pictures
amctl export list
amctl export download <export file> design.zip
# on the destination server
amctl import upload design.zip
amctl import list available
amctl import process <uploaded file> --imported-users active

עקבו אחר המשימות באמצעות amctl export job list ו-amctl import job list. עבור ייצוא של קהילה או ערוץ, --imported-users הוא חובה: active כאשר האנשים עוברים לשרת זה, ו-inactive כאשר מייבאים לשרת שבו להם כבר יש חשבונות, כך שהחשבונות שנוצרו מתאימות לא ודאיות יישארו כלא פעילים עד שמנהל יבדוק אותם. --destination-team-name מייבא לקהילה קיימת. ייצואים וייבואים נשמרים באחסון של השרת (ExportSettings.Directory, ImportSettings.Directory) למשך 30 ימים כברירת מחדל.

על השרת עצמו, antimatter export bulk ו-antimatter import bulk --apply מבצעים את אותן פעולות מקבצים, ללא שימוש ב-API.
