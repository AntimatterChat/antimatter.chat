Il database e i file vanno insieme: fai il backup di entrambi nello stesso momento e conserva copie fuori dal server. I nomi dei volumi iniziano con il nome del progetto compose, antimatter (docker volume ls li elenca).

Backup

Dalla directory di compose.yaml. Arrestare Antimatter prima garantisce una copia completamente coerente; un backup eseguito durante il funzionamento è generalmente accettabile, ma i file caricati durante il backup potrebbero non esservi inclusi.

stamp=$(date +%Y%m%d-%H%M%S)
mkdir -p backups
docker compose stop antimatter
# Database
docker compose exec -T postgres pg_dump -U antimatter -d antimatter -Fc \
    > "backups/antimatter-db-$stamp.dump"
# File storage and GIF service
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data:ro" -v "$PWD/backups:/backup" \
        alpine tar -czf "/backup/antimatter-$v-$stamp.tar.gz" -C /data .
done
docker compose start antimatter
# Secrets
cp .env "backups/env-$stamp"

Eseguilo tramite cron per backup giornalieri e copia la directory backups/ su un'altra macchina. Conserva le copie di .env con la stessa sicurezza del server: contengono le sue password.

Per copiare i file caricati oggetto per oggetto (ad esempio su un altro archivio S3), usa il tool da riga di comando AWS del servizio bucket:

docker compose run --rm -v "$PWD/backups/files:/backup" bucket \
    "aws --endpoint-url http://files:9000 s3 sync s3://antimatter /backup"

Con un archivio di rilascio, fai il backup del database con pg_dump -Fc e delle directory data/ e config/ con i tuoi strumenti abituali.

Ripristino su un nuovo host

Metti compose.yaml, il .env salvato e i backup in una nuova directory, poi:

stamp=20261016-030000          # the backup to restore
docker compose create           # creates the volumes, starts nothing
docker compose up -d postgres
docker compose exec -T postgres pg_restore -U antimatter -d antimatter --no-owner \
    < "backups/antimatter-db-$stamp.dump"
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data" -v "$PWD/backups:/backup" \
        alpine tar -xzf "/backup/antimatter-$v-$stamp.tar.gz" -C /data
done
docker compose up -d

Usa lo stesso .env: l'archivio e il database devono mantenere le password che avevano. Se il nuovo host ha un indirizzo diverso, aggiorna SITE_URL (e DOMAIN).

Testa i tuoi backup ripristinandoli periodicamente su un'altra macchina.

Aggiornamento

  1. Fai un backup.
  2. Cambia il tag dell'immagine in .env (ANTIMATTER_IMAGE), se ne fissi uno, come raccomandato.
  3. Scarica e riavvia: 
    docker compose pull
docker compose up -d
docker compose logs -f antimatter

All'avvio, il server aggiorna lo schema del database (è possibile seguirne il progresso nel log; per un server di grandi dimensioni l'operazione può richiedere diversi minuti) e installa le versioni più recenti delle app incluse nell'immagine. In caso di archivio di rilascio: arresta il server, sostituisci tutto tranne config/, data/, logs/, plugins/ e client/plugins/ con il contenuto del nuovo archivio, quindi avvialo di nuovo.

Gli aggiornamenti avvengono solo in avanti. Una volta che un server più recente ha aggiornato il database, una versione precedente non può più utilizzarlo: per tornare indietro, è necessario ripristinare il backup effettuato prima dell'aggiornamento. Lo stesso vale per il passaggio da antimatter-next a antimatter.

Versioni

Il server di Antimatter riporta la versione della linea Mattermost su cui si basa (attualmente 12.0.0). Le immagini vengono ricostruite dai rami main: antimatter-next ogni notte (tag nightly-<YYYYMMDD>) e entrambe le immagini a ogni modifica (tag sha-<commit>). Fissa uno di questi tag, esegui gli aggiornamenti in modo intenzionale e annota il tag precedente per sapere a quale backup corrisponde.

Versioni principali di PostgreSQL

Il file compose utilizza postgres:17-alpine. Antimatter richiede PostgreSQL 15 o versioni successive. Una nuova versione principale di PostgreSQL non può leggere la directory dati della versione precedente: per passare a una nuova versione, è necessario eseguire un dump del database, avviare la nuova versione su un volume nuovo e ripristinare il dump in essa.

Passaggio da Mattermost

Antimatter utilizza lo schema del database di Mattermost e aggiunge le proprie tabelle, quindi può assumere il controllo del database PostgreSQL e dei file di un server Mattermost. Provare prima su una copia:

  1. Eseguire il backup del database Mattermost, del suo archivio file (data/ o bucket S3) e di config.json, quindi arrestare Mattermost.
  2. Ripristinare il database nel PostgreSQL di Antimatter, oppure puntare Antimatter a una copia di esso (AM_SQLSETTINGS_DATASOURCE).
  3. Copiare i file nell'archivio di Antimatter, mantenendone i percorsi: nel bucket antimatter con uno strumento S3, oppure in data/ con un archivio di rilascio.
  4. Riutilizzare le proprie impostazioni: copiare config.json oppure spostarlo nel database con amctl --local config migrate (vedere Configurazione). Le variabili di ambiente MM_ continuano a funzionare; rinominarle in AM_ quando è opportuno.
  5. Avvia Antimatter e monitora il log durante l'aggiornamento del database. Successivamente, verifica Console di Sistema › Plugins › Gestione plugin. Antimatter installa le proprie versioni di Chiamate, Playbook, Kanban (Bacheche), Agenti e integrazioni quando sono più recenti della versione installata. Se Mattermost aveva una versione più recente di uno di questi elementi, rimuovi quell'app e riavvia Antimatter, in modo che venga installata la sua versione.
  6. Configura nuovamente le notifiche push, utilizzando il tuo proxy push: Antimatter non invia mai notifiche ai servizi push di Mattermost, sia di test che gestiti, che consegnano solo alle app di Mattermost. Finché non modifichi Server notifiche push, il server non invia notifiche push (vedi Notifiche push).

Antimatter non contatta alcun servizio gestito da Mattermost, Inc. (vedi Connessioni a servizi esterni), anche se la tua configurazione ne indica ancora uno:

  • un server di notifiche push presso Mattermost è mantenuto nelle impostazioni ma non viene mai utilizzato;
  • gli indirizzi di Mattermost per il marketplace delle app (URL marketplace) e per gli avvisi di prodotto vengono svuotati;
  • l'app Chiamate utilizza il server STUN pubblico di Cloudflare invece di quello di Mattermost, senza modificare l'impostazione salvata (vedi Chiamate);
  • la verifica degli aggiornamenti di sicurezza e la segnalazione dei crash sono stati rimossi, insieme alle relative impostazioni della Console di Sistema (Abilita avvisi di sicurezza, Abilita diagnostica e segnalazione errori) e alla pagina Avvisi.

Il socket della modalità locale è ora /var/tmp/antimatter_local.socket; amctl tenta anche il vecchio /var/tmp/mattermost_local.socket. Mattermost supporta solo PostgreSQL nelle sue versioni recenti, e così fa Antimatter: sposta prima un database MySQL su PostgreSQL. Tornare a Mattermost dopo che Antimatter ha aggiornato il database significa ripristinare il backup di Mattermost.

Esporta e importa dati

Il formato di esportazione in blocco sposta i dati tra i server: l'intero server, alcune community o alcuni canali, con allegati, foto del profilo ed emoji personalizzate, se lo desideri.

# on the source server
amctl export create --team-name design --include-profile-pictures
amctl export list
amctl export download <export file> design.zip
# on the destination server
amctl import upload design.zip
amctl import list available
amctl import process <uploaded file> --imported-users active

Monitora i lavori con amctl export job list e amctl import job list. Per un'export di un'area di lavoro o di un canale, è obbligatorio specificare --imported-users: active se le persone si trasferiscono a questo server, inactive se si importa in un server in cui hanno già un account, in modo che gli account creati da corrispondenze incerte restino disattivati finché un amministratore non li verifica. --destination-team-name importa in un'area di lavoro esistente. Le esportazioni e le importazioni vengono conservate nello storage del server (ExportSettings.Directory, ImportSettings.Directory) per 30 giorni di default.

Sul server stesso, antimatter export bulk e antimatter import bulk --apply eseguono le stesse operazioni da file, senza l'API.
