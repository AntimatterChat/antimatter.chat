بدون مفتاح تشفير الذكاء الاصطناعي، لا يستطيع الخادم المُستعاد قراءة مفاتيح واجهة برمجة التطبيقات (API) الخاصة باتصالات نماذجه، ويجب إعادة إدخال كل مفتاح يدويًا. احتفظ بنسخة من المفتاح منفصلة عن نسخ احتياطية لقاعدة البيانات، حتى لا تحتوي نسخة واحدة مسروقة على كلاهما. راجع مفتاح التشفير.

قاعدة البيانات والملفات متلازمان: انسخهما احتياطياً في نفس الوقت، واحتفظ بنسخ منهما خارج الخادم. تبدأ أسماء الأحجام باسم مشروع compose، antimatter (تُعرض القائمة عبر docker volume ls).

النسخ الاحتياطي

من مجلد compose.yaml. إيقاف Antimatter أولاً يمنحك نسخة متسقة تماماً؛ والنسخة المأخوذة أثناء التشغيل غالباً ما تكون جيدة، لكن الملفات المرفوعة أثناء النسخ الاحتياطي قد لا تكون موجودة فيها.

stamp=$(date +%Y%m%d-%H%M%S)
mkdir -p backups
docker compose stop antimatter
# Database
docker compose exec -T postgres pg_dump -U antimatter -d antimatter -Fc \
    > "backups/antimatter-db-$stamp.dump"
# File storage and GIF service
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data:ro" -v "$PWD/backups:/backup" \
        alpine tar -czf "/backup/antimatter-$v-$stamp.tar.gz" -C /data .
done
docker compose start antimatter
# Secrets
cp .env "backups/env-$stamp"

إذا لم تضبط AM_AI_ENCRYPTION_KEY وأنشأ الخادم ملف مفتاحه، انسخ الملف أيضًا (مرة واحدة تكفي: فهو لا يتغير): docker compose cp antimatter:/antimatter/data/ai-encryption.key "backups/ai-encryption.key". والأفضل، وضع محتواه في .env كما يشرح مفتاح التشفير: إذًا ستحتوي النسخة الاحتياطية من .env عليه.

شغّله من cron للنسخ الاحتياطي اليومي، وانسخ مجلد backups/ إلى جهاز آخر. احتفظ بنسخ .env بأمان مساوٍ للخادم: فهي تحتوي على كلمات المرور الخاصة به.

لنسخ الملفات المرفوعة كائنًا تلو الآخر (على سبيل المثال إلى تخزين S3 آخر)، استخدم أداة سطر الأوامر AWS الخاصة بخدمة bucket:

docker compose run --rm -v "$PWD/backups/files:/backup" bucket \
    "aws --endpoint-url http://files:9000 s3 sync s3://antimatter /backup"

باستخدام أرشيف الإصدار، انسخ قاعدة البيانات احتياطيًا باستخدام pg_dump -Fc، والمجلدات data/ وconfig/ باستخدام أدواتك المعتادة (يحتوي data/ على ملف مفتاح الذكاء الاصطناعي). وباستخدام الحزم، انسخ قاعدة البيانات احتياطيًا بالطريقة نفسها، و/etc/antimatter، و/var/lib/antimatter، و/etc/gifs-server، و/var/lib/gifs-server.

الاستعادة على مضيف جديد

ضع compose.yaml، و .env المحفوظ، والنسخ الاحتياطية في مجلد جديد، ثم:

stamp=20261016-030000          # the backup to restore
docker compose create           # creates the volumes, starts nothing
docker compose up -d postgres
docker compose exec -T postgres pg_restore -U antimatter -d antimatter --no-owner \
    < "backups/antimatter-db-$stamp.dump"
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data" -v "$PWD/backups:/backup" \
        alpine tar -xzf "/backup/antimatter-$v-$stamp.tar.gz" -C /data
done
docker compose up -d

استخدم نفس .env: يجب أن تحتفظ التخزين وقاعدة البيانات بكلمات المرور التي كانت لديها، وتحتاج اتصالات النماذج إلى نفس مفتاح تشفير الذكاء الاصطناعي. إذا كان المضيف الجديد له عنوان آخر، حدّث SITE_URL (وDOMAIN).

اختبر نسخك الاحتياطية من خلال استعادتها على جهاز آخر من حين لآخر.

الترقية

  1. أنشئ نسخة احتياطية.
  2. غيّر وسم الصورة في .env (ANTIMATTER_IMAGE)، إذا كنت تثبته، كما يُوصى به.
  3. اسحب الصورة وأعد التشغيل: 
    docker compose pull
docker compose up -d
docker compose logs -f antimatter

عند البدء، يحدّث الخادم مخطط قاعدة البيانات (تابع ذلك في السجل؛ فقد يستغرق خادم كبير عدة دقائق) ويثبّت الإصدارات الأحدث من التطبيقات المدمجة من الصورة. باستخدام أرشيف الإصدار: أوقف الخادم، واستبدل كل شيء ما عدا config/، وdata/، وlogs/، وplugins/، وclient/plugins/ بمحتوى الأرشيف الجديد، ثم ابدأه مرة أخرى. باستخدام حزمة ‎.deb أو ‎.rpm، ثبّت الحزمة الجديدة كما يشرح ترقية الحزمة.

التحديثات تتم للأمام فقط. بمجرد أن يحدّث خادم أحدث قاعدة البيانات، لا يمكن للإصدار الأقدم استخدامها: للرجوع، استعِد النسخة الاحتياطية المأخوذة قبل التحديث. وينطبق الأمر نفسه على الانتقال من antimatter-next إلى antimatter.

الإصدارات

يُبلّغ خادم Antimatter عن إصدار خط Mattermost الذي يستند إليه (حاليًا 12.0.0). للإصدارات على GitHub، مع أرشيفاتها وحقائبها، أرقام إصدار خاصة بها، ضمن سلسلة 0.9.0 أثناء فترة الاختبار: يُظهر الأمر antimatter version الرقم كـرقم الإصدار. تُعاد بناء الصور من فروع main: صورة antimatter-next كل ليلة (وسوم nightly-<YYYYMMDD>)، وكلا الصورتين عند كل تغيير (وسوم sha-<commit>). ثبّت أحد هذه الوسوم، وارتقِ عمدًا، ودوّن الوسم السابق حتى تعرف أي نسخة احتياطية تتوافق معه.

الإصدارات الرئيسية لـ PostgreSQL

يستخدم ملف compose postgres:17-alpine. يحتاج Antimatter إلى PostgreSQL 15 أو أحدث. لا يمكن لإصدار رئيسي جديد من PostgreSQL قراءة مجلد بيانات الإصدار السابق: للانتقال إلى إصدار جديد، قم بتصدير قاعدة البيانات، ابدأ الإصدار الجديد على مجلد جديد، واستعِد التصدير فيه.

الترقية إلى 0.9.0

أول تشغيل للإصدار 0.9.0 (أو لصورة مبنية من 17 أكتوبر 2026 فصاعدًا) يُجري بعض التغييرات لمرة واحدة على البيانات. يُنفَّذ كل تغيير مرة واحدة، ويُسجَّل في قاعدة البيانات. تُنقل القيم التي بقيت على الإعداد الافتراضي القديم إلى الجديد، وتُترك القيم التي اختارها المدير كما هي. راقب هذه التغييرات في السجل.

إذا كان Antimatter مخصصًا لشركة أو مؤسسة، اضبط نوع المجتمعات الجديدة على مكان العمل قبل الترقية: AM_TEAMSETTINGS_DEFAULTCOMMUNITYKIND=workplace. تمنح الترقية كل مجتمع النوع الذي تحمله هذه الإعدادات في تلك اللحظة، وتكون المكالمات معطلة افتراضيًا في قنوات مجتمعات نوع المجتمع. راجع مكان العمل أو المجتمع.
العنصرالتغيير
أنواع المجتمعيحصل كل مجتمع على نوع، إما المجتمع أو مكان العمل: وهو قيمة نوع المجتمعات الجديدة (TeamSettings.DefaultCommunityKind) عند أول تشغيل. يُحفظ النوع المُعيَّن مسبقًا. يمكن لمديري المجتمع تغيير نوع مجتمعهم لاحقًا، من إعدادات الفريق › قنوات › نوع المجتمع.
من يُرشف القنواتلم يعد أعضاء القنوات يُرشفون القنوات التي ينتمون إليها: بل يفعلها مديرو المجتمع. في مكان العمل، يُرشف أيضًا مديرو القناة (منشئها، وأولئك الذين جعلهم مديريًا) القناة. يغيّر هذا أدوار مخطط النظام؛ وتُترك مخططات الأذونات التي أنشأها مدير النظام لبعض المجتمعات كما هي.
دور المشرفين في قوالب التخطيطيحصل دور المشرفين الذي حصلت عليه المجتمعات من قالب التخطيط على صلاحية إزالة أشخاص، وهي صلاحية يحتاجها توقيف الأشخاص وإزالتهم. تتغير فقط الأدوار التي لا تزال مطابقة تمامًا لما أنشأه القالب؛ وتُترك الأدوار التي عدّلها شخص ما كما هي.
الأدوار التي تحمل صلاحية مديرالدور المجتمعي الذي يكون فيه مفتاح مدير مفعّلًا يكتسب الآن كل الصلاحيات التي يملكها مدراء المجتمع، كما يشير المفتاح، وليس فقط إعدادات المجتمع.
الحد الأقصى لعدد الأعضاءيتغير الحد الأقصى لعدد الأعضاء في كل مجتمع (TeamSettings.MaxUsersPerTeam) من 50، وهو الحد الافتراضي السابق، إلى 0 (بدون حد). تُحفظ أي قيمة أخرى، وكذلك أي حد مُعيَّن عبر AM_TEAMSETTINGS_MAXUSERSPERTEAM.
اتصالات النماذجيحصل مدراء النظام على إدارة اتصالات النماذج، بينما يدير مدراء المجتمع (والأدوار التي تحمل صلاحية مدير) اتصالات نماذج مجتمعهم الخاصة. تصبح خدمات الذكاء الاصطناعي في تطبيق الوكلاء اتصالات نماذج على مستوى الخادم، راجع أدناه.
تصبح Town Square قناة Generalيتم إعادة تسمية القناة الافتراضية لكل مجتمع من town-square (Town Square) إلى general (General). تحتفظ القناة بمعرّفها وأعضائها ورسائلها وإعداداتها، وكذلك بالاسم المعروض الذي اختاره المدراء. لا تزال الروابط القديمة والبحث باستخدام town-square تؤدي إلى القناة. المجتمع الذي يملك بالفعل قناة باسم general، حتى لو كانت مؤرشفة، يحتفظ بقناة town-square كقناة افتراضية، وكذلك المجتمع التي تكون قناته town-square مؤرشفة: تُذكر هذه الحالات في السجل، ويمكن لمداريها إعادة تسمية القنوات.
المفضلةيتم إعادة تسمية تصنيف الشريط الجانبي «المفضلة» الخاص بجميع المستخدمين إلى «المفضلة» (Favourites)، بما يتوافق مع ما تظهره الواجهة الآن. تُترك التصنيفات التي أنشأها المستخدمون بنفس الاسم دون تغيير.

خدمات تطبيق الوكلاء

ينسخ الترقية كل خدمة ذكاء اصطناعي في تطبيق الوكلاء إلى اتصال نموذج على مستوى الخادم، يُشارك مع جميع المجتمعات ويمكن استخدامه من قبل الجميع باستثناء الضيوف (فعّل الضيوف أيضًا للسماح لهم بذلك). يتم تشفير المفاتيح أثناء النقل، لذا يحتاج الخادم إلى مفتاح تشفير الذكاء الاصطناعي الخاص به: في التجمّع الذي تُخزَّن ملفاتاته في S3، اضبط AM_AI_ENCRYPTION_KEY أولاً، وإلا فسيتم تأجيل النسخ حتى الإقلاع التالي. ثم تحقق من وحدة التحكم بالنظام › الذكاء الاصطناعي › اتصالات النماذج:

  • تحتفظ كل اتصال بمعرّف خدمتها، لذا لا يزال وكلاء التطبيق وإعداد الترجمة التلقائية المرتبط بخدمة الوكلاء يجدونها.
  • تصبح خدمات OpenAI، وOpenAI المتوافقة، وAnthropic، وMistral، وCohere، وGemini اتصالات بنهاية نقطة (endpoint) متوافقة مع OpenAI (أو Anthropic). تصبح خدمة Azure اتصالًا بنهاية نقطة متوافقة مع OpenAI للمورد: اختبرها.
  • يتم وضع علامة يتطلب الانتباه على خدمات AWS Bedrock وGoogle Vertex AI وCohere North والأنواع غير المعروفة، مع ذكر السبب. لا يتم نسخ بيانات الاعتماد السحابية الخاصة بها: وجّهها إلى نقطة النهاية المتوافقة مع OpenAI لدى المزوّد أو إلى بوابة مثل LiteLLM، ثم احفظ التغييرات.
  • تصبح خدمة التضمين (Embedding) نموذج التضمينات في الاتصال الذي يحمل العنوان والمفتاح نفسيهما، أو في اتصال خاص بها. تحصل خدمة النسخ النصي على نموذج whisper-1.
  • عندما لا يكون هناك اتصال بعد لإعادة الصياغة والملخصات، تحصل على الخدمة والنموذج الخاص بالوكيل الافتراضي للتطبيق.

تُترك الإعدادات والبيانات الخاصة بتطبيق الوكلاء كما هي: تستمر وكلاءه في استخدام خدماته.

تغييرات أخرى في الإعدادات الافتراضية

  • المكالمات: يكون وضع الاختبار معطلاً وتفعيل الفيديو مفعّلاً افتراضياً. يتم الاحتفاظ بأي خيار محفوظ في الإعدادات. تتبع المكالمات أيضاً نوع المجتمع (انظر المكالمات والصوت).
  • وضع الرسائل في المقدمة متاح لإداريي القناة، وإداريي المجتمع ومُشرفيه (مع صلاحية إدارة الرسائل)؛ لا يزال بإمكان أعضاء الرسائل المباشرة أو الجماعية القيام بذلك.
  • يمكن للقنوات المؤرشفة قبول أعضاء جدد، الذين يقرؤون سجلها. لا يستطيع أحد النشر أو إضافة ردود فعل أو تغيير أي شيء فيها.

الانتقال من Mattermost

يستخدم Antimatter مخطط قاعدة بيانات Mattermost ويضيف جداوله الخاصة، لذا يمكنه الاستيلاء على قاعدة بيانات PostgreSQL وملفات خادم Mattermost. جرّب ذلك على نسخة أولاً:

  1. أنشئ نسخة احتياطية من قاعدة بيانات Mattermost، وتخزين الملفات الخاص بها (data/ أو حاوية S3) وconfig.json، ثم أوقف Mattermost.
  2. استعِد قاعدة البيانات في PostgreSQL الخاص بـ Antimatter، أو وجّه Antimatter إلى نسخة منها (AM_SQLSETTINGS_DATASOURCE).
  3. انسخ الملفات إلى تخزين Antimatter، مع الحفاظ على مساراتها: إلى حاوية antimatter باستخدام أداة S3، أو إلى data/ باستخدام أرشيف إصدار.
  4. أعد استخدام إعداداتك: انسخ config.json، أو انقله إلى قاعدة البيانات باستخدام amctl --local config migrate (انظر الإعدادات). تبقى متغيرات البيئة MM_ الخاصة بك تعمل؛ أعد تسميتها إلى AM_ عند الحاجة.
  5. شغّل Antimatter وتابع السجل أثناء ترقية قاعدة البيانات. ثم افحص وحدة التحكم بالنظام › الإضافات › إدارة الإضافات. يقوم Antimatter بتثبيت نسخاته الخاصة من مكالمات، أدلة التشغيل، لوحات كانبان، الوكلاء، والتكاملات عندما تكون أحدث من الإصدار المثبّت. إذا كان لدى Mattermost إصدار أحدث لأيٍّ منها، احذف تلك التطبيق وأعد تشغيل Antimatter ليتم تثبيت نسخته الخاصة.
  6. قم بإعداد الإشعارات الفورية مرة أخرى باستخدام وكيل الإشعارات الخاص بك: لا يرسل Antimatter أي إشعارات إلى خدمات Mattermost الفورية، سواء كانت تجريبية أو مستضافة، لأنها تصل فقط إلى تطبيقات Mattermost الخاصة. حتى تقوم بتغيير خادم الإشعارات الفورية، لن يرسل الخادم أي إشعارات فورية (راجع الإشعارات الفورية).

لا يتواصل Antimatter مع أي خدمة تشغّلها Mattermost, Inc. (راجع الاتصالات مع الخدمات الخارجية)، حتى إذا كان تكوينك لا يزال يذكر خدمةً منها:

  • يُحفظ خادم الإشعارات الفورية الخاص بـ Mattermost في الإعدادات لكنه لا يُستخدم أبداً؛
  • تُفرَّغ عناوين Mattermost الخاصة بسوق التطبيقات (عنوان URL للمتجر) والإشعارات المتعلقة بالمنتج؛
  • تُستبدل روابط تنزيل التطبيقات التي كانت افتراضية في Mattermost (رابط صفحة تنزيل تطبيقات Antimatter، رابط تنزيل تطبيق Android ورابط تنزيل تطبيق iOS) بصفحات تنزيل تطبيقات Antimatter على GitHub؛ يتم الاحتفاظ بالروابط التي قمت بإعدادها بنفسك؛
  • يستخدم تطبيق المكالمات خادم STUN العام من Cloudflare بدلاً من خادم Mattermost، دون تغيير الإعداد المحفوظ (راجع المكالمات)؛
  • تمت إزالة فحص التحديثات الأمنية والإبلاغ عن الأعطال، وكذلك إعدادات وحدة التحكم بالنظام الخاصة بها (تفعيل التنبيهات الأمنية، تفعيل التشخيص والإبلاغ عن الأخطاء) وصفحة الإشعارات.

أصبح المقبس الخاص بالوضع المحلي /var/tmp/antimatter_local.socket؛ ويحاول amctl أيضاً استخدام المقبس القديم /var/tmp/mattermost_local.socket. يدعم Mattermost قاعدة بيانات PostgreSQL فقط في إصداراته الحديثة، وكذلك يفعل Antimatter: انقل قاعدة بيانات MySQL إلى PostgreSQL أولاً. العودة إلى Mattermost بعد ترقية Antimatter لقاعدة البيانات تعني استعادة نسخة احتياطية من Mattermost.

تصدير واستيراد البيانات

تنسيق التصدير الشامل ينقل البيانات بين الخوادم: الخادم بأكمله، أو بعض المجتمعات، أو بعض القنوات، مع المرفقات وصور الملفات الشخصية والرموز التعبيرية المخصصة إذا رغبت في ذلك.

# on the source server
amctl export create --team-name design --include-profile-pictures
amctl export list
amctl export download <export file> design.zip
# on the destination server
amctl import upload design.zip
amctl import list available
amctl import process <uploaded file> --imported-users active

راقب المهام باستخدام amctl export job list وamctl import job list. عند تصدير مجتمع أو قناة، يكون --imported-users مطلوبًا: active إذا انتقل الأشخاص إلى هذا الخادم، وinactive عند الاستيراد إلى خادم لديهم فيه حسابات بالفعل، حتى تبقى الحسابات المُنشأة من تطابقات غير مؤكدة موقوفة حتى يفحصها مدير. يستورد --destination-team-name إلى مجتمع موجود. تُحفظ عمليات التصدير والاستيراد على تخزين الخادم (ExportSettings.Directory، ImportSettings.Directory) لمدة 30 يومًا افتراضيًا.

على الخادم نفسه، تنجز antimatter export bulk وantimatter import bulk --apply نفس الشيء من الملفات، دون استخدام واجهة برمجة التطبيقات.
