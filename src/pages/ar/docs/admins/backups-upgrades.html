قاعدة البيانات والملفات متلازمان: انسخهما احتياطياً في نفس الوقت، واحتفظ بنسخ منهما خارج الخادم. تبدأ أسماء الأحجام باسم مشروع compose، antimatter (تُعرض القائمة عبر docker volume ls).

النسخ الاحتياطي

من مجلد compose.yaml. إيقاف Antimatter أولاً يمنحك نسخة متسقة تماماً؛ والنسخة المأخوذة أثناء التشغيل غالباً ما تكون جيدة، لكن الملفات المرفوعة أثناء النسخ الاحتياطي قد لا تكون موجودة فيها.

stamp=$(date +%Y%m%d-%H%M%S)
mkdir -p backups
docker compose stop antimatter
# Database
docker compose exec -T postgres pg_dump -U antimatter -d antimatter -Fc \
    > "backups/antimatter-db-$stamp.dump"
# File storage and GIF service
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data:ro" -v "$PWD/backups:/backup" \
        alpine tar -czf "/backup/antimatter-$v-$stamp.tar.gz" -C /data .
done
docker compose start antimatter
# Secrets
cp .env "backups/env-$stamp"

شغّله من cron للنسخ الاحتياطي اليومي، وانسخ مجلد backups/ إلى جهاز آخر. احتفظ بنسخ .env بأمان مساوٍ للخادم: فهي تحتوي على كلمات المرور الخاصة به.

لنسخ الملفات المرفوعة كائنًا تلو الآخر (على سبيل المثال إلى تخزين S3 آخر)، استخدم أداة سطر الأوامر AWS الخاصة بخدمة bucket:

docker compose run --rm -v "$PWD/backups/files:/backup" bucket \
    "aws --endpoint-url http://files:9000 s3 sync s3://antimatter /backup"

مع أرشيف الإصدار، انسخ قاعدة البيانات احتياطياً باستخدام pg_dump -Fc، ومجلدي data/ و config/ باستخدام أدواتك المعتادة.

الاستعادة على مضيف جديد

ضع compose.yaml، و .env المحفوظ، والنسخ الاحتياطية في مجلد جديد، ثم:

stamp=20261016-030000          # the backup to restore
docker compose create           # creates the volumes, starts nothing
docker compose up -d postgres
docker compose exec -T postgres pg_restore -U antimatter -d antimatter --no-owner \
    < "backups/antimatter-db-$stamp.dump"
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data" -v "$PWD/backups:/backup" \
        alpine tar -xzf "/backup/antimatter-$v-$stamp.tar.gz" -C /data
done
docker compose up -d

استخدم نفس .env: يجب أن يحتفظ التخزين وقاعدة البيانات بكلمات المرور التي كانت لديهم. إذا كان للمضيف الجديد عنوان آخر، حدّث SITE_URL (و DOMAIN).

اختبر نسخك الاحتياطية من خلال استعادتها على جهاز آخر من حين لآخر.

الترقية

  1. أنشئ نسخة احتياطية.
  2. غيّر وسم الصورة في .env (ANTIMATTER_IMAGE)، إذا كنت تثبته، كما يُوصى به.
  3. اسحب الصورة وأعد التشغيل: 
    docker compose pull
docker compose up -d
docker compose logs -f antimatter

عند بدء التشغيل، يحدّث الخادم مخطط قاعدة البيانات (يمكنك متابعة ذلك في السجل؛ وقد يستغرق الأمر عدة دقائق على خادم كبير) ويثبّت الإصدارات الأحدث من التطبيقات المضمّنة من الصورة. عند استخدام أرشيف إصدار: أوقف الخادم، واستبدل كل شيء باستثناء config/، data/، logs/، plugins/ وclient/plugins/ بمحتوى الأرشيف الجديد، ثم ابدأه مرة أخرى.

التحديثات تتم للأمام فقط. بمجرد أن يحدّث خادم أحدث قاعدة البيانات، لا يمكن للإصدار الأقدم استخدامها: للرجوع، استعِد النسخة الاحتياطية المأخوذة قبل التحديث. وينطبق الأمر نفسه على الانتقال من antimatter-next إلى antimatter.

الإصدارات

يقوم خادم Antimatter بالإبلاغ عن إصدار خط Mattermost الذي يستند إليه (حاليًا 12.0.0). تُعاد بناء الصور من فروع main: antimatter-next كل ليلة (وسوم nightly-<YYYYMMDD>)، وكلا من الصور عند كل تغيير (وسوم sha-<commit>). ثبّت أحد هذه الوسوم، وحدث عمدًا، واحتفظ بتدوين الوسم السابق حتى تعرف أي نسخة احتياطية تتوافق معه.

الإصدارات الرئيسية لـ PostgreSQL

يستخدم ملف compose postgres:17-alpine. يحتاج Antimatter إلى PostgreSQL 15 أو أحدث. لا يمكن لإصدار رئيسي جديد من PostgreSQL قراءة مجلد بيانات الإصدار السابق: للانتقال إلى إصدار جديد، قم بتصدير قاعدة البيانات، ابدأ الإصدار الجديد على مجلد جديد، واستعِد التصدير فيه.

الانتقال من Mattermost

يستخدم Antimatter مخطط قاعدة بيانات Mattermost ويضيف جداوله الخاصة، لذا يمكنه الاستيلاء على قاعدة بيانات PostgreSQL وملفات خادم Mattermost. جرّب ذلك على نسخة أولاً:

  1. أنشئ نسخة احتياطية من قاعدة بيانات Mattermost، وتخزين الملفات الخاص بها (data/ أو حاوية S3) وconfig.json، ثم أوقف Mattermost.
  2. استعِد قاعدة البيانات في PostgreSQL الخاص بـ Antimatter، أو وجّه Antimatter إلى نسخة منها (AM_SQLSETTINGS_DATASOURCE).
  3. انسخ الملفات إلى تخزين Antimatter، مع الحفاظ على مساراتها: إلى حاوية antimatter باستخدام أداة S3، أو إلى data/ باستخدام أرشيف إصدار.
  4. أعد استخدام إعداداتك: انسخ config.json، أو انقله إلى قاعدة البيانات باستخدام amctl --local config migrate (انظر الإعدادات). تبقى متغيرات البيئة MM_ الخاصة بك تعمل؛ أعد تسميتها إلى AM_ عند الحاجة.
  5. شغّل Antimatter وتابع السجل أثناء ترقية قاعدة البيانات. ثم افحص وحدة التحكم بالنظام › الإضافات › إدارة الإضافات. يقوم Antimatter بتثبيت نسخاته الخاصة من مكالمات، أدلة التشغيل، لوحات كانبان، الوكلاء، والتكاملات عندما تكون أحدث من الإصدار المثبّت. إذا كان لدى Mattermost إصدار أحدث لأيٍّ منها، احذف تلك التطبيق وأعد تشغيل Antimatter ليتم تثبيت نسخته الخاصة.
  6. قم بإعداد الإشعارات الفورية مرة أخرى باستخدام وكيل الإشعارات الخاص بك: لا يرسل Antimatter أي إشعارات إلى خدمات Mattermost الفورية، سواء كانت تجريبية أو مستضافة، لأنها تصل فقط إلى تطبيقات Mattermost الخاصة. حتى تقوم بتغيير خادم الإشعارات الفورية، لن يرسل الخادم أي إشعارات فورية (راجع الإشعارات الفورية).

لا يتواصل Antimatter مع أي خدمة تشغّلها Mattermost, Inc. (راجع الاتصالات مع الخدمات الخارجية)، حتى إذا كان تكوينك لا يزال يذكر خدمةً منها:

  • يُحفظ خادم الإشعارات الفورية الخاص بـ Mattermost في الإعدادات لكنه لا يُستخدم أبداً؛
  • يتم إفراغ عناوين Mattermost الخاصة بمتجر التطبيقات (عنوان URL للمتجر) والإشعارات المتعلقة بالمنتج؛
  • يستخدم تطبيق المكالمات خادم STUN العام من Cloudflare بدلاً من خادم Mattermost، دون تغيير الإعداد المحفوظ (راجع المكالمات)؛
  • تمت إزالة فحص التحديثات الأمنية والإبلاغ عن الأعطال، وكذلك إعدادات وحدة التحكم بالنظام الخاصة بها (تفعيل التنبيهات الأمنية، تفعيل التشخيص والإبلاغ عن الأخطاء) وصفحة الإشعارات.

أصبح المقبس الخاص بالوضع المحلي /var/tmp/antimatter_local.socket؛ ويحاول amctl أيضاً استخدام المقبس القديم /var/tmp/mattermost_local.socket. يدعم Mattermost قاعدة بيانات PostgreSQL فقط في إصداراته الحديثة، وكذلك يفعل Antimatter: انقل قاعدة بيانات MySQL إلى PostgreSQL أولاً. العودة إلى Mattermost بعد ترقية Antimatter لقاعدة البيانات تعني استعادة نسخة احتياطية من Mattermost.

تصدير واستيراد البيانات

تنسيق التصدير الشامل ينقل البيانات بين الخوادم: الخادم بأكمله، أو بعض المجتمعات، أو بعض القنوات، مع المرفقات وصور الملفات الشخصية والرموز التعبيرية المخصصة إذا رغبت في ذلك.

# on the source server
amctl export create --team-name design --include-profile-pictures
amctl export list
amctl export download <export file> design.zip
# on the destination server
amctl import upload design.zip
amctl import list available
amctl import process <uploaded file> --imported-users active

راقب المهام باستخدام amctl export job list وamctl import job list. عند تصدير مجتمع أو قناة، يكون --imported-users مطلوبًا: active إذا انتقل الأشخاص إلى هذا الخادم، وinactive عند الاستيراد إلى خادم لديهم فيه حسابات بالفعل، حتى تبقى الحسابات المُنشأة من تطابقات غير مؤكدة موقوفة حتى يفحصها مدير. يستورد --destination-team-name إلى مجتمع موجود. تُحفظ عمليات التصدير والاستيراد على تخزين الخادم (ExportSettings.Directory، ImportSettings.Directory) لمدة 30 يومًا افتراضيًا.

على الخادم نفسه، تنجز antimatter export bulk وantimatter import bulk --apply نفس الشيء من الملفات، دون استخدام واجهة برمجة التطبيقات.
