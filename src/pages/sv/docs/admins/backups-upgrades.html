Databasen och filerna hör ihop: säkerhetskopiera dem samtidigt och förvaria kopiorna utanför servern. Volymnamnen börjar med compose-projektets namn, antimatter (docker volume ls listar dem).

Säkerhetskopiera

Från mappen där compose.yaml finns. Om du stänger av Antimatter först får du en helt konsistent kopia; en säkerhetskopia som tas medan det körs är oftast i ordning, men filer som laddas upp under säkerhetskopieringen kan saknas i den.

stamp=$(date +%Y%m%d-%H%M%S)
mkdir -p backups
docker compose stop antimatter
# Database
docker compose exec -T postgres pg_dump -U antimatter -d antimatter -Fc \
    > "backups/antimatter-db-$stamp.dump"
# File storage and GIF service
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data:ro" -v "$PWD/backups:/backup" \
        alpine tar -czf "/backup/antimatter-$v-$stamp.tar.gz" -C /data .
done
docker compose start antimatter
# Secrets
cp .env "backups/env-$stamp"

Kör den från cron för dagliga säkerhetskopior och kopiera backups/-mappen till en annan maskin. Förvaria kopiorna av .env lika säkert som servern: de innehåller dess lösenord.

Om du istället vill kopiera de uppladdade filerna objekt för objekt (till exempel till en annan S3-lagring), använd AWS-kommandotoljaten för tjänsten bucket:

docker compose run --rm -v "$PWD/backups/files:/backup" bucket \
    "aws --endpoint-url http://files:9000 s3 sync s3://antimatter /backup"

Med ett release-arkiv, säkerhetskopiera databasen med pg_dump -Fc, och data/- och config/-mapparna med dina vanliga verktyg.

Återställ på en ny värd

Lägg compose.yaml, den sparade .env-filen och säkerhets kopiorna i en ny mapp, och sedan:

stamp=20261016-030000          # the backup to restore
docker compose create           # creates the volumes, starts nothing
docker compose up -d postgres
docker compose exec -T postgres pg_restore -U antimatter -d antimatter --no-owner \
    < "backups/antimatter-db-$stamp.dump"
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data" -v "$PWD/backups:/backup" \
        alpine tar -xzf "/backup/antimatter-$v-$stamp.tar.gz" -C /data
done
docker compose up -d

Använd samma .env: lagringen och databasen måste behålla de lösenord de hade. Om den nya värden har en annan adress, uppdatera SITE_URL (och DOMAIN).

Testa dina säkerhetskopior genom att återställa dem på en annan maskin från tid till annan.

Uppgradera

  1. Ta en säkerhetskopia.
  2. Ändra bildtaggen i .env (ANTIMATTER_IMAGE), om du fäster en, som rekommenderas.
  3. Hämta och starta om: 
    docker compose pull
docker compose up -d
docker compose logs -f antimatter

Vid start uppgraderar servern databasschemat (följ det i loggen; en stor server kan ta flera minuter) och installerar de nyare versionerna av de medföljande apparna från bilden. Med ett releasearkiv: stoppa servern, ersätt allt utom config/, data/, logs/, plugins/ och client/plugins/ med det nya arkivets innehåll, och starta den igen.

Uppgraderingar går bara framåt. När en nyare server har uppgraderat databasen kan en äldre version inte använda den: för att gå tillbaka, återställ den backup som togs före uppgraderingen. Detsamma gäller för att gå från antimatter-next tillbaka till antimatter.

Versioner

Antimatters server rapporterar versionen av Mattermost-linjen den är baserad på (för närvarande 12.0.0). Bilderna byggs om från main-grenarna: antimatter-next varje natt (tags nightly-<YYYYMMDD>), och båda bilderna vid varje ändring (tags sha-<commit>). Fäst en av dessa tags, uppgradera medvetet, och håll den föregående taggen noterad så att du vet vilken backup som hör till den.

PostgreSQL:s huvudversioner

Compose-filen använder postgres:17-alpine. Antimatter kräver PostgreSQL 15 eller nyare. En ny huvudversion av PostgreSQL kan inte läsa den föregående versionens datamapp: för att flytta till en, dumpa databasen, starta den nya versionen på en ny volym och återställ dumpen i den.

Flytta från Mattermost

Antimatter använder Mattermosts databasschema och lägger till egna tabeller, så det kan ta över en Mattermost-servers PostgreSQL-databas och filer. Testa det först på en kopia:

  1. Säkerhetskopiera Mattermost-databasen, dess filförvaring (data/ eller S3-bucket) och config.json, och stoppa sedan Mattermost.
  2. Återställ databasen i Antimatters PostgreSQL, eller peka Antimatter mot en kopia av den (AM_SQLSETTINGS_DATASOURCE).
  3. Kopiera filerna till Antimatters förvaring, med deras sökvägar bevarade: till antimatter-bucketen med ett S3-verktyg, eller till data/ med ett releasearkiv.
  4. Återanvänd dina inställningar: kopiera config.json, eller flytta den till databasen med amctl --local config migrate (se Konfiguration). Dina MM_-miljövariabler fortsätter att fungera; byt namn på dem till AM_ när det passar.
  5. Starta Antimatter och följ loggen medan den uppgraderar databasen. Kontrollera sedan Systemkonsol › Plugin › Pluginadministration. Antimatter installerar egna versioner av Samtal, Playbooks, Kanban (Tavlor), Agents och integreringar när de är nyare än den installerade versionen. Om Mattermost hade en nyare version av någon av dem, ta bort den appen och starta om Antimatter så att dess egen version installeras.
  6. Konfigurera push-aviseringar igen med din egen push-proxy: Antimatter skickar aldrig aviseringar till Mattermosts push-tjänster, oavsett om de är test- eller hostade, eftersom de endast levereras till Mattermosts egna appar. Så länge du inte ändrar Push Notification Server, skickar servern inga push-aviseringar (se Push-aviseringar).

Antimatter kontaktar inga tjänster som drivs av Mattermost, Inc. (se Anslutningar till externa tjänster), även om din konfiguration fortfarande anger sådana:

  • en push-aviseringsserver hos Mattermost finns kvar i inställningarna men används aldrig;
  • Mattermosts adresser för appmarknaden (Marketplace URL) och för produktmeddelanden rensas;
  • apparna Samtal använder Cloudflares publika STUN-server i stället för Mattermosts, utan att ändra den sparade inställningen (se Samtal);
  • säkerhetsuppdateringskontrollen och kraschrapporteringen är borta, liksom deras inställningar i Systemkonsolen (Enable Security Alerts, Enable Diagnostics and Error Reporting) och sidan Meddelanden.

Socketen för lokalt läge är nu /var/tmp/antimatter_local.socket; amctl försöker också med den gamla /var/tmp/mattermost_local.socket. Mattermost stöder endast PostgreSQL i sina senaste versioner, och Antimatter gör detsamma: flytta en MySQL-databas till PostgreSQL först. Att gå tillbaka till Mattermost efter att Antimatter har uppgraderat databasen innebär att du måste återställa din Mattermost-säkerhetskopia.

Exportera och importera data

Formatet för massexport flyttar data mellan servrar: hela servern, vissa team eller vissa kanaler, med bilagor, profilbilder och anpassade emojier om du önskar.

# on the source server
amctl export create --team-name design --include-profile-pictures
amctl export list
amctl export download <export file> design.zip
# on the destination server
amctl import upload design.zip
amctl import list available
amctl import process <uploaded file> --imported-users active

Följ jobben med amctl export job list och amctl import job list. För export av en community eller kanal krävs --imported-users: active när personerna flyttar till den här servern, inactive när du importerar till en server där de redan har konton, så att konton som skapats från osäkra matchningar förblir inaktiva tills en administratör har granskat dem. --destination-team-name importerar till en befintlig community. Exporter och importer sparas på serverns lagringsplats (ExportSettings.Directory, ImportSettings.Directory) i 30 dagar som standard.

På själva servern gör antimatter export bulk och antimatter import bulk --apply samma sak från filer, utan API:et.
