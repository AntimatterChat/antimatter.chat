Tietokanta ja tiedostot kuuluvat yhteen: varmuuskopioi ne samanaikaisesti ja säilytä kopiot palvelimen ulkopuolella. Volyymien nimet alkavat compose-projektin nimellä antimatter (docker volume ls listaa ne).

Varmuuskopioi

compose.yaml:n kansio. Antimatterin pysäyttäminen ensin antaa täysin yhdenmukaisen kopion; varmuuskopio, joka otetaan, kun palvelin on käynnissä, on yleensä kunnossa, mutta varmuuskopiointiaikana lähetetyt tiedostot voivat puuttua siitä.

stamp=$(date +%Y%m%d-%H%M%S)
mkdir -p backups
docker compose stop antimatter
# Database
docker compose exec -T postgres pg_dump -U antimatter -d antimatter -Fc \
    > "backups/antimatter-db-$stamp.dump"
# File storage and GIF service
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data:ro" -v "$PWD/backups:/backup" \
        alpine tar -czf "/backup/antimatter-$v-$stamp.tar.gz" -C /data .
done
docker compose start antimatter
# Secrets
cp .env "backups/env-$stamp"

Suorita se cronnin kautta päivittäisiksi varmuuskopioiksi ja kopioi backups/-kansio toiselle koneelle. Säilytä .env:n kopiot yhtä turvallisesti kuin palvelin: siinä ovat sen salasanat.

Jos haluat kopioida lähetetyt tiedostot esine kerrallaan (esimerkiksi toiseen S3-varastoon), käytä bucket-palvelun AWS-komennonrivityökalua:

docker compose run --rm -v "$PWD/backups/files:/backup" bucket \
    "aws --endpoint-url http://files:9000 s3 sync s3://antimatter /backup"

Julkaisupaketilla varmuuskopioi tietokanta pg_dump -Fc:lla sekä data/- ja config/-kansiot tavallisilla työkaluillasi.

Palauta uuteen isäntäpalvelimeen

Aseta compose.yaml, tallennettu .env ja varmuuskopiot uuteen kansioon, sitten:

stamp=20261016-030000          # the backup to restore
docker compose create           # creates the volumes, starts nothing
docker compose up -d postgres
docker compose exec -T postgres pg_restore -U antimatter -d antimatter --no-owner \
    < "backups/antimatter-db-$stamp.dump"
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data" -v "$PWD/backups:/backup" \
        alpine tar -xzf "/backup/antimatter-$v-$stamp.tar.gz" -C /data
done
docker compose up -d

Käytä samaa .env:tä: varaston ja tietokannan on säilytettävä ne salasanat, joita niillä oli. Jos uuden isäntäpalvelimen osoite on toinen, päivitä SITE_URL (ja DOMAIN).

Testaa varmuuskopioitasi palauttamalla ne toiselle koneelle ajoittain.

Päivitys

  1. Ota varmuuskopio.
  2. Muuta kuvan tagi .env:ssä (ANTIMATTER_IMAGE), jos kiinnität sen, kuten suositellaan.
  3. Hae ja käynnistä uudelleen: 
    docker compose pull
docker compose up -d
docker compose logs -f antimatter

Käynnistyessä palvelin päivittää tietokannan skeeman (seuraa etenemistä lokissa; suuressa palvelimessa se voi kestää useita minuutteja) ja asenta kuvan mukana toimitettujen sovellusten uudemmat versiot. Jos käytät julkaisupakettia: pysäytä palvelin, korvaa kaikki paitsi config/, data/, logs/, plugins/ ja client/plugins/ uuden paketin sisällöllä ja käynnistä palvelin uudelleen.

Päivitykset tehdään vain eteenpäin. Kun uudempi palvelin on päivittänyt tietokannan, vanhempi versio ei voi käyttää sitä: palataksesi taaksepäin palauta varuuskopiota, joka otettiin ennen päivitystä. Sama pätee, jos siirryt antimatter-next:stä takaisin antimatter:iin.

Versiot

Antimatterin palvelin ilmoittaa, minkä Mattermost-pohjaisen versiotason se perustuu (tällä hetkellä 12.0.0). Kuvat rakennetaan uudelleen main-haaroista: antimatter-next joka yö (tagit nightly-<YYYYMMDD>) ja molemmat kuvat jokaisesta muutoksesta (tagit sha-<commit>). Kiinnitä jokin näistä tageista, tee päivitys tarkoituksella ja merkitse ylös edellinen tagi, jotta tiedät, minkä varuuskopion se vastaa.

PostgreSQL:n pääversiot

Compose-tiedostossa käytetään postgres:17-alpine:a. Antimatter vaatii PostgreSQL 15:tä tai uudemman. Uusi PostgreSQL-pääversio ei voi lukea edellisen versiotason tietokansioa: siirtyäksesi uuteen versioon, luo varuuskopio tietokannasta, käynnistä uusi versio uuteen tilavuuteen ja palauta varuuskopio siihen.

Siirtyminen Mattermostista

Antimatter käyttää Mattermostin tietokantaskeemaa ja lisää siihen omia taulujaan, joten se voi ottaa haltuunsa Mattermost-palvelimen PostgreSQL-tietokannan ja tiedostot. Kokeile ensin kopiolla:

  1. Luo varuuskopio Mattermostin tietokannasta, sen tiedostovarastosta (data/ tai S3-astio) ja config.json-tiedostosta, ja pysäytä sitten Mattermost.
  2. Palauta tietokanta Antimatterin PostgreSQL-tietokantaan, tai osoita Antimatterin kohdalle sen kopio (AM_SQLSETTINGS_DATASOURCE).
  3. Kopioi tiedostot Antimatterin varastoon, säilyttäen niiden polut: S3-työkalulla antimatter-astiaan, tai julkaisupaketilla data/-kansioon.
  4. Tee uudelleen käyttämiäsi asetuksia: kopioi config.json-tiedosto, tai siirrä se tietokantaan komennolla amctl --local config migrate (katso Asetukset). MM_-ympäristömuuttujasi toimivat yhä; nimeä ne AM_-muuttujiksi, kun se on kätevää.
  5. Käynnistä Antimatter ja seuraa lokitiedostoa, kun se päivittää tietokannan. Tarkista sen jälkeen Järjestelmäkonsoli › Liiteohjelmat › Liiteohjelmien hallinta. Antimatter asettaa omat rakennelmansa Puheluille, Ohjekirjoille, Kanban-tauluille, Agenteille ja integraatioille, jos ne ovat uudemmat kuin asennetut versiot. Jos Mattermostilla oli jostain näistä uudempi versio, poista se sovellus ja käynnistä Antimatter uudelleen, jotta sen oma rakennelma asennetaan.
  6. Aseta push-ilmoitukset uudelleen omalla push-välityspalvelimellasi: Antimatter ei koskaan lähetä ilmoituksia Mattermostin push-palveluihin, olipa kyseessä testipalvelin tai hosting-palvelin, sillä ne toimittavat ilmoitukset vain Mattermostin omiin sovelluksiin. Kunnes muutat Push-ilmoituspalvelin-asetusta, palvelin ei lähetä push-ilmoituksia (ks. Push-ilmoitukset).

Antimatter ei ota yhteyttä Mattermost, Inc.:n ylläpitämiin palveluihin (ks. Yhteydet ulkoisiin palveluihin), vaikka asetuksissasi olisi yhä mainittu jokin tällainen palvelu:

  • Mattermostin push-ilmoituspalvelin säilyy asetuksissa, mutta sitä ei koskaan käytetä;
  • Mattermostin osoitteet sovelluskauppaan (Kaupan URL) ja tuotetilaisuuksiin tyhjennetään;
  • Puhelut-sovellus käyttää Cloudflaren julkista STUN-palvelinta Mattermostin sijaan, mutta tallennettua asetusta ei muuteta (ks. Puhelut);
  • tietoturvapäivitysten tarkistus ja kaatumisilmoitukset poistetaan, ja samoin niiden Järjestelmäkonsolin asetukset (Ota tietoturvailmoitukset käyttöön, Ota diagnostiikan ja virheilmoitusten käyttöön) sekä Ilmoitukset-sivu.

Paikallisen tilan pistorasia on nyt /var/tmp/antimatter_local.socket; amctl yrittää myös vanhan /var/tmp/mattermost_local.socket-pistorasian. Mattermost tukee vain PostgreSQL-tietokantaa uusimmissa versioissaan, ja sama pätee Antimatteriin: siirrä MySQL-tietokanta ensin PostgreSQLiin. Paluu Mattermostiin Antimatterin päivittämän tietokannan jälkeen vaatii Mattermost-varuksen palauttamisen.

Vie ja tuo dataa

Massavienti-muoto siirtää dataa palvelimien välillä: koko palvelimen, jonkin yhteisön tai jonkin kanavan, liitteineen, profiilikuvineen ja mukautetuine emojineen, jos haluat.

# on the source server
amctl export create --team-name design --include-profile-pictures
amctl export list
amctl export download <export file> design.zip
# on the destination server
amctl import upload design.zip
amctl import list available
amctl import process <uploaded file> --imported-users active

Seuraa työtä komennoilla amctl export job list ja amctl import job list. Kanavan tai yhteisön viennissä --imported-users-valitsin on pakollinen: active, jos käyttäjät siirtyvät tälle palvelimelle, ja inactive, kun tuodaan palvelimelle, jossa heillä on jo tilin. Näin tilit, jotka on luotu epävarmoista osumista, pysyvät poissa käytöstä, kunnes ylläpitäjä tarkistaa ne. --destination-team-name-valitsin tuo viennin olemassa olevaan yhteisöön. Viennit ja tuonnit säilytetään palvelimen tallennustilassa (ExportSettings.Directory, ImportSettings.Directory) oletusarvoisesti 30 päivää.

Suorita palvelimella komennot antimatter export bulk ja antimatter import bulk --apply suorittamaan sama tiedostoista ilman API:ta.
