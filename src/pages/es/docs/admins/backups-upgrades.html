La base de datos y los archivos pertenecen juntos: haga copias de seguridad al mismo tiempo y mantenga copias fuera del servidor. Los nombres de los volúmenes comienzan con el nombre del proyecto compose, antimatter (docker volume ls los lista).

Hacer copia de seguridad

Desde el directorio de compose.yaml. Detener Antimatter primero proporciona una copia totalmente coherente; una copia de seguridad tomada mientras se ejecuta suele estar bien, pero los archivos subidos durante la copia de seguridad pueden no estar presentes en ella.

stamp=$(date +%Y%m%d-%H%M%S)
mkdir -p backups
docker compose stop antimatter
# Database
docker compose exec -T postgres pg_dump -U antimatter -d antimatter -Fc \
    > "backups/antimatter-db-$stamp.dump"
# File storage and GIF service
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data:ro" -v "$PWD/backups:/backup" \
        alpine tar -czf "/backup/antimatter-$v-$stamp.tar.gz" -C /data .
done
docker compose start antimatter
# Secrets
cp .env "backups/env-$stamp"

Ejecute desde cron para copias de seguridad diarias y copie el directorio backups/ a otra máquina. Mantenga las copias de .env tan seguras como el servidor: contienen sus contraseñas.

Para copiar los archivos subidos objeto por objeto (por ejemplo, a otro almacenamiento S3), use la herramienta de línea de comandos de AWS del servicio bucket:

docker compose run --rm -v "$PWD/backups/files:/backup" bucket \
    "aws --endpoint-url http://files:9000 s3 sync s3://antimatter /backup"

Con un archivo de liberación, haga copia de seguridad de la base de datos con pg_dump -Fc y de los directorios data/ y config/ con sus herramientas habituales.

Restaurar en un nuevo host

Coloque compose.yaml, el .env guardado y las copias de seguridad en un nuevo directorio, luego:

stamp=20261016-030000          # the backup to restore
docker compose create           # creates the volumes, starts nothing
docker compose up -d postgres
docker compose exec -T postgres pg_restore -U antimatter -d antimatter --no-owner \
    < "backups/antimatter-db-$stamp.dump"
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data" -v "$PWD/backups:/backup" \
        alpine tar -xzf "/backup/antimatter-$v-$stamp.tar.gz" -C /data
done
docker compose up -d

Use el mismo .env: el almacenamiento y la base de datos deben mantener las contraseñas que tenían. Si el nuevo host tiene otra dirección, actualice SITE_URL (y DOMAIN).

Pruebe sus copias de seguridad restaurándolas en otra máquina de vez en cuando.

Actualizar

  1. Haga una copia de seguridad.
  2. Cambie la etiqueta de la imagen en .env (ANTIMATTER_IMAGE), si fija una, como se recomienda.
  3. Descargue y reinicie: 
    docker compose pull
docker compose up -d
docker compose logs -f antimatter

Al iniciar, el servidor actualiza el esquema de la base de datos (puedes seguir el proceso en el registro; en un servidor grande puede tardar varios minutos) e instala las versiones más recientes de las aplicaciones incluidas en la imagen. Si usas un archivo de versión: detén el servidor, reemplaza todo excepto config/, data/, logs/, plugins/ y client/plugins/ con el contenido del nuevo archivo y vuelve a iniciarlo.

Las actualizaciones solo se realizan hacia adelante. Una vez que un servidor más reciente ha actualizado la base de datos, una versión anterior no puede usarla: para revertir, restaura la copia de seguridad realizada antes de la actualización. Lo mismo aplica al pasar de antimatter-next de vuelta a antimatter.

Versiones

El servidor de Antimatter informa la versión de la línea de Mattermost en la que se basa (actualmente 12.0.0). Las imágenes se reconstruyen desde las ramas main: antimatter-next cada noche (etiquetas nightly-<YYYYMMDD>) y ambas imágenes en cada cambio (etiquetas sha-<commit>). Fija una de estas etiquetas, actualiza de forma intencional y anota la etiqueta anterior para saber con qué copia de seguridad corresponde.

Versiones principales de PostgreSQL

El archivo de compose usa postgres:17-alpine. Antimatter requiere PostgreSQL 15 o superior. Una nueva versión principal de PostgreSQL no puede leer el directorio de datos de la versión anterior: para pasar a una nueva, realiza un volcado de la base de datos, inicia la nueva versión en un volumen nuevo y restaura el volcado en ella.

Migración desde Mattermost

Antimatter usa el esquema de base de datos de Mattermost y agrega sus propias tablas, por lo que puede tomar el control de la base de datos PostgreSQL y los archivos de un servidor de Mattermost. Pruébalo primero en una copia:

  1. Realiza una copia de seguridad de la base de datos de Mattermost, su almacenamiento de archivos (data/ o cubo S3) y config.json, y luego detén Mattermost.
  2. Restaura la base de datos en el PostgreSQL de Antimatter, o apunta Antimatter a una copia de esta (AM_SQLSETTINGS_DATASOURCE).
  3. Copia los archivos al almacenamiento de Antimatter, manteniendo sus rutas: al cubo antimatter con una herramienta S3, o a data/ con un archivo de versión.
  4. Reutiliza tu configuración: copia config.json o muévelo a la base de datos con amctl --local config migrate (ver Configuración). Tus variables de entorno MM_ siguen funcionando; renómbralas a AM_ cuando sea conveniente.
  5. Inicia Antimatter y sigue el registro mientras actualiza la base de datos. Después, revisa Consola de sistema › Plugins › Gestión de Plugins. Antimatter instala sus propias versiones de Llamadas, Playbooks, Kanban (Tableros), Agentes e integraciones cuando son más recientes que la versión instalada. Si Mattermost tenía una versión más reciente de alguna de ellas, elimina esa aplicación y reinicia Antimatter para que se instale su propia versión.
  6. Configura las notificaciones móviles de nuevo, con tu propio proxy de notificaciones: Antimatter nunca envía notificaciones a los servicios de Mattermost, ya sean de prueba o alojados, que solo las entregan a las propias aplicaciones de Mattermost. Hasta que cambies Servidor de Notificaciones Móviles, el servidor no envía notificaciones móviles (ver Notificaciones móviles).

Antimatter no contacta ningún servicio operado por Mattermost, Inc. (consulta Conexiones a servicios externos), incluso si tu configuración aún menciona uno:

  • un servidor de notificaciones push de Mattermost se conserva en la configuración, pero nunca se utiliza;
  • se vacían las direcciones de Mattermost para el marketplace de aplicaciones (URL del Marketplace) y para los avisos de producto;
  • la aplicación Llamadas utiliza el servidor STUN público de Cloudflare en lugar del de Mattermost, sin modificar la configuración guardada (consulta Llamadas);
  • se eliminan la comprobación de actualizaciones de seguridad y el informe de errores, junto con sus ajustes en la Consola de sistema (Activar alertas de seguridad, Activar diagnóstico e informe de errores) y la página Avisos.

El socket de modo local ahora es /var/tmp/antimatter_local.socket; amctl también intenta el antiguo /var/tmp/mattermost_local.socket. Mattermost solo admite PostgreSQL en sus versiones recientes, y lo mismo ocurre con Antimatter: primero, migra una base de datos de MySQL a PostgreSQL. Volver a Mattermost después de que Antimatter haya actualizado la base de datos implica restaurar tu copia de seguridad de Mattermost.

Exportar e importar datos

El formato de exportación masiva permite mover datos entre servidores: el servidor completo, algunas comunidades o algunos canales, con adjuntos, fotos de perfil y emojis personalizados si los deseas.

# on the source server
amctl export create --team-name design --include-profile-pictures
amctl export list
amctl export download <export file> design.zip
# on the destination server
amctl import upload design.zip
amctl import list available
amctl import process <uploaded file> --imported-users active

Puedes observar los trabajos con amctl export job list y amctl import job list. Para una exportación de comunidad o canal, se requiere --imported-users: active cuando las personas se trasladan a este servidor, inactive cuando se importa en un servidor donde ya tienen cuentas, de modo que las cuentas creadas a partir de coincidencias inciertas permanezcan inactivas hasta que un administrador las verifique. --destination-team-name importa en una comunidad existente. Las exportaciones e importaciones se conservan en el almacenamiento del servidor (ExportSettings.Directory, ImportSettings.Directory) durante 30 días por defecto.

En el propio servidor, antimatter export bulk y antimatter import bulk --apply realizan lo mismo desde archivos, sin pasar por la API.
