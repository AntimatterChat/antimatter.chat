"OpenAI-compatible" means a server that offers the same HTTP API as OpenAI. Most model servers you can run yourself do (for example Ollama, vLLM, llama.cpp's server, or Whisper and text-to-speech servers), as do many cloud providers and gateways such as LiteLLM or OpenRouter. No licence is needed for any of these features.

The built-in features (rewrite, recaps, translation and read aloud) and the agents need no app: they use the model connections you add in the System Console.

Model connections

A model connection is an AI provider Antimatter may call: its address, its key and its models. You add it once, then pick it for each feature that should use it. There are two kinds:

  • Server-wide connections, managed by system administrators in System Console › AI › Connections and agents. Only they can serve the built-in features. Apps can use them too, for the people allowed to.
  • Community connections, which a community's admins add for their own community in the community's settings (see below). Apps use them for the community's people. They never serve the built-in features.

The AI section of the System Console shows to the people who may manage the server-wide connections: system administrators, by default. Its Connections and agents page (the same address as before, admin_console/ai/model_connections) lists the server-wide connections and those of every community, then the server-wide agents (see AI agents).

Add a connection

In System Console › AI › Connections and agents, under Model connections, click Add a connection, then fill in the form:

Test connection checks the address and the key: the server asks the endpoint for its models, or sends a one-token chat. A changed address is tested with the saved key only after you save, or if you type the key again. Click Add connection to save.

The server makes the requests itself, so it must reach the API: a model server in the same compose project, on your network, or on the Internet. Outgoing requests honour the HTTP_PROXY and HTTPS_PROXY variables.

Deleting a connection forgets its key. The features that used it stop using AI until you pick another connection.

Limits and budgets

Each connection has four limits. Empty or 0 means no limit.

  • Requests per minute and Per person, requests per minute. They are counted by each server separately: a cluster of three servers lets through up to three times the rate.
  • Tokens per month and Per person, tokens per month: token budgets, per calendar month (UTC), counted in the database for the whole cluster. Several requests running at the same moment can go slightly past a budget.

The per-person limits also apply to the rewrite and to recaps: they count against the person who rewrites, or who owns the recap.

Usage

The list shows each connection's use this month. Usage opens the details: tokens in and out, requests, the monthly budget, use by day (UTC) and by use (Rewrite, Recaps, Auto-translation, Text to speech, People, through apps, or an app).

Every call that a person or an app makes through a connection also writes an audit record: who, the connection, the use, the model, the token counts and whether it worked, never what was said. The built-in features are only counted in the usage: translation alone makes one call per message and language.

Community connections

Community admins add their community's own connections in the community's settings, in the AI tab, under Model connections. The form is the same, without Communities: a community's connection works only in its own channels, for its own members, and its audience can only name its own teams. Roles with the Manage model connections permission can manage them too. By default, community admins have it.

A community's connection can't reach private or loopback addresses (an Ollama server on your network, for example), unless System Console › Environment › Developer › Allow untrusted internal connections to (ServiceSettings.AllowedUntrustedInternalConnections) lists them. Server-wide connections can.

See Community settings for the community admins' side.

MCP servers

An MCP server is a service that offers tools over the Model Context Protocol, which agents can use. MCP servers are listed under the model connections, in System Console › AI › Connections and agents (server-wide) or a community's AI tab (its own), managed by the same permissions as model connections. Add one with its:

FieldWhat to put
Name, and a Short nameThe short name (a slug) never changes once set: it names the server's tools, mcp.<short name>.<tool>.
AddressThe server's Streamable HTTP endpoint.
AccountEach person signs in (OAuth: an optional client ID, since Antimatter can register itself; a write-only client secret; scopes; the callback is /api/v4/ai/mcp/oauth/callback, which needs the site URL set), None, or A shared account (headers, write-only): only that server's tools that read are offered through a shared account.
SharingServer-wide servers only: which communities may use it. A community's own MCP servers are for that community's agents only.

A community's MCP server can't reach internal addresses unless Allow untrusted internal connections to allows them, as for community model connections; a server-wide server's own declared address is always reachable. MCP requests never follow a redirect. Changing a server's address or account kind signs everyone out of it; deleting one forgets everyone's sign-in.

The encryption key

The keys and extra headers of model connections are encrypted in the database (AES-256-GCM) with one encryption key. A database backup alone doesn't reveal them. The server finds the key in this order:

  1. The AM_AI_ENCRYPTION_KEY variable: 32 random bytes, in base64. Make one with openssl rand -base64 32.
  2. Otherwise, the file ai-encryption.key at the root of the server's data directory (FileSettings.Directory, ./data/ by default). The server creates it, readable by itself only, the first time a connection needs it. Apps, exports and file archives can't read it.
Without the key, the saved API keys can't be read, and every connection has to be given its key again. Back the key up with the database (see Backups and upgrades), and keep it apart from the database backups.

When to set the variable:

  • With the site's compose file. compose.yaml passes AM_AI_ENCRYPTION_KEY from .env, and keeps the key file in the data volume when the variable is empty. Setting the variable is better: the backup of .env then holds the key, apart from the database. Add it to .env and run docker compose up -d: 
    echo "AM_AI_ENCRYPTION_KEY=$(openssl rand -base64 32)" >> .env
    If the server has already created its key file, put the key it holds in .env instead, so that the saved keys stay readable: docker compose exec antimatter cat /antimatter/data/ai-encryption.key prints it.
  • A cluster whose files are in S3. Its servers share no directory, so the server doesn't create the file: set the same variable on every server. Until it is set, connections can't save keys.
  • With the release archive or the packages, the file is in data/ (/var/lib/antimatter/data for the packages). You can keep it there, or set the variable in your environment file.

To change the key, set the new one in AM_AI_ENCRYPTION_KEY and the old one in AM_AI_ENCRYPTION_PREVIOUS_KEYS (several keys separated by commas): the keys saved with the old one can still be read. A connection's key is encrypted with the new key when you type it again. Keep the old key in the list until every connection's key has been typed again.

The built-in features

In System Console › AI › Built-in features, pick for each feature a server-wide connection and its model, or Off. A feature without a connection uses no AI. Load models lists all the models of the connection; by default each feature uses the connection's chat model.

FeatureSettingWhat else it needs

Recaps: summaries of the channels people choose, on demand or on a scheduleAISettings.RecapsEnable AI Recaps in System Console › Site Configuration › Recaps (on by default), which also sets how many recaps people may make.
Auto-translationAISettings.AutoTranslationThe translation provider Model connection (recommended), in Automatic translation.
Text to speechAISettings.TextToSpeechRead messages aloud on, in Text-to-speech. The connection's /audio/speech endpoint replaces the address and key set there.

Each setting has a ConnectionId and a Model key, for example AISettings.Rewrite.ConnectionId (AM_AISETTINGS_REWRITE_CONNECTIONID). An empty Model uses the connection's default model.

The built-in features use the connection's limits, but not its audience: everyone who can use the feature can use its connection. A connection that needs attention, or that was deleted, makes the feature fail until you pick another one: the page says so.

AI agents

An agent is an account people mention or message like a colleague, shown with an AGENT tag. Agents are part of the server. There are two kinds:

  • Built-in: Antimatter answers for the agent when someone mentions it, messages it or replies in its threads, with a model connection and the agent's instructions. It answers as the person asking, with their rights: their access to the connection, and their limits and budget.
  • External agent: a program elsewhere (a coding agent on a project, for instance) signs in with the agent's token and answers like a person would. Antimatter doesn't answer for it. See Agents in the developers' guide.

System administrators manage the server-wide agents in System Console › AI › Connections and agents, below the model connections. A community's admins manage their community's own agents in the AI tab of its settings, below its model connections (see Community settings). Nobody else can create agents.

From the list you can edit an agent (its picture too), turn it off or on (nobody can talk to an agent that is off), or delete it: its account is deactivated and its settings forgotten, but its messages stay.

Tools

The agent form's Tools switch turns tools on for the agent, then offers, for each source (Antimatter's own tools, each running app's, and each MCP server available in the agent's scope): Off, All or Chosen, and Its reads run without asking. Tools always act as the person who asked, with their own rights, never as the agent.

  • A read the agent's policy allows to run on its own runs at once. Every other call (any write, and a read not set to run on its own) waits for the person: it is shown on the agent's reply with Confirm and Decline, the exact arguments, and a day to answer; only that person can answer, and the agent, the tool, and the person's access are checked again when they confirm. A declined call doesn't run, and the agent says nothing more about it.
  • An MCP tool counts as a read only when its server marks it so; everything else is a write. A shared account (see MCP servers) only offers that server's tools that read.
  • A person's own tool choices, in their AI chat settings, are one preference for every agent: they can only narrow what the agent's policy allows, never widen it.
  • Antimatter's own tools, for now: search messages, read a thread, read a channel, look someone up, and post a message, which always needs confirming.
  • Every tool call is written to the audit log: who, the tool, the agent, where, how it was decided and the outcome, and the size and a hash of the arguments, never their content.

Where agents answer

  • A built-in agent answers a message that mentions it (up to three agents per message), a message in a direct message with it, and a reply in a thread it started or was asked in that mentions nobody else. It answers in the message's thread.
  • Someone who may not talk to it gets a notice only they see: "@agent isn't available to you here."
  • Agents don't answer bots, apps, webhooks or each other.
  • Each answer is given once, by one server of a cluster.

The AI chat app

The AI chat app (id mattermost-ai, on by default) is the side panel where people talk to the agents they may use: it lists their conversations with agents and offers summaries of the channel being read. It also adds the AI actions of the message menu (Summarise thread, Find action items, Find open questions), the Ask AI menu of the new-messages line and the calls' Create meeting summary, which ask the person's agent through the server and are answered in their direct message with it. When it has no agent to offer, its panel sends admins to System Console › AI › Connections and agents, or a community admin to their community's AI tab.

The app still has its own settings, now in System Console › AI › AI chat app (the Plugins page for it is gone; the old address redirects), with its own AI Services, for the features that are still its own: React for me, AI search, custom prompts, the automatic replies of the channels set for them, and the automatic summaries of call transcripts. Its Embedding search (experimental, off) powers AI search: it needs PostgreSQL with the pgvector extension and an embedding model, and it sends every message to the embedding model, private channels and direct messages included. Under Debug, Trace Output (off, server logs or an OpenTelemetry endpoint) and Enable Token Usage Logging (written to logs/agents/token_usage.log) help find problems.

On a server upgraded to 0.9.0, the agents of the Agents app became server-wide agents, with the same accounts, connection, model, instructions and access (see Upgrading to 0.9.0). Check those marked as needing attention in System Console › AI › Connections and agents.

Speech-to-text: call transcripts and captions

Calls can be transcribed, with live captions, by a speech-to-text server that offers an OpenAI-compatible /v1/audio/transcriptions endpoint. The setup is in Calls and voice. With Summarize transcriptions on, the AI chat app's default agent also posts a summary of each transcript. People can also ask their own agent for one with Create meeting summary.

Text-to-speech: read aloud

With text-to-speech on, every message's menu has Read aloud: the server sends the message's text to a text-to-speech API and plays the audio. Settings, in System Console › Integrations › Text to speech:

Read messages aloudTextToSpeechSettings.Enable, AM_TEXTTOSPEECHSETTINGS_ENABLEtrue (off by default)
API base URLTextToSpeechSettings.URL, AM_TEXTTOSPEECHSETTINGS_URLThe base URL up to and including /v1, for example http://tts.internal:8000/v1. The server calls its /audio/speech endpoint.
ModelTextToSpeechSettings.Model, AM_TEXTTOSPEECHSETTINGS_MODELThe model as the API names it, for example tts-1. Required.
VoiceTextToSpeechSettings.Voice, AM_TEXTTOSPEECHSETTINGS_VOICEOne of the model's voices, or empty for its default.
API keyTextToSpeechSettings.APIKey, AM_TEXTTOSPEECHSETTINGS_APIKEYSent as a bearer token. Empty if the API needs none.

To use a model connection instead of the address and key above, pick it for Text to speech in AI › Built-in features. The page then says that messages are read aloud with that connection: API base URL and API key aren't used, Voice still is, and so is Model when the connection names no model. Read messages aloud must still be on.

Before sending, the server removes code blocks, links, emoji codes and formatting, and keeps at most 4000 characters. It asks for MP3 audio and keeps the last 64 results in memory, so a message read twice is only sent once.

Automatic translation

Automatic translation shows the messages of a channel in each reader's own language. Configure it in System Console › Site Configuration › Localization, under Auto-translation:

EnableAutoTranslationSettings.Enableoff
Translation providerAutoTranslationSettings.Providerconnection (shown as "Model connection (recommended)", the one picked when none is set), libretranslate, openai ("OpenAI-compatible API, set up here") or agents ("AI chat app's service (older)")
Languages allowedAutoTranslationSettings.TargetLanguagesen: the languages messages can be translated into
Translation timeout (ms)AutoTranslationSettings.TimeoutMs5000
Restrict auto-translation on direct messages and group messagesAutoTranslationSettings.RestrictDMAndGMoff

Each provider has its own fields:

  • Model connection: a server-wide connection and its model, the same setting as Auto-translation in AI › Built-in features (AISettings.AutoTranslation). A dedicated translation model is fast and accurate; a general LLM works too.
  • LibreTranslate: LibreTranslate API Endpoint and LibreTranslate API Key (AutoTranslationSettings.LibreTranslate.URL, .APIKey). A LibreTranslate server can run on your own network.
  • OpenAI-compatible API: API base URL (up to and including /v1; the server uses its chat completions endpoint), Model and API key (AutoTranslationSettings.OpenAI.URL, .Model, .APIKey). A small translation model run locally works well.
  • AI chat app's service (older): the provider of servers set up before 0.9.0, which used a service of the Agents app. It no longer needs the app: it translates with the connection picked for auto-translation in AI › Built-in features, or else with the connection copied from the app's service at the upgrade. Switch to Model connection moves the setting to the recommended provider.

Once it is on, channel admins turn translation on for a channel in its settings (Auto-translation), and each member can opt out from the channel menu (Translate messages). In direct and group messages any member can turn it on; with the restriction on, translation isn't available there. Translated messages show "Translated from …" with a link to the original.

Code, links, mentions and emoji are replaced by placeholders before the text is sent, and put back afterwards.

To keep all of it on your network, point every feature at servers you run yourself. With a cloud provider, check its data retention terms, and tell your users which features send their messages out.

Turning AI off

There is no single switch: each feature has its own.

  • Rewrite and recaps: set them to Off in System Console › AI › Built-in features. People keep reading the recaps they already have.
  • Model connections: delete a connection to stop every use of it. Without any connection, neither the built-in features nor the apps can use AI through the server.
  • Agents: turn off or delete each agent in System Console › AI › Connections and agents and in the communities' AI tabs. Disabling the AI chat app only removes its side panel and its own features (including call summaries): people can still mention or message the agents.
  • Transcription and captions: AM_CALLS_ENABLE_TRANSCRIPTIONS=false and AM_CALLS_ENABLE_LIVE_CAPTIONS=false (the defaults).
  • Read aloud: Read messages aloud off (AM_TEXTTOSPEECHSETTINGS_ENABLE=false, the default), whether or not it uses a connection.
  • Translation: auto-translation off (AM_AUTOTRANSLATIONSETTINGS_ENABLE=false, the default).

Disabling the AI chat app doesn't turn off the other features: they use model connections or their own APIs.
