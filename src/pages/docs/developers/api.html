title: The REST API description: Antimatter's REST API: the base URL, personal access tokens, session tokens and OAuth, the main resources, pagination, errors, rate limits, the WebSocket event stream and client libraries. guide: developers order: 2 nav: REST API lead: Everything the Antimatter apps do goes through the same HTTP API, so your scripts can do it too. This page explains how to authenticate, the resources you will use most, how responses and errors look, and how to follow events live over the WebSocket. ---

Basics

  • Base URL: https://chat.example.com/api/v4. All endpoints below are relative to it.
  • Format: JSON in and out, except file uploads (multipart). Send Content-Type: application/json.
  • IDs: every object has a 26-character id. Times are milliseconds since the Unix epoch (create_at, update_at, delete_at; 0 means "not deleted").
  • Communities are teams: the API calls them teams, with a team_id.
  • Yourself: wherever a path takes a user_id, me means the signed-in user, as in GET /users/me.

The full list of endpoints is in the server's code: the routes are declared in server/channels/api4/*.go and the types in server/public/model. The OpenAPI description in the repository's api/v4/source folder covers the endpoints inherited from Mattermost, and some of Antimatter's additions: moving threads, model connections, agents, community rules, focus mode and message actions. The others are only in the code.

Authentication

Every request, except signing in and a few public endpoints, needs a token in the Authorization header:

curl -H "Authorization: Bearer $TOKEN" https://chat.example.com/api/v4/users/me

Three kinds of token are accepted there: personal access tokens, session tokens and OAuth access tokens. Authorization: Token … is accepted too. Tokens in the query string (?access_token=) are only accepted for OAuth access tokens.

Personal access tokens (recommended for scripts)

A personal access token acts as you, does not expire unless you give it an expiry date, and can be revoked at any time. Personal access tokens are off by default:

  1. A system admin turns on Enable Personal Access Tokens in System Console › Integrations › Integration Management (ServiceSettings.EnableUserAccessTokens, AM_SERVICESETTINGS_ENABLEUSERACCESSTOKENS).
  2. For each person who may create tokens, a system admin opens System Console › User Management › Users, chooses Manage roles in the person's menu and ticks Allow this account to generate personal access tokens. System admins can always create them.
  3. The person opens their avatar at the top right, then Profile & settings › Security. Under Personal access tokens, they describe what the token is for and choose Create token. The token is shown once: copy it.

With the API: POST /users/{user_id}/tokens with {"description": "backup script", "expires_at": 0} (expires_at in milliseconds; 0 for none). The response's token field is the secret; its id is what you use to revoke it (POST /users/tokens/revoke with {"token_id": "…"}). From the command line: amctl token generate <user> <description>.

A system admin can cap token lifetimes with Maximum Personal Access Token Lifetime (days) on the same System Console page.

Session tokens

Signing in with a password returns a session token in the Token response header, the same kind of session the apps use:

curl -i -X POST https://chat.example.com/api/v4/users/login \
  -H 'Content-Type: application/json' \
  -d '{"login_id": "maya", "password": "…"}'

Add "token": "123456" for an account with multi-factor authentication. Sessions expire as the server's session settings say, and the login endpoint is rate limited (5 requests per second). POST /users/logout ends the session.

Browsers authenticate with a cookie instead. A request authenticated by the cookie must also send the X-CSRF-Token header for anything but GET; a token in the Authorization header needs no CSRF header.

OAuth 2.0 apps

To let people sign in to your application with their Antimatter account, register an OAuth 2.0 app. Antimatter is then the OAuth provider:

  1. Enable OAuth 2.0 Service Provider must be on (System Console › Integrations › Integration Management, ServiceSettings.EnableOAuthServiceProvider, on by default).
  2. Someone with the right to manage OAuth apps (system admins by default) opens Integrations › OAuth 2.0 apps (community menu › Community settings › Integrations), and adds the app with its callback URLs. They get a client ID and a client secret.
  3. Your application sends people to https://chat.example.com/oauth/authorize with response_type=code, client_id, redirect_uri and state. PKCE with code_challenge_method=S256 is supported.
  4. It exchanges the code at POST https://chat.example.com/oauth/access_token (grant_type=authorization_code, then refresh_token to renew), and calls the API with Authorization: Bearer <access token>.

People see the apps they authorised in Profile & settings › Security › Apps you authorized.

Post a message

curl -X POST https://chat.example.com/api/v4/posts \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"channel_id": "'$CHANNEL_ID'", "message": "Backup finished: **42 GB** in 3 min"}'

Messages are Markdown. Add "root_id" (the first post of a thread) to reply in a thread, "file_ids" for files and "props" for attachments and other extras (see Attachments).

Find a channel's ID

curl -H "Authorization: Bearer $TOKEN" \
  https://chat.example.com/api/v4/teams/name/lumen-labs/channels/name/ops-alerts

The names are those in the channel's link: /lumen-labs/channels/ops-alerts.

Pagination

List endpoints take page (from 0) and per_page (60 by default, at most 200). Keep asking for the next page until a page comes back shorter than per_page.

A channel's messages (GET /channels/{channel_id}/posts) also take since (a time: everything changed since then), or before and after (a post ID). They come back as a post list: {"order": [IDs, newest first], "posts": {ID: post}, "next_post_id", "prev_post_id"}.

Errors

Errors use the usual HTTP status codes (400 bad input, 401 not signed in, 403 not allowed, 404 not found, 501 feature turned off) and a JSON body:

{
  "id": "api.context.permissions.app_error",
  "message": "You do not have the appropriate permissions.",
  "detailed_error": "",
  "request_id": "jz8zm5nunpbt8f3gpqsz5dq6so",
  "status_code": 403
}

Use id in your code: message is translated into the user's language. detailed_error is empty unless the server runs in developer mode (ServiceSettings.EnableDeveloper). Quote request_id to the server's admin: it is in the logs.

Rate limits

Rate limiting is off by default. When a system admin turns it on (System Console › Environment › Rate Limiting), each client gets 10 requests per second with bursts of 100 by default, counted by IP address or by user. Responses carry X-RateLimit-Limit, X-RateLimit-Remaining and X-RateLimit-Reset; over the limit, the server answers 429 with a Retry-After header in seconds. Some endpoints, such as signing in, have their own limit whatever the setting.

Write scripts that wait and retry on 429, and avoid polling: follow the WebSocket instead.

The WebSocket event stream

Connect to wss://chat.example.com/api/v4/websocket. Authenticate either with the Authorization: Bearer header on the connection request, or by sending this as the first message:

{"seq": 1, "action": "authentication_challenge", "data": {"token": "…"}}

The server sends a hello event, then an event for everything you are allowed to see:

{
  "event": "posted",
  "data": {"channel_id": "…", "channel_type": "O", "post": "{\"id\":\"…\",\"message\":\"Hello\",…}"},
  "broadcast": {"channel_id": "…", "team_id": "", "user_id": "", "omit_users": null},
  "seq": 4
}

Note that data.post is the post as a JSON string. Common events: posted, post_edited, post_deleted, reaction_added, reaction_removed, typing, status_change, user_added, direct_added. Apps send their own events, named custom_<app id>_<event>.

You can also send actions, each with an increasing seq: user_typing with {"channel_id", "parent_id"}, or get_statuses. Reconnect when the connection drops, and fetch what you missed with since (see Pagination).

Antimatter adds these events: agent_activity_changed and agent_post_stream (see Agents), ai_tools_changed (see Agents), community_rules_updated and community_rules_accepted (see Community rules), focus_ended (see Focus mode), community_attributes_updated, member_timeouts_updated, post_put_on_top, post_removed_from_top, server_categories_updated, channel_overrides_updated and category_overrides_updated. A new sign-in to your own account sends session_created to your other sessions (session_id, create_at, platform, os, browser, mobile; never a token), and handling its warning sends session_revoked or session_acknowledged (session_id) to all of them.

Client libraries

  • Go: model.Client4 in server/public/model (import github.com/mattermost/mattermost/server/public/model). model.NewAPIv4Client(url), then client.SetToken(token); model.NewWebSocketClient4(wsURL, token) follows events. Antimatter's copy adds methods for its own endpoints, such as UpdateMessageRequest, PutPostOnTop and ExportChannel.
  • TypeScript: the Client4 class of @mattermost/client, in webapp/platform/client, with its types in webapp/platform/types. The copy in Antimatter's repository includes Antimatter's endpoints; the package published on npm by Mattermost does not.
package main

import (
	"context"
	"log"

	"github.com/mattermost/mattermost/server/public/model"
)

func main() {
	client := model.NewAPIv4Client("https://chat.example.com")
	client.SetToken("…")
	post, _, err := client.CreatePost(context.Background(), &model.Post{
		ChannelId: "…",
		Message:   "Hello from Go",
	})
	if err != nil {
		log.Fatal(err)
	}
	log.Println("posted", post.Id)
}

New fields

  • Communities (Team, and PUT /teams/{team_id}/patch): all_channels_membership (everyone is in every channel they may see), default_channel_id (where newcomers land), welcome_channel_id (where its join and leave messages go, empty for none), kind (community or workplace, shown in the interface as Guild and Workspace: a guild also turns all_channels_membership on; new communities get the server's TeamSettings.DefaultCommunityKind, community/Guild by default), member_list_view (how the member list groups members: choice, the default, lets each member choose; roles or teams fixes it), hide_role_colors, require_team_badges, name_display (how the community shows people: empty for the server's default), onboarding and autolinks (both JSON strings).
  • The default channel of a new community is general (General), not town-square. The 0.9.0 upgrade renames each community's town-square to general, keeping its ID, unless the community already has a general channel. Old names keep working: GET /teams/{team_id}/channels/name/town-square, GET /teams/name/{team}/channels/name/town-square and an incoming webhook's channel give the community's default channel when no channel has that name. Use default_channel_id, or the name general, in new code.
  • Channel links: #channel-name links a channel, as ~channel-name does. The post's channel_mentions prop lists the channels linked either way; a #word that names no channel stays a hashtag. Antimatter's web interface and mobile app write #name.
  • Archived channels still take new members (POST /channels/{channel_id}/members), who can read their history. Nobody can post, react, pin, put a message on top, rename the channel or change its members' roles there.
  • Inline replies: a post with "props": {"reply_to": "<post id>"} quotes that message of the same channel. Add "reply_to_mention": false to leave its author unnotified. The server fills metadata.reply_to with a short description of the quoted message.
  • Spoilers: "props": {"spoiler": true} hides a post's text and files until the reader chooses to see them.
  • Ignoring and blocking are preferences: category user_block, named after the other person's ID, with the value ignore or block. Whether a direct message waits as a request is in your channel member's notify_props.dm_request (pending, accepted or dismissed).
  • Message attachments can carry stages and a chart: see Cards.

Move a thread

POST /posts/{post_id}/move_to_channel moves a thread, its first message and all its replies, to another channel of the same community. post_id can be the first message or any reply.

curl -X POST https://chat.example.com/api/v4/posts/$POST_ID/move_to_channel \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"channel_id": "'$TARGET_CHANNEL_ID'", "flatten": false}'
  • channel_id (required): the channel the thread moves to.
  • flatten (default false): true makes the replies messages of the target channel instead of a thread. Fusion's Make it a channel uses it.

The messages keep their authors, times, reactions and files. Their copies carry the silent_notification prop, so they notify nobody. The original messages are deleted. The answer is the moved first message, with its new ID.

Who may move a thread

  • You must be able to read the thread and to post in the target channel.
  • The channel's admins, the community's admins, people with Manage messages (delete_others_posts) in the channel, and system admins may move any thread.
  • The thread's author may move it when both channels are public, or when every message of the thread is theirs. Otherwise the answer is 403 with the ID api.post.move_thread.private_needs_moderator.app_error.
  • Both channels must be in the same community (no direct or group messages), different, and not archived. System messages and burn-on-read messages can't be moved.
  • A thread longer than WranglerSettings.MoveThreadMaxCount messages (100 by default; 0 for no limit) is refused.

The pointer and the note

The move leaves two system messages of type system_wrangler: a pointer in the old channel ("A thread with 13 messages has been moved to #target") and a note in the target ("This thread was moved from #source"), under the moved thread or, with flatten, after its messages. Besides the message text, their props let a client draw the channel name as a link:

  • The pointer: MovedThreadPermalink, NumMessages, MovedThreadChannelId, MovedThreadTeamName, MovedThreadPostId, and, for a public target, MovedThreadChannelName and MovedThreadChannelDisplayName.
  • The note: MovedFromChannelId, MovedFromTeamName, MovedFromPostId (the pointer), MovedFromPermalink, and, for a public source, MovedFromChannelName and MovedFromChannelDisplayName.

Both also have a TranslationID. A private channel's name is left out: readers see "another channel". Mattermost's own POST /posts/{post_id}/move stays off in Antimatter; use this endpoint.

Community rules

A community's admins can make its members agree to its rules before they post in its channels. While the rules are on, a member who hasn't agreed to the current version can't post, reply, send files, schedule, edit or restore a message, or run a command that posts in the community's channels: the server answers 403 with the ID api.post.community_rules_not_accepted, and a scheduled message due then fails with the error code community_rules_not_accepted. Reading, reactions, and direct and group messages aren't held back; neither are bots, incoming webhooks, system messages, and the community's admins (manage_team, which system admins have too).

EndpointWhat it does
GET /teams/{team_id}/rulesThe rules (enabled, text in Markdown, version), with the latest version you agreed to (accepted_version) and whether you must agree before you post (must_accept). For members, and for anyone who may join an open community.
PUT /teams/{team_id}/rulesSaves them, with {"enabled", "text", "ask_again"} (manage_team). ask_again makes a new version that everyone must agree to again; the first save is version 1. The text is required to turn them on, at most 16,000 characters.
POST /teams/{team_id}/rules/acceptAgrees, as a member, to the version you read; 409 when a newer version was saved since, and 0 agrees to the current one.
GET /teams/{team_id}/rules/statsHow many of the community's members agreed to the current version (manage_team).

The community_rules_updated event goes to the community when an admin saves the rules (team_id, enabled, version), and community_rules_accepted to the one who agreed, on all their sessions (team_id, version).

Focus mode

Focus mode is Do not disturb with an end time: notifications are muted (no push, email, desktop or persistent notifications, urgent messages included), the reason becomes the custom status with the 🎯 emoji (dart), expiring at the end, and Antimatter's apps hide the person's own unread badges. Only the person themself can use these endpoints (me or their own ID): nobody else, system admins included, may start, end or read someone's focus or its summary.

EndpointWhat it does
GET /users/me/focusThe current focus (active, start_at, end_at, reason), or the last one once it ended (ended_at set), or all zero.
POST /users/me/focusStarts focusing, or while focusing changes the end and the reason: {"duration": "1h30m", "reason": "…"}, or {"end_at": ms} instead of the duration, from a minute to a week away. "duration": "tomorrow" ends at 09:00 the next day in the person's time zone. The end is rounded down to the minute; the reason is at most 100 characters. Needs user statuses on (ServiceSettings.EnableUserStatuses); bots can't focus.
DELETE /users/me/focusEnds the focus now.
GET /users/me/focus/summary?since=&until=What was missed in that window (a focus's start_at and ended_at): the channels with unread messages from others (direct and group messages first, then those with mentions; muted channels only with a mention), and, with collapsed reply threads, the followed threads with new replies, each with its count, mentions and last sender.
POST /users/me/focus/summary/readWith {"since", "until"}: marks those channels and threads read up to until only; what came after stays unread.

While someone focuses, their user has the prop focus_until (milliseconds), which clients use to show the focusing status; it can't be changed through the profile. The focus ends when the person ends it, when its time comes (within a minute), or when they pick a status themself, which then stays. Otherwise the status and custom status from before come back. All their sessions then get the focus_ended event, with start_at, end_at and ended_by (user, timer or status).

Model connections

A model connection is an AI provider's address and key, set up by an admin. The server's AI features and the apps that call the AI service use them. System admins manage the server-wide connections (manage_ai_connections); a community's admins manage their community's own (manage_team_ai_connections). Keys are write-only: no answer carries one, only api_key_set and api_key_last4.

Changes are written to the audit log. The admin guide explains the settings: see AI.

Agents

An agent is a bot account of the kind agent (is_agent on its user), with its settings: its scope (server, or a community's ID), built-in or external, and for a built-in agent its model connection, model, system prompt and reasoning. System admins manage the server-wide agents (manage_system), a community's admins their community's (manage_team); on top of that, manage_own_agent for an agent they made and manage_others_agent for the others. The agent's ID in these paths is its user ID. Running an external agent, and how a built-in agent's status is set, is explained in Bots; PUT /users/{user_id}/status and the custom status endpoints refuse a built-in agent's ID, for system admins too (403, api.status.agent.app_error).
