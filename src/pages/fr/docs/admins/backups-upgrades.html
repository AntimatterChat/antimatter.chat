La base de données et les fichiers vont ensemble : sauvegardez-les en même temps et conservez des copies hors du serveur. Les noms de volumes commencent par le nom du projet compose, antimatter (docker volume ls les liste).

Sauvegarder

Depuis le répertoire de compose.yaml. Arrêter Antimatter d'abord donne une copie entièrement cohérente ; une sauvegarde effectuée pendant son fonctionnement est généralement correcte, mais les fichiers envoyés pendant la sauvegarde peuvent en être absents.

stamp=$(date +%Y%m%d-%H%M%S)
mkdir -p backups
docker compose stop antimatter
# Database
docker compose exec -T postgres pg_dump -U antimatter -d antimatter -Fc \
    > "backups/antimatter-db-$stamp.dump"
# File storage and GIF service
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data:ro" -v "$PWD/backups:/backup" \
        alpine tar -czf "/backup/antimatter-$v-$stamp.tar.gz" -C /data .
done
docker compose start antimatter
# Secrets
cp .env "backups/env-$stamp"

Exécutez-le depuis cron pour des sauvegardes quotidiennes, et copiez le répertoire backups/ sur une autre machine. Conservez les copies de .env aussi sûres que le serveur : elles contiennent ses mots de passe.

Pour copier les fichiers envoyés objet par objet (par exemple vers un autre stockage S3), utilisez l'outil en ligne de commande AWS du service bucket :

docker compose run --rm -v "$PWD/backups/files:/backup" bucket \
    "aws --endpoint-url http://files:9000 s3 sync s3://antimatter /backup"

Avec une archive de version, sauvegardez la base de données avec pg_dump -Fc, et les répertoires data/ et config/ avec vos outils habituels.

Restaurer sur un nouvel hôte

Placez compose.yaml, le .env sauvegardé et les sauvegardes dans un nouveau répertoire, puis :

stamp=20261016-030000          # the backup to restore
docker compose create           # creates the volumes, starts nothing
docker compose up -d postgres
docker compose exec -T postgres pg_restore -U antimatter -d antimatter --no-owner \
    < "backups/antimatter-db-$stamp.dump"
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data" -v "$PWD/backups:/backup" \
        alpine tar -xzf "/backup/antimatter-$v-$stamp.tar.gz" -C /data
done
docker compose up -d

Utilisez le même .env : le stockage et la base de données doivent conserver les mots de passe qu'ils avaient. Si le nouvel hôte a une autre adresse, mettez à jour SITE_URL (et DOMAIN).

Testez vos sauvegardes en les restaurant sur une autre machine de temps en temps.

Mettre à niveau

  1. Faites une sauvegarde.
  2. Changez l'étiquette de l'image dans .env (ANTIMATTER_IMAGE), si vous en fixez une, comme recommandé.
  3. Tirez et redémarrez : 
    docker compose pull
docker compose up -d
docker compose logs -f antimatter

Au démarrage, le serveur met à jour le schéma de la base de données (suivez le processus dans le journal ; cela peut prendre plusieurs minutes sur un serveur volumineux) et installe les versions plus récentes des applications intégrées à l’image. Avec une archive de version : arrêtez le serveur, remplacez tout sauf config/, data/, logs/, plugins/ et client/plugins/ par le contenu de la nouvelle archive, puis redémarrez-le.

Les mises à niveau ne se font que vers l’avant. Une fois qu’un serveur plus récent a mis à jour la base de données, une version antérieure ne peut plus l’utiliser : pour revenir en arrière, restaurez la sauvegarde effectuée avant la mise à niveau. La même règle s’applique au retour de antimatter-next à antimatter.

Versions

Le serveur Antimatter indique la version de la ligne Mattermost sur laquelle il est basé (actuellement 12.0.0). Les images sont reconstruites à partir des branches main : antimatter-next chaque nuit (étiquettes nightly-<YYYYMMDD>) et les deux images à chaque modification (étiquettes sha-<commit>). Fixez l'une de ces étiquettes, effectuez les mises à niveau de manière intentionnelle et notez l'étiquette précédente pour savoir à quelle sauvegarde elle correspond.

Versions majeures de PostgreSQL

Le fichier compose utilise postgres:17-alpine. Antimatter nécessite PostgreSQL 15 ou une version plus récente. Une nouvelle version majeure de PostgreSQL ne peut pas lire le répertoire de données de la version précédente : pour passer à une nouvelle version, effectuez une copie de la base de données, démarrez la nouvelle version sur un nouveau volume et restaurez la copie dans celle-ci.

Migration depuis Mattermost

Antimatter utilise le schéma de base de données de Mattermost et y ajoute ses propres tables, ce qui lui permet de reprendre la base de données PostgreSQL et les fichiers d’un serveur Mattermost. Testez d’abord sur une copie :

  1. Sauvegardez la base de données Mattermost, son stockage de fichiers (data/ ou bucket S3) et config.json, puis arrêtez Mattermost.
  2. Restaurez la base de données dans PostgreSQL d’Antimatter, ou pointez Antimatter vers une copie de celle-ci (AM_SQLSETTINGS_DATASOURCE).
  3. Copiez les fichiers dans le stockage d’Antimatter en conservant leurs chemins : vers le bucket antimatter avec un outil S3, ou vers data/ avec une archive de version.
  4. Réutilisez vos paramètres : copiez config.json, ou transférez-le dans la base de données avec amctl --local config migrate (voir Configuration). Vos variables d’environnement MM_ continuent de fonctionner ; renommez-les en AM_ lorsque c’est pratique.
  5. Démarrez Antimatter et suivez le journal pendant la mise à niveau de la base de données. Vérifiez ensuite Console système › Plugins › Gestion des plugins. Antimatter installe ses propres versions des applications Appels, Playbooks, Kanban (Tableaux), Agents et des intégrations lorsqu’elles sont plus récentes que la version installée. Si Mattermost disposait d’une version plus récente de l’une de ces applications, supprimez-la et redémarrez Antimatter afin que sa propre version soit installée.
  6. Reconfigurez les notifications push avec votre propre proxy push : Antimatter n’envoie jamais de notifications aux services push de Mattermost, qu’ils soient de test ou hébergés, car ceux-ci ne livrent que vers les applications de Mattermost. Tant que vous ne modifiez pas le Serveur de notifications push, le serveur n’envoie aucune notification push (voir Notifications push).

Antimatter ne contacte aucun service exploité par Mattermost, Inc. (voir Connexions aux services externes), même si votre configuration en mentionne encore un :

  • un serveur de notifications push chez Mattermost est conservé dans les paramètres mais n’est jamais utilisé ;
  • les adresses de Mattermost pour le marché d’applications (URL du marché) et pour les notifications produit sont vidées ;
  • l’application Appels utilise le serveur STUN public de Cloudflare au lieu de celui de Mattermost, sans modifier le paramètre enregistré (voir Appels) ;
  • la vérification des mises à jour de sécurité et la télémétrie des pannes ont été supprimées, ainsi que leurs paramètres dans la Console système (Activer les alertes de sécurité, Activer le diagnostic et la télémétrie des erreurs) et la page Notifications.

Le socket du mode local est désormais /var/tmp/antimatter_local.socket ; amctl tente également l’ancien /var/tmp/mattermost_local.socket. Mattermost ne prend en charge que PostgreSQL dans ses versions récentes, et il en va de même pour Antimatter : migrez d’abord une base de données MySQL vers PostgreSQL. Revenir à Mattermost après que Antimatter a mis à niveau la base de données implique de restaurer votre sauvegarde Mattermost.

Exporter et importer des données

Le format d’exportation en masse permet de transférer des données entre serveurs : l’ensemble du serveur, certaines communautés ou certains canaux, avec les pièces jointes, les photos de profil et les emojis personnalisés si vous le souhaitez.

# on the source server
amctl export create --team-name design --include-profile-pictures
amctl export list
amctl export download <export file> design.zip
# on the destination server
amctl import upload design.zip
amctl import list available
amctl import process <uploaded file> --imported-users active

Surveillez les tâches avec amctl export job list et amctl import job list. Pour une exportation ou une importation de communauté ou de canal, l'option --imported-users est obligatoire : active si les personnes rejoignent ce serveur, inactive si vous importez vers un serveur où elles disposent déjà d'un compte, afin que les comptes créés à partir d'appariements incertains restent inactifs jusqu'à ce qu'un administrateur les vérifie. L'option --destination-team-name permet d'importer vers une communauté existante. Les exportations et importations sont conservées sur le stockage du serveur (ExportSettings.Directory, ImportSettings.Directory) pendant 30 jours par défaut.

Sur le serveur lui-même, les commandes antimatter export bulk et antimatter import bulk --apply effectuent les mêmes opérations à partir de fichiers, sans passer par l'API.
