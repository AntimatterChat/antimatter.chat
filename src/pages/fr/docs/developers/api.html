Bases

  • URL de base : https://chat.example.com/api/v4. Tous les points de terminaison ci-dessous sont relatifs à celle-ci.
  • Format : JSON en entrée et en sortie, à l'exception des envois de fichiers (multipart). Envoyez Content-Type: application/json.
  • Identifiants : chaque objet possède un id de 26 caractères. Les dates sont en millisecondes depuis l'époque Unix (create_at, update_at, delete_at ; 0 signifie « non supprimé »).
  • Les communautés sont des équipes : l'API les appelle teams, avec un team_id.
  • Vous-même : partout où un chemin prend un user_id, me désigne l'utilisateur connecté, comme dans GET /users/me.

La liste complète des points de terminaison se trouve dans le code du serveur : les routes sont déclarées dans server/channels/api4/*.go et les types dans server/public/model. La description OpenAPI dans le dossier api/v4/source du dépôt couvre les points de terminaison hérités de Mattermost, et non les ajouts d'Antimatter.

Authentification

Chaque requête, à l'exception de la connexion et de quelques points de terminaison publics, nécessite un jeton dans l'en-tête Authorization :

curl -H "Authorization: Bearer $TOKEN" https://chat.example.com/api/v4/users/me

Trois types de jetons y sont acceptés : jetons d'accès personnels, jetons de session et jetons d'accès OAuth. Authorization: Token … est également accepté. Les jetons dans la chaîne de requête (?access_token=) ne sont acceptés que pour les jetons d'accès OAuth.

Jetons d'accès personnels (recommandés pour les scripts)

Un jeton d'accès personnel agit en votre nom, n'expire pas à moins que vous ne lui donniez une date d'expiration, et peut être révoqué à tout moment. Les jetons d'accès personnels sont désactivés par défaut :

  1. Un admin système active Activer les jetons d'accès personnel dans Console système › Intégrations › Gestion des intégrations (ServiceSettings.EnableUserAccessTokens, AM_SERVICESETTINGS_ENABLEUSERACCESSTOKENS).
  2. Pour chaque personne pouvant créer des jetons, un administrateur système ouvre Console système › Gestion des utilisateurs › Utilisateurs, choisit Gérer les rôles dans le menu de la personne et coche Permettre à ce compte de générer des jetons d'accès personnels. Les administrateurs système peuvent toujours les créer.
  3. La personne ouvre son avatar en haut à droite, puis Profil et paramètres › Sécurité. Sous Jetons d'accès personnel, elle décrit l'usage du jeton et choisit Créer un nouveau jeton. Le jeton n'est affiché qu'une seule fois : copiez-le.

Via l'API : POST /users/{user_id}/tokens avec {"description": "backup script", "expires_at": 0} (expires_at en millisecondes ; 0 pour aucune). Le champ token de la réponse est le secret ; son id est ce que vous utilisez pour le révoquer (POST /users/tokens/revoke avec {"token_id": "…"}). Depuis la ligne de commande : amctl token generate <user> <description>.

Un admin système peut limiter la durée de validité des jetons avec Durée de validité maximale des jetons d’accès personnels (jours) sur la même page de la Console système.

Jetons de session

La connexion avec un mot de passe renvoie un jeton de session dans l'en-tête de réponse Token, le même type de session utilisé par les applications :

curl -i -X POST https://chat.example.com/api/v4/users/login \
  -H 'Content-Type: application/json' \
  -d '{"login_id": "maya", "password": "…"}'

Ajoutez "token": "123456" pour un compte avec authentification multifacteur. Les sessions expirent selon les paramètres de session du serveur, et le point de terminaison de connexion est limité en débit (5 requêtes par seconde). POST /users/logout met fin à la session.

Les navigateurs s'authentifient avec un cookie. Une requête authentifiée par le cookie doit également envoyer l'en-tête X-CSRF-Token pour tout ce qui n'est pas une requête GET ; un jeton dans l'en-tête Authorization n'a pas besoin d'en-tête CSRF.

Applications OAuth 2.0

Pour permettre aux personnes de se connecter à votre application avec leur compte Antimatter, enregistrez une application OAuth 2.0. Antimatter est alors le fournisseur OAuth :

  1. Activer le fournisseur de service OAuth 2.0 doit être activé (Console système › Intégrations › Gestion des intégrations, ServiceSettings.EnableOAuthServiceProvider, activé par défaut).
  2. Une personne ayant le droit de gérer les applications OAuth (les administrateurs système par défaut) ouvre son avatar, puis Intégrations › Applications OAuth 2.0, et ajoute l'application avec ses URL de rappel. Elle obtient un identifiant de client et un secret de client.
  3. Votre application redirige les utilisateurs vers https://chat.example.com/oauth/authorize avec response_type=code, client_id, redirect_uri et state. PKCE avec code_challenge_method=S256 est pris en charge.
  4. Elle échange le code via POST https://chat.example.com/oauth/access_token (grant_type=authorization_code, puis refresh_token pour le renouveler), et appelle l'API avec Authorization: Bearer <access token>.

Les utilisateurs voient les applications qu'ils ont autorisées dans Profil et paramètres › Sécurité › Applications autorisées.

Publier un message

curl -X POST https://chat.example.com/api/v4/posts \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"channel_id": "'$CHANNEL_ID'", "message": "Backup finished: **42 GB** in 3 min"}'

Les messages sont au format Markdown. Ajoutez "root_id" (le premier message d'un fil de discussion) pour répondre dans un fil, "file_ids" pour les fichiers et "props" pour les pièces jointes et autres éléments supplémentaires (voir Pièces jointes).

Trouver l'identifiant d'un canal

curl -H "Authorization: Bearer $TOKEN" \
  https://chat.example.com/api/v4/teams/name/lumen-labs/channels/name/ops-alerts

Les noms sont ceux présents dans le lien du canal : /lumen-labs/channels/ops-alerts.

Pagination

Les points d'accès de liste acceptent page (à partir de 0) et per_page (60 par défaut, 200 au maximum). Continuez à demander la page suivante jusqu'à ce qu'une page renvoyée soit plus courte que per_page.

Les messages d'un canal (GET /channels/{channel_id}/posts) acceptent également since (un horodatage : tout ce qui a changé depuis) ou before et after (un identifiant de message). Ils sont renvoyés sous forme de liste de messages : {"order": [IDs, newest first], "posts": {ID: post}, "next_post_id", "prev_post_id"}.

Erreurs

Les erreurs utilisent les codes d'état HTTP habituels (400 entrée invalide, 401 non authentifié, 403 non autorisé, 404 introuvable, 501 fonction désactivée) et un corps JSON :

{
  "id": "api.context.permissions.app_error",
  "message": "You do not have the appropriate permissions.",
  "detailed_error": "",
  "request_id": "jz8zm5nunpbt8f3gpqsz5dq6so",
  "status_code": 403
}

Utilisez id dans votre code : message est traduit dans la langue de l'utilisateur. detailed_error est vide sauf si le serveur fonctionne en mode développeur (ServiceSettings.EnableDeveloper). Citez request_id à l'admin du serveur : il figure dans les journaux.

Limites de débit

La limitation de débit est désactivée par défaut. Lorsqu'un admin système l'active (Console système › Environnement › Limitation de débit), chaque client reçoit 10 requêtes par seconde avec des rafales de 100 par défaut, comptées par adresse IP ou par utilisateur. Les réponses contiennent X-RateLimit-Limit, X-RateLimit-Remaining et X-RateLimit-Reset ; au-delà de la limite, le serveur répond 429 avec un en-tête Retry-After en secondes. Certains points d'accès, comme l'authentification, ont leur propre limite quelle que soit la configuration.

Écrivez des scripts qui attendent et réessaient en cas de 429, et évitez le sondage : suivez plutôt le WebSocket.

Le flux d'événements WebSocket

Connectez-vous à wss://chat.example.com/api/v4/websocket. Authentifiez-vous soit avec l'en-tête Authorization: Bearer sur la requête de connexion, soit en envoyant ceci comme premier message :

{"seq": 1, "action": "authentication_challenge", "data": {"token": "…"}}

Le serveur envoie un événement hello, puis un événement pour tout ce que vous êtes autorisé à voir :

{
  "event": "posted",
  "data": {"channel_id": "…", "channel_type": "O", "post": "{\"id\":\"…\",\"message\":\"Hello\",…}"},
  "broadcast": {"channel_id": "…", "team_id": "", "user_id": "", "omit_users": null},
  "seq": 4
}

Notez que data.post est le message au format JSON. Événements courants : posted, post_edited, post_deleted, reaction_added, reaction_removed, typing, status_change, user_added, direct_added. Les applications émettent leurs propres événements, nommés custom_<app id>_<event>.

Vous pouvez également envoyer des actions, chacune avec un seq croissant : user_typing avec {"channel_id", "parent_id"}, ou get_statuses. Reconnectez-vous lorsque la connexion est interrompue, et récupérez ce que vous avez manqué avec since (voir Pagination).

Antimatter ajoute les événements suivants : community_attributes_updated, member_timeouts_updated, post_put_on_top, post_removed_from_top, server_categories_updated, channel_overrides_updated et category_overrides_updated.

Bibliothèques client

  • Aller à : model.Client4 dans server/public/model (importer github.com/mattermost/mattermost/server/public/model). model.NewAPIv4Client(url), puis client.SetToken(token) ; model.NewWebSocketClient4(wsURL, token) suit les événements. La copie d'Antimatter ajoute des méthodes pour ses propres points d'entrée, telles que UpdateMessageRequest, PutPostOnTop et ExportChannel.
  • TypeScript : la classe Client4 de @mattermost/client, dans webapp/platform/client, avec ses types dans webapp/platform/types. La copie dans le dépôt d'Antimatter inclut les points de terminaison d'Antimatter ; le package publié sur npm par Mattermost ne les inclut pas.
package main

import (
	"context"
	"log"

	"github.com/mattermost/mattermost/server/public/model"
)

func main() {
	client := model.NewAPIv4Client("https://chat.example.com")
	client.SetToken("…")
	post, _, err := client.CreatePost(context.Background(), &model.Post{
		ChannelId: "…",
		Message:   "Hello from Go",
	})
	if err != nil {
		log.Fatal(err)
	}
	log.Println("posted", post.Id)
}

Ce qu'Antimatter ajoute à l'API

Ces points de terminaison et champs n'existent pas sur un serveur Mattermost. Tous nécessitent une session.

Nouveaux champs

  • Communautés (Team, et PUT /teams/{team_id}/patch) : all_channels_membership (tout le monde est membre de chaque canal qu'il peut voir, comme dans Discord), default_channel_id (où atterrissent les nouveaux ; vide signifie Town Square), hide_role_colors, require_team_badges, onboarding et autolinks (les deux sont des chaînes JSON).
  • Réponses en ligne : un message avec "props": {"reply_to": "<post id>"} cite ce message du même canal. Ajoutez "reply_to_mention": false pour ne pas notifier son auteur. Le serveur remplit metadata.reply_to avec une brève description du message cité.
  • Spoilers : "props": {"spoiler": true} masque le texte et les fichiers d'un message jusqu'à ce que le lecteur choisisse de les voir.
  • Ignorer et bloquer sont des préférences : catégorie user_block, nommée d'après l'identifiant de l'autre personne, avec la valeur ignore ou block. Savoir si un message personnel attend en tant que demande se trouve dans notify_props.dm_request de votre membre de canal (pending, accepted ou dismissed).
  • Les pièces jointes de messages peuvent contenir des stages et un chart : voir Cartes.
