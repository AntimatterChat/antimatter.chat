Ohne den KI-Verschlüsselungsschlüssel kann ein wiederhergestellter Server die API-Schlüssel seiner Modellverbindungen nicht lesen, und jeder muss erneut eingegeben werden. Bewahren Sie eine Kopie des Schlüssels getrennt von den Datenbank-Backups auf, damit ein gestohlenes Backup nicht beides enthält. Siehe Der Verschlüsselungsschlüssel.

Die Datenbank und die Dateien gehören zusammen: Sichern Sie sie gleichzeitig und bewahren Sie Kopien außerhalb des Servers auf. Die Volumennamen beginnen mit dem Compose-Projektnamen, antimatter (docker volume ls listet sie auf).

Sichern

Aus dem Verzeichnis von compose.yaml. Wenn Antimatter vorher gestoppt wird, ergibt das eine vollständig konsistente Kopie; ein Backup, das während des Betriebs erstellt wird, ist in der Regel in Ordnung, aber Dateien, die während des Backups hochgeladen wurden, können darin fehlen.

stamp=$(date +%Y%m%d-%H%M%S)
mkdir -p backups
docker compose stop antimatter
# Database
docker compose exec -T postgres pg_dump -U antimatter -d antimatter -Fc \
    > "backups/antimatter-db-$stamp.dump"
# File storage, GIF service and the data directory (the AI key file)
for v in files gifs data; do
    docker run --rm -v "antimatter_$v:/data:ro" -v "$PWD/backups:/backup" \
        alpine tar -czf "/backup/antimatter-$v-$stamp.tar.gz" -C /data .
done
docker compose start antimatter
# Secrets
cp .env "backups/env-$stamp"

Wenn Sie AM_AI_ENCRYPTION_KEY nicht festgelegt haben, befindet sich die Schlüsseldatei des Servers im data-Volume, das der obige Loop zusammen mit den Dateien speichert. Besser ist es, den Inhalt in .env zu hinterlegen, wie in Der Verschlüsselungsschlüssel erklärt, und eine Kopie davon getrennt von den Datenbank-Backups aufzubewahren.

Führen Sie es über cron für tägliche Backups aus und kopieren Sie das backups/-Verzeichnis auf einen anderen Rechner. Bewahren Sie die Kopien von .env so sicher auf wie den Server selbst: Sie enthalten dessen Passwörter.

Um die hochgeladenen Dateien stattdessen Objekt für Objekt zu kopieren (z. B. auf einen anderen S3-Speicher), verwenden Sie das AWS-Command-Line-Tool des bucket-Diensts:

docker compose run --rm -v "$PWD/backups/files:/backup" bucket \
    "aws --endpoint-url http://files:9000 s3 sync s3://antimatter /backup"

Bei einem Release-Archiv sichern Sie die Datenbank mit pg_dump -Fc und die Verzeichnisse data/ und config/ mit Ihren üblichen Werkzeugen (data/ enthält die AI-Schlüsseldatei). Bei den Paketen sichern Sie die Datenbank auf die gleiche Weise sowie /etc/antimatter, /var/lib/antimatter, /etc/gifs-server und /var/lib/gifs-server.

Wiederherstellung auf einem neuen Host

Legen Sie compose.yaml, das gespeicherte .env und die Backups in einem neuen Verzeichnis ab, dann:

stamp=20261016-030000          # the backup to restore
docker compose create           # creates the volumes, starts nothing
docker compose up -d postgres
docker compose exec -T postgres pg_restore -U antimatter -d antimatter --no-owner \
    < "backups/antimatter-db-$stamp.dump"
for v in files gifs data; do
    docker run --rm -v "antimatter_$v:/data" -v "$PWD/backups:/backup" \
        alpine tar -xzf "/backup/antimatter-$v-$stamp.tar.gz" -C /data
done
docker compose up -d

Verwenden Sie dasselbe .env: Der Speicher und die Datenbank müssen die Passwörter beibehalten, die sie hatten, und die Modellverbindungen benötigen denselben AI-Verschlüsselungsschlüssel. Wenn der neue Host eine andere Adresse hat, aktualisieren Sie SITE_URL (und DOMAIN).

Testen Sie Ihre Backups, indem Sie sie von Zeit zu Zeit auf einem anderen Rechner wiederherstellen.

Upgrade

Compose-Dateien, die vor dem 17. Oktober 2026 heruntergeladen wurden, hatten kein data-Volume: Die AI-Schlüsseldatei befand sich im Container. Bevor Sie die neue compose.yaml verwenden und .env kein AM_AI_ENCRYPTION_KEY enthält, speichern Sie den vom Server erstellten Schlüssel: echo "AM_AI_ENCRYPTION_KEY=$(docker compose exec -T antimatter cat /antimatter/data/ai-encryption.key)" >> .env. Wenn der Befehl keine Datei findet, hat noch keine Modellverbindung einen Schlüssel gespeichert.
  1. Erstellen Sie ein Backup.
  2. Ändern Sie das Image-Tag in .env (ANTIMATTER_IMAGE), falls Sie eines festlegen, wie empfohlen.
  3. Ziehen Sie das Image und starten Sie neu: 
    docker compose pull
docker compose up -d
docker compose logs -f antimatter

Beim Start aktualisiert der Server das Datenbank-Schema (verfolgen Sie den Fortschritt im Protokoll; bei großen Servern kann dies mehrere Minuten dauern) und installiert die neueren Versionen der mitgelieferten Apps aus dem Image. Bei einem Release-Archiv: Server stoppen, alles außer config/, data/, logs/, plugins/ und client/plugins/ durch den Inhalt des neuen Archivs ersetzen und den Server erneut starten. Bei einem .deb- oder .rpm-Paket: Installieren Sie das neue Paket, wie in Paket aktualisieren beschrieben.

Aktualisierungen sind nur in eine Richtung möglich. Sobald ein neuerer Server die Datenbank aktualisiert hat, kann eine ältere Version sie nicht mehr verwenden: Um zurückzugehen, müssen Sie das Backup wiederherstellen, das vor der Aktualisierung erstellt wurde. Dasselbe gilt für die Rückkehr von antimatter-next zu antimatter.

Versionen

Der Antimatter-Server meldet die Version der Mattermost-Zeile, auf der er basiert (derzeit 12.0.0). Die Releases auf GitHub, mit ihren Archiven und Paketen, haben eigene Versionsnummern, in der 0.9.0-Serie während der Beta: antimatter version zeigt sie als Build-Nummer an. Die Images werden von den main-Branches neu erstellt: antimatter-next jede Nacht (Tags nightly-<YYYYMMDD>) und beide Images bei jeder Änderung (Tags sha-<commit>). Verwenden Sie einen dieser Tags, aktualisieren Sie bewusst und notieren Sie sich den vorherigen Tag, damit Sie wissen, welches Backup dazu passt.

PostgreSQL-Hauptversionen

Die Compose-Datei verwendet postgres:17-alpine. Antimatter benötigt PostgreSQL 15 oder neuer. Eine neue Hauptversion von PostgreSQL kann das Datenverzeichnis der vorherigen Version nicht lesen: Um darauf umzusteigen, erstellen Sie ein Datenbank-Dump, starten Sie die neue Version auf einem neuen Volume und stellen Sie das Dump darin wieder her.

Aktualisierung auf 0.9.0

Der erste Start der Version 0.9.0 (oder eines Images, das ab dem 17. Oktober 2026 erstellt wurde) führt einige einmalige Änderungen an den Daten durch. Jede Änderung wird nur einmal ausgeführt und in der Datenbank protokolliert. Sie bringen das, was bei einem alten Standardwert geblieben ist, auf den neuen Standardwert, und belassen das, was ein Administrator gewählt hat, unverändert. Verfolgen Sie diese Änderungen im Protokoll.

Wenn Antimatter für ein Unternehmen oder eine Organisation gedacht ist, setzen Sie Art der neuen Arbeitsbereiche auf Arbeitsbereich vor dem Upgrade: AM_TEAMSETTINGS_DEFAULTCOMMUNITYKIND=workplace. Das Upgrade weist jedem Arbeitsbereich die Art zu, die diese Einstellung zum Zeitpunkt des Upgrades hat. In Arbeitsbereichen der Art Community sind Anrufe in Kanälen standardmäßig deaktiviert. Siehe Arbeitsbereich oder Community.

Die Dienste der Agents-App

Das Upgrade kopiert jeden KI-Dienst der Agents-App in eine serverweite Modellverbindung, die von jeder Community geteilt und von allen außer Gästen verwendet werden kann (aktivieren Sie Auch Gäste, um dies zu ermöglichen). Die Schlüssel werden dabei verschlüsselt, daher benötigt der Server seinen KI-Verschlüsselungsschlüssel: Bei einem Cluster, dessen Dateien in S3 liegen, muss zuerst AM_AI_ENCRYPTION_KEY gesetzt werden, andernfalls wartet die Kopie auf den nächsten Start. Prüfen Sie anschließend Systemkonsole › KI › Modellverbindungen:

  • Jede Verbindung behält die ID ihres Dienstes bei, sodass die Agenten der App und eine automatische Übersetzung, die auf einen Agents-Dienst eingestellt ist, sie weiterhin finden.
  • OpenAI-, OpenAI-kompatible, Anthropic-, Mistral-, Cohere- und Gemini-Dienste werden zu Verbindungen zu ihrem OpenAI-kompatiblen (bzw. Anthropic-)Endpunkt. Ein Azure-Dienst wird zu einer Verbindung zum OpenAI-kompatiblen Endpunkt der Ressource: Testen Sie dies.
  • AWS Bedrock-, Google Vertex AI- und Cohere North-Dienste sowie unbekannte Typen werden mit Braucht Aufmerksamkeit markiert, zusammen mit dem Grund. Ihre Cloud-Zugangsdaten werden nicht kopiert: Verweisen Sie sie auf den OpenAI-kompatiblen Endpunkt des Anbieters oder auf ein Gateway wie LiteLLM und speichern Sie dann.
  • Der Embedding-Dienst wird zum Embeddings-Modell der Verbindung mit derselben Adresse und demselben Schlüssel oder zu einer eigenen Verbindung. Der Transkriptions-Dienst erhält das whisper-1-Modell.
  • Wenn die Umformulierung und die Zusammenfassungen noch keine Verbindung haben, erhalten sie den Dienst und das Modell des Standardagenten der App.

Die eigenen Einstellungen und Daten der Agents-App bleiben wie sie sind: Ihre Agenten nutzen weiterhin ihre Dienste.

Weitere Änderungen an Standardwerten

  • Calls: Testmodus ist standardmäßig deaktiviert und Video aktivieren ist standardmäßig aktiviert. Eine in der Konfiguration gespeicherte Auswahl wird beibehalten. Calls folgen auch der Art der Community (siehe Calls und Sprache).
  • Nachrichten nach oben zu verschieben ist für die Administratoren des Kanals, die Administratoren und Moderatoren der Community (mit Nachrichten verwalten) vorgesehen. Mitglieder einer Direktnachricht oder Gruppennachricht können dies weiterhin tun.
  • Archivierte Kanäle können neue Mitglieder aufnehmen, die den Verlauf lesen. Niemand kann dort posten, reagieren oder Änderungen vornehmen.

Umzug von Mattermost

Antimatter verwendet das Datenbank-Schema von Mattermost und ergänzt eigene Tabellen, sodass es die PostgreSQL-Datenbank und Dateien eines Mattermost-Servers übernehmen kann. Testen Sie dies zunächst an einer Kopie:

  1. Sichern Sie die Mattermost-Datenbank, den Dateispeicher (data/ oder S3-Bucket) und config.json, und stoppen Sie dann Mattermost.
  2. Stellen Sie die Datenbank in die PostgreSQL-Instanz von Antimatter wieder her oder verweisen Sie Antimatter auf eine Kopie davon (AM_SQLSETTINGS_DATASOURCE).
  3. Kopieren Sie die Dateien in den Speicher von Antimatter, wobei die Pfade beibehalten werden: in den antimatter-Bucket mit einem S3-Tool oder in data/ mit einem Release-Archiv.
  4. Wiederverwenden Sie Ihre Einstellungen: Kopieren Sie config.json oder verschieben Sie es in die Datenbank mit amctl --local config migrate (siehe Konfiguration). Ihre MM_-Umgebungsvariablen funktionieren weiterhin; benennen Sie sie bei Gelegenheit in AM_ um.
  5. Starten Sie Antimatter und beobachten Sie das Protokoll, während die Datenbank aktualisiert wird. Prüfen Sie anschließend Systemkonsole › Plugins › Plugin-Verwaltung. Antimatter installiert eigene Builds von Calls, Playbooks, Kanban (Boards), Agents und Integrationen, wenn diese neuer sind als die installierte Version. Falls Mattermost eine neuere Version einer dieser Apps hatte, entfernen Sie diese App und starten Sie Antimatter neu, damit der eigene Build installiert wird.
  6. Richten Sie Push-Benachrichtigungen erneut ein, mit Ihrem eigenen Push-Proxy: Antimatter sendet keine Benachrichtigungen an die Push-Dienste von Mattermost, weder Test- noch gehostete, da diese nur an die eigenen Apps von Mattermost zugestellt werden. Solange Sie Push-Benachrichtigungs-Server nicht ändern, sendet der Server keine Push-Benachrichtigungen (siehe Push-Benachrichtigungen).

Antimatter kontaktiert keine von Mattermost, Inc. betriebenen Dienste (siehe Verbindungen zu externen Diensten), selbst wenn Ihre Konfiguration noch einen davon angibt:

  • ein Push-Benachrichtigungs-Server bei Mattermost wird in den Einstellungen beibehalten, aber nie verwendet;
  • die Adressen von Mattermost für den App-Marktplatz (Marktplatz-URL) und für Produktmitteilungen werden geleert;
  • die App-Downloadlinks, die die Standardwerte von Mattermost waren (Antimatter Apps Download Page Link, Android-App Downloadlink und iOS-App-Downloadlink), werden durch die Downloadseiten der Antimatter-Apps auf GitHub ersetzt; selbst festgelegte Links bleiben unverändert;
  • die Calls-App verwendet den öffentlichen STUN-Server von Cloudflare anstelle des von Mattermost, ohne die gespeicherte Einstellung zu ändern (siehe Calls);
  • die Sicherheitsaktualisierungsprüfung und das Crash-Reporting wurden entfernt, ebenso wie die zugehörigen Einstellungen in der Systemkonsole (Enable Security Alerts, Enable Diagnostics and Error Reporting) und die Seite Ankündigungen.

Der Socket für den lokalen Modus ist jetzt /var/tmp/antimatter_local.socket; amctl versucht auch den alten /var/tmp/mattermost_local.socket. Mattermost unterstützt in seinen aktuellen Versionen nur noch PostgreSQL, und das tut Antimatter auch: Migrieren Sie zuerst eine MySQL-Datenbank nach PostgreSQL. Wenn Sie nach dem Upgrade der Datenbank durch Antimatter zu Mattermost zurückkehren, müssen Sie Ihr Mattermost-Backup wiederherstellen.

Daten exportieren und importieren

Das Format für Massenexporte verschiebt Daten zwischen Servern: den gesamten Server, bestimmte Communities oder bestimmte Kanäle, einschließlich Anhänge, Profilbilder und benutzerdefinierte Emojis, falls gewünscht.

# on the source server
amctl export create --team-name design --include-profile-pictures
amctl export list
amctl export download <export file> design.zip
# on the destination server
amctl import upload design.zip
amctl import list available
amctl import process <uploaded file> --imported-users active

Beobachten Sie die Jobs mit amctl export job list und amctl import job list. Für einen Community- oder Kanal-Export ist --imported-users erforderlich: active, wenn die Personen auf diesen Server wechseln, inactive, wenn in einen Server importiert wird, in dem sie bereits Konten haben, damit aus unklaren Übereinstimmungen erstellte Konten deaktiviert bleiben, bis ein Administrator sie überprüft. --destination-team-name importiert in eine bestehende Community. Exporte und Importe werden standardmäßig 30 Tage im Speicher des Servers aufbewahrt (ExportSettings.Directory, ImportSettings.Directory).

Auf dem Server selbst führen antimatter export bulk und antimatter import bulk --apply dieselben Vorgänge aus Dateien aus, ohne die API zu verwenden.
