Die Datenbank und die Dateien gehören zusammen: Sichern Sie sie gleichzeitig und bewahren Sie Kopien außerhalb des Servers auf. Die Volumennamen beginnen mit dem Compose-Projektnamen antimatter (docker volume ls listet sie auf).

Sichern

Führen Sie dies aus dem Verzeichnis von compose.yaml aus. Wenn Sie Antimatter vorher stoppen, erhalten Sie eine vollständig konsistente Kopie; eine Sicherung während des Betriebs ist in der Regel in Ordnung, aber während der Sicherung hochgeladene Dateien können darin fehlen.

stamp=$(date +%Y%m%d-%H%M%S)
mkdir -p backups
docker compose stop antimatter
# Database
docker compose exec -T postgres pg_dump -U antimatter -d antimatter -Fc \
    > "backups/antimatter-db-$stamp.dump"
# File storage and GIF service
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data:ro" -v "$PWD/backups:/backup" \
        alpine tar -czf "/backup/antimatter-$v-$stamp.tar.gz" -C /data .
done
docker compose start antimatter
# Secrets
cp .env "backups/env-$stamp"

Führen Sie dies über cron für tägliche Sicherungen aus und kopieren Sie das Verzeichnis backups/ auf einen anderen Rechner. Bewahren Sie die Kopien von .env so sicher auf wie den Server: Sie enthalten dessen Passwörter.

Um die hochgeladenen Dateien stattdessen Objekt für Objekt zu kopieren (z. B. in einen anderen S3-Speicher), verwenden Sie das AWS-Befehlszeilenwerkzeug des bucket-Dienstes:

docker compose run --rm -v "$PWD/backups/files:/backup" bucket \
    "aws --endpoint-url http://files:9000 s3 sync s3://antimatter /backup"

Mit einem Release-Archiv sichern Sie die Datenbank mit pg_dump -Fc und die Verzeichnisse data/ und config/ mit Ihren üblichen Werkzeugen.

Wiederherstellung auf einem neuen Host

Legen Sie compose.yaml, die gespeicherte .env-Datei und die Sicherungen in einem neuen Verzeichnis ab, dann:

stamp=20261016-030000          # the backup to restore
docker compose create           # creates the volumes, starts nothing
docker compose up -d postgres
docker compose exec -T postgres pg_restore -U antimatter -d antimatter --no-owner \
    < "backups/antimatter-db-$stamp.dump"
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data" -v "$PWD/backups:/backup" \
        alpine tar -xzf "/backup/antimatter-$v-$stamp.tar.gz" -C /data
done
docker compose up -d

Verwenden Sie dieselbe .env-Datei: Der Speicher und die Datenbank müssen die Passwörter beibehalten, die sie hatten. Wenn der neue Host eine andere Adresse hat, aktualisieren Sie SITE_URL (und DOMAIN).

Testen Sie Ihre Sicherungen, indem Sie sie von Zeit zu Zeit auf einem anderen Rechner wiederherstellen.

Upgrade

  1. Erstellen Sie eine Sicherung.
  2. Ändern Sie das Image-Tag in .env (ANTIMATTER_IMAGE), falls Sie eines festlegen, wie empfohlen.
  3. Ziehen Sie es ab und starten Sie neu: 
    docker compose pull
docker compose up -d
docker compose logs -f antimatter

Beim Start aktualisiert der Server das Datenbank-Schema (dieser Vorgang wird im Protokoll protokolliert; bei großen Servern kann er mehrere Minuten dauern) und installiert die neueren Versionen der mitgelieferten Apps aus dem Image. Bei einem Release-Archiv: Server stoppen, alles außer config/, data/, logs/, plugins/ und client/plugins/ durch den Inhalt des neuen Archivs ersetzen und den Server erneut starten.

Upgrades sind nur in eine Richtung möglich. Sobald ein neuerer Server die Datenbank aktualisiert hat, kann eine ältere Version sie nicht mehr verwenden: Um zurückzugehen, muss das vor dem Upgrade erstellte Backup wiederhergestellt werden. Dasselbe gilt für den Wechsel von antimatter-next zurück zu antimatter.

Versionen

Der Antimatter-Server meldet die Version der Mattermost-Zeile, auf der er basiert (derzeit 12.0.0). Die Images werden aus den main-Branches neu gebaut: antimatter-next jede Nacht (Tags nightly-<YYYYMMDD>) und beide Images bei jeder Änderung (Tags sha-<commit>). Verwenden Sie einen dieser Tags, führen Sie Upgrades bewusst durch und notieren Sie sich den vorherigen Tag, damit Sie wissen, welches Backup dazu passt.

PostgreSQL-Hauptversionen

Die Compose-Datei verwendet postgres:17-alpine. Antimatter benötigt PostgreSQL 15 oder neuer. Eine neue Hauptversion von PostgreSQL kann das Datenverzeichnis der vorherigen Version nicht lesen: Um zu wechseln, müssen Sie die Datenbank dumpen, die neue Version auf einem neuen Volume starten und den Dump darin wiederherstellen.

Umzug von Mattermost

Antimatter verwendet das Datenbank-Schema von Mattermost und fügt eigene Tabellen hinzu, sodass es die PostgreSQL-Datenbank und Dateien eines Mattermost-Servers übernehmen kann. Testen Sie dies zunächst an einer Kopie:

  1. Sichern Sie die Mattermost-Datenbank, ihren Dateispeicher (data/ oder S3-Bucket) und config.json, und stoppen Sie dann Mattermost.
  2. Stellen Sie die Datenbank in der PostgreSQL-Instanz von Antimatter wieder her oder verweisen Sie Antimatter auf eine Kopie davon (AM_SQLSETTINGS_DATASOURCE).
  3. Kopieren Sie die Dateien in den Speicher von Antimatter, wobei ihre Pfade beibehalten werden: mit einem S3-Tool in den antimatter-Bucket oder mit einem Release-Archiv in data/.
  4. Wiederverwenden Sie Ihre Einstellungen: Kopieren Sie config.json oder verschieben Sie es in die Datenbank mit amctl --local config migrate (siehe Konfiguration). Ihre MM_-Umgebungsvariablen funktionieren weiterhin; benennen Sie sie bei Gelegenheit in AM_ um.
  5. Starten Sie Antimatter und beobachten Sie das Protokoll, während die Datenbank aktualisiert wird. Prüfen Sie anschließend Systemkonsole › Plugins › Plugin-Verwaltung. Antimatter installiert eigene Versionen von Calls, Playbooks, Kanban (Boards), Agents und Integrationen, wenn diese neuer sind als die installierte Version. Falls Mattermost eine neuere Version einer dieser Apps hatte, entfernen Sie diese App und starten Sie Antimatter neu, damit die eigene Version installiert wird.
  6. Richten Sie Push-Benachrichtigungen erneut mit Ihrem eigenen Push-Proxy ein: Antimatter sendet keine Benachrichtigungen an die Push-Dienste von Mattermost (weder Test- noch gehostete), da diese nur an die eigenen Apps von Mattermost zugestellt werden. Solange Sie Push-Benachrichtigungs-Server nicht ändern, sendet der Server keine Push-Benachrichtigungen (siehe Push-Benachrichtigungen).

Antimatter kontaktiert keinen von Mattermost, Inc. betriebenen Dienst (siehe Verbindungen zu externen Diensten), selbst wenn Ihre Konfiguration noch einen solchen angibt:

  • ein Push-Benachrichtigungs-Server bei Mattermost wird in den Einstellungen beibehalten, aber nie verwendet;
  • die Adressen von Mattermost für den App-Marktplatz (Marktplatz-URL) und für Produktankündigungen werden geleert;
  • die Calls-App verwendet den öffentlichen STUN-Server von Cloudflare anstelle des von Mattermost, ohne die gespeicherte Einstellung zu ändern (siehe Calls);
  • die Sicherheitsaktualisierungsprüfung und die Crash-Meldung sind entfernt, ebenso wie deren Einstellungen in der Systemkonsole (Sicherheitswarnungen aktivieren, Diagnose- und Fehlerberichte aktivieren) und die Seite Ankündigungen.

Der Socket für den lokalen Modus ist nun /var/tmp/antimatter_local.socket; amctl versucht auch den alten /var/tmp/mattermost_local.socket. Mattermost unterstützt in seinen neueren Versionen nur noch PostgreSQL, und dies gilt auch für Antimatter: Verschieben Sie eine MySQL-Datenbank zunächst nach PostgreSQL. Wenn Sie nach der Datenbankaktualisierung durch Antimatter zu Mattermost zurückkehren, müssen Sie Ihr Mattermost-Backup wiederherstellen.

Daten exportieren und importieren

Das Format für Massenexporte verschiebt Daten zwischen Servern: den gesamten Server, bestimmte Communities oder bestimmte Kanäle, einschließlich Anhänge, Profilbilder und benutzerdefinierter Emojis, wenn gewünscht.

# on the source server
amctl export create --team-name design --include-profile-pictures
amctl export list
amctl export download <export file> design.zip
# on the destination server
amctl import upload design.zip
amctl import list available
amctl import process <uploaded file> --imported-users active

Beobachten Sie die Jobs mit amctl export job list und amctl import job list. Für einen Export von Communities oder Kanälen ist --imported-users erforderlich: active, wenn die Personen auf diesen Server wechseln, inactive, wenn in einen Server importiert wird, in dem sie bereits Konten haben, damit Konten aus unsicheren Übereinstimmungen deaktiviert bleiben, bis ein Administrator sie überprüft. --destination-team-name importiert in eine bestehende Community. Exporte und Importe werden standardmäßig 30 Tage im Speicher des Servers (ExportSettings.Directory, ImportSettings.Directory) aufbewahrt.

Auf dem Server selbst erledigen antimatter export bulk und antimatter import bulk --apply dasselbe aus Dateien, ohne die API.
