Alapok

  • Alap URL: https://chat.example.com/api/v4. Az alábbi végpontok mind ehhez viszonyítva vannak megadva.
  • Formátum: bemenet és kimenet is JSON, kivéve a fájlfeltöltéseket (multipart). Küldd a Content-Type: application/json fejlécet.
  • Azonosítók: minden objektum rendelkezik egy 26 karakteres id-val. Az idők a Unix-epoch óta eltelt milliszekundumokban vannak megadva (create_at, update_at, delete_at; a 0 azt jelenti, hogy „nem törölve”).
  • A közösségek csapatok: az API teams néven hivatkozik rájuk, team_id azonosítóval.
  • Önmagad: bárhová, ahol a útvonal egy user_id-t vár, a me a bejelentkezett felhasználót jelenti, ahogy a GET /users/me példában is.

A végpontok teljes listája a szerver kódjában található: az útvonalakat a server/channels/api4/*.go fájlokban, a típusokat pedig a server/public/model könyvtárban deklarálják. A repozitórium api/v4/source mappájában található OpenAPI-leírás a Mattermosttól örökölt végpontokat fedi le, nem pedig az Antimatter-hoz hozzáadottakat.

Hitelesítés

Minden kéréshez, a bejelentkezéssel és néhány nyilvános végponttal kivéve, token szükséges az Authorization fejlécben:

curl -H "Authorization: Bearer $TOKEN" https://chat.example.com/api/v4/users/me

Háromféle token fogadott el itt: személyes hozzáférési tokenek, munkamenet-tokenek és OAuth-hozzáférési tokenek. Az Authorization: Token … formátum is elfogadott. A lekérdezési paraméterben (?access_token=) megadott tokenek csak OAuth-hozzáférési tokenek esetén érvényesek.

Személyes hozzáférési tokenek (ajánlott szkriptekhez)

A személyes hozzáférési token a neked cselekszik, nem jár le, hacsak nem adsz meg lejárati dátumot, és bármikor visszavonható. A személyes hozzáférési tokenek alapértelmezés szerint le vannak tiltva:

  1. Egy rendszeradminisztrátor engedélyezi a Személyes hozzáférési tokenek engedélyezése beállítást a Rendszerkonzol › Integrációk › Integrációkezelés menüben (ServiceSettings.EnableUserAccessTokens, AM_SERVICESETTINGS_ENABLEUSERACCESSTOKENS).
  2. Minden olyan felhasználó számára, aki tokeneket hozhat létre, a rendszeradminisztrátor nyissa meg a Rendszerkonzol › Felhasználókezelés › Felhasználók oldalt, válassza a Szerepkörök kezelése lehetőséget a felhasználó menüjében, és pipálja be az Engedélyezze, hogy ez a fiók személyes hozzáférési tokeneket generáljon opciót. A rendszeradminisztrátorok mindig létrehozhatnak tokeneket.
  3. A felhasználó megnyitja a profilját a jobb felső sarokban, majd a Profil és beállítások › Biztonság menüpontot. A Személyes hozzáférési tokenek alatt leírja, mire használja a tokenet, és kiválasztja a Token létrehozása gombot. A token csak egyszer jelenik meg: másolja le.

API-n keresztül: POST /users/{user_id}/tokens a következő testtel: {"description": "backup script", "expires_at": 0} (az expires_at milliszekundumban van megadva; 0 esetén nincs lejárati idő). A válasz token mezője a titok; a id mezővel lehet visszavonni (POST /users/tokens/revoke a {"token_id": "…"} testtel). Parancssorból: amctl token generate <user> <description>.

A rendszeradminisztrátor korlátozhatja a tokenek élettartamát a Személyes hozzáférési token maximális élettartama (nap) beállítással a Rendszerkonzol ugyanazon az oldalán.

Munkamenet-tokenek

A jelszóval történő bejelentkezés egy munkamenet-tokent ad vissza a Token válaszfejlécben, ugyanolyan típusú munkamenetet, amelyet az alkalmazások is használnak:

curl -i -X POST https://chat.example.com/api/v4/users/login \
  -H 'Content-Type: application/json' \
  -d '{"login_id": "maya", "password": "…"}'

Többfaktoros hitelesítéssel rendelkező fiókhoz adjon meg "token": "123456" értéket. A munkamenetek a szerver munkamenet-beállításai szerint járnak le, a bejelentkezési végpont pedig sebességkorlátozott (5 kérés per másodperc). A POST /users/logout lezárja a munkamenetet.

A böngészők cookie-val hitelesítenek. A cookie-val hitelesített kérésnek GET-nél minden más műveletnél el kell küldenie a X-CSRF-Token fejlécet is; az Authorization fejlécben lévő tokenhez nem szükséges CSRF-fejléc.

OAuth 2.0 alkalmazások

Ha azt szeretné, hogy a felhasználók Antimatter-fiókjukkal jelentkezzenek be az Ön alkalmazásába, regisztráljon egy OAuth 2.0 alkalmazást. Ekkor az Antimatter lesz az OAuth-szolgáltató:

  1. Az OAuth 2.0 szolgáltató engedélyezése bekapcsolva kell legyen (Rendszerkonzol › Integrációk › Integrációkezelés, ServiceSettings.EnableOAuthServiceProvider, alapértelmezetten bekapcsolva).
  2. Aki jogosultsággal rendelkezik az OAuth-alkalmazások kezeléséhez (alapértelmezetten a rendszeradminisztrátorok), megnyitja a profilját, majd a Integrációk › OAuth 2.0 alkalmazások menüpontot, és hozzáadja az alkalmazást a visszahívási URL-jeivel. Ilyen módon kap egy kliensazonosítót (client ID) és egy kliens titkot (client secret).
  3. Az alkalmazásod a felhasználókat a https://chat.example.com/oauth/authorize címre irányítja, a response_type=code, client_id, redirect_uri és state paraméterekkel. A code_challenge_method=S256 értékű PKCE támogatott.
  4. A kódot a POST https://chat.example.com/oauth/access_token végponton cseréli be (először grant_type=authorization_code, majd refresh_token megújításához), és a Authorization: Bearer <access token> fejléccel hívja meg a API-t.

A felhasználók a Profil és beállítások › Biztonság › Engedélyezett alkalmazások menüben láthatják az engedélyezett alkalmazásaikat.

Üzenet küldése

curl -X POST https://chat.example.com/api/v4/posts \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"channel_id": "'$CHANNEL_ID'", "message": "Backup finished: **42 GB** in 3 min"}'

Az üzenetek Markdown formátumúak. Üzenetszálban való válaszhoz add meg a "root_id" (a szál első bejegyzése) értékét, fájlokhoz a "file_ids", csatolmányokhoz és egyéb kiegészítőkhöz a "props" mezőt (lásd: Csatolmányok).

Csatorna-azonosító keresése

curl -H "Authorization: Bearer $TOKEN" \
  https://chat.example.com/api/v4/teams/name/lumen-labs/channels/name/ops-alerts

A nevek a csatorna hivatkozásában szereplők: /lumen-labs/channels/ops-alerts.

Lapozás

A listázó végpontok a page (0-tól) és per_page (alapértelmezés szerint 60, maximum 200) paramétereket fogadják el. Kérdezd tovább a következő lapokat, amíg egy lap rövidebb nem lesz, mint a per_page értéke.

A csatorna üzenetei (GET /channels/{channel_id}/posts) szintén elfogadnak since (időpont: minden, ami azóta változott), vagy before és after (bejegyzés-Azonosító) paramétert. Válaszként bejegyzéslistát kapunk: {"order": [IDs, newest first], "posts": {ID: post}, "next_post_id", "prev_post_id"}.

Hibák

A hibák a szokásos HTTP-státuszkódokat használják (400 hibás bemenet, 401 nem bejelentkezve, 403 nem engedélyezett, 404 nem található, 501 funkció kikapcsolva), JSON-testtel:

{
  "id": "api.context.permissions.app_error",
  "message": "You do not have the appropriate permissions.",
  "detailed_error": "",
  "request_id": "jz8zm5nunpbt8f3gpqsz5dq6so",
  "status_code": 403
}

A kódban a id értékét használd: a message a felhasználó nyelvén van lefordítva. A detailed_error csak akkor nem üres, ha a szerver fejlesztői módban fut (ServiceSettings.EnableDeveloper). A szerver adminisztrátorának idézd a request_id értékét: ez szerepel a naplóban.

Kérésekre vonatkozó korlátok

A sebességkorlátozás alapértelmezetten kikapcsolva van. Amikor a rendszeradminisztrátor bekapcsolja (Rendszerkonzol › Környezet › Sebességkorlátozás), minden kliens alapértelmezetten másodpercenként 10 kérést kaphat, 100-as burst-tel, IP-cím vagy felhasználó alapján számolva. A válaszok tartalmazzák a X-RateLimit-Limit, X-RateLimit-Remaining és X-RateLimit-Reset fejlécet; ha a limitet meghaladják, a szerver 429 státuszkóddal válaszol, Retry-After fejléccel, másodpercben. Egyes végpontok, például a bejelentkezés, saját korláttal rendelkeznek, függetlenül a beállításoktól.

Írj olyan szkripteket, amelyek 429 esetén várakoznak és újrapróbálkoznak, és kerüljük a pollinget: a WebSocketet kövesd.

A WebSocket-eseményfolyam

Csatlakozz a wss://chat.example.com/api/v4/websocket címre. A hitelesítés vagy a Authorization: Bearer fejléc használatával történik a csatlakozási kérésben, vagy az első üzenetként küldd el ezt:

{"seq": 1, "action": "authentication_challenge", "data": {"token": "…"}}

A szerver egy hello eseményt küld, majd mindenhez, amit látni engedélyeztek, egy-egy eseményt:

{
  "event": "posted",
  "data": {"channel_id": "…", "channel_type": "O", "post": "{\"id\":\"…\",\"message\":\"Hello\",…}"},
  "broadcast": {"channel_id": "…", "team_id": "", "user_id": "", "omit_users": null},
  "seq": 4
}

Megjegyzés: a data.post a bejegyzés JSON-sztringként. Gyakori események: posted, post_edited, post_deleted, reaction_added, reaction_removed, typing, status_change, user_added, direct_added. Az alkalmazások saját eseményeket küldenek, custom_<app id>_<event> néven.

Akkciókat is küldhetsz, mindegyik növekvő seq értékkel: user_typing {"channel_id", "parent_id"} paraméterekkel, vagy get_statuses. Ha a kapcsolat megszakad, csatlakozz újra, és a since paraméterrel (lásd Lapozás) szerezd be, amit elhagytál.

Az Antimatter hozzáadja az alábbi eseményeket: community_attributes_updated, member_timeouts_updated, post_put_on_top, post_removed_from_top, server_categories_updated, channel_overrides_updated és category_overrides_updated.

Klienskönyvtárak

  • Mehet: model.Client4 a server/public/model könyvtárban (import: github.com/mattermost/mattermost/server/public/model). model.NewAPIv4Client(url), majd client.SetToken(token); model.NewWebSocketClient4(wsURL, token) követi az eseményeket. Az Antimatter saját másolata módszereket ad hozzá a saját végpontjaihoz, például UpdateMessageRequest, PutPostOnTop és ExportChannel.
  • TypeScript: a @mattermost/client Client4 osztálya a webapp/platform/client könyvtárban, a típusok a webapp/platform/types könyvtárban. Az Antimatter repozitóriumban lévő másolat tartalmazza az Antimatter végpontjait; a Mattermost által npm-en publikált csomag nem.
package main

import (
	"context"
	"log"

	"github.com/mattermost/mattermost/server/public/model"
)

func main() {
	client := model.NewAPIv4Client("https://chat.example.com")
	client.SetToken("…")
	post, _, err := client.CreatePost(context.Background(), &model.Post{
		ChannelId: "…",
		Message:   "Hello from Go",
	})
	if err != nil {
		log.Fatal(err)
	}
	log.Println("posted", post.Id)
}

Új mezők

  • Közösségek (Team, és PUT /teams/{team_id}/patch): all_channels_membership (mindenki minden csatornában tag, amelyet láthat, hasonlóan a Discordhoz), default_channel_id (ahová az újak kerülnek; ha üres, az Town Square), hide_role_colors, require_team_badges, onboarding és autolinks (mindkettő JSON-szöveg).
  • Belső válaszok: egy bejegyzés, amelynek "props": {"reply_to": "<post id>"} értéke, idézi a csatorna másik üzenetét. A "reply_to_mention": false hozzáadása esetén a szerző nem kap értesítést. A szerver kitölti a metadata.reply_to mezőt a hivatkozott üzenet rövid leírásával.
  • Spoilerek: a "props": {"spoiler": true} elrejteti a bejegyzés szövegét és fájljait, amíg az olvasó nem dönt úgy, hogy megtekinti őket.
  • Mellőzés és blokkolás beállítások: user_block kategória, a másik személy azonosítója szerint elnevezve, ignore vagy block értékkel. Hogy egy közvetlen üzenet kérésként vár-e, a csatorna-tagod notify_props.dm_request mezőjében látható (pending, accepted vagy dismissed).
  • Üzenet-csatolmányok tartalmazhatnak stages és chart elemeket: lásd Kártyák.
