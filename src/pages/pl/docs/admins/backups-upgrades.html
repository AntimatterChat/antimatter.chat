Baza danych i pliki są ze sobą powiązane: wykonuj ich kopie zapasowe jednocześnie i przechowuj kopie poza serwerem. Nazwy wolumenów zaczynają się od nazwy projektu compose, antimatter (listę wyświetla docker volume ls).

Kopia zapasowa

Z katalogu, w którym znajduje się compose.yaml. Najpierw zatrzymaj Antimatter, aby uzyskać w pełni spójną kopię; kopia wykonana podczas działania jest zwykle w porządku, ale pliki przesłane w trakcie tworzenia kopii mogą w niej brakować.

stamp=$(date +%Y%m%d-%H%M%S)
mkdir -p backups
docker compose stop antimatter
# Database
docker compose exec -T postgres pg_dump -U antimatter -d antimatter -Fc \
    > "backups/antimatter-db-$stamp.dump"
# File storage and GIF service
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data:ro" -v "$PWD/backups:/backup" \
        alpine tar -czf "/backup/antimatter-$v-$stamp.tar.gz" -C /data .
done
docker compose start antimatter
# Secrets
cp .env "backups/env-$stamp"

Uruchamiaj ją z cron dla dziennych kopii zapasowych i kopiuj katalog backups/ na inny komputer. Przechowuj kopie .env tak bezpiecznie jak sam serwer: zawierają jego hasła.

Aby kopiować przesłane pliki obiekt po obiekcie (na przykład do innego magazynu S3), użyj narzędzia wiersza poleceń AWS usługi bucket:

docker compose run --rm -v "$PWD/backups/files:/backup" bucket \
    "aws --endpoint-url http://files:9000 s3 sync s3://antimatter /backup"

W przypadku archiwum wydania, wykonaj kopię zapasową bazy danych za pomocą pg_dump -Fc, a katalogi data/ i config/ za pomocą standardowych narzędzi.

Przywracanie na nowym hoście

Umieść compose.yaml, zapisany .env i kopie zapasowe w nowym katalogu, a następnie:

stamp=20261016-030000          # the backup to restore
docker compose create           # creates the volumes, starts nothing
docker compose up -d postgres
docker compose exec -T postgres pg_restore -U antimatter -d antimatter --no-owner \
    < "backups/antimatter-db-$stamp.dump"
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data" -v "$PWD/backups:/backup" \
        alpine tar -xzf "/backup/antimatter-$v-$stamp.tar.gz" -C /data
done
docker compose up -d

Użyj tego samego .env: magazyn i baza danych muszą zachować swoje hasła. Jeśli nowy host ma inny adres, zaktualizuj SITE_URL (oraz DOMAIN).

Testuj swoje kopie zapasowe, przywracając je od czasu do czasu na innym komputerze.

Aktualizacja

  1. Wykonaj kopię zapasową.
  2. Zmień tag obrazu w .env (ANTIMATTER_IMAGE), jeśli go przypinas, jak zalecane.
  3. Pobierz i uruchom ponownie: 
    docker compose pull
docker compose up -d
docker compose logs -f antimatter

Po uruchomieniu serwer aktualizuje schemat bazy danych (można to śledzić w dzienniku; na dużym serwerze może to potrwać kilka minut) i instaluje nowsze wersje aplikacji dołączonych do obrazu. W przypadku archiwum wydania: zatrzymaj serwer, zastąp wszystko poza config/, data/, logs/, plugins/ i client/plugins/ zawartością nowego archiwum, a następnie uruchom serwer ponownie.

Aktualizacje są wykonywane wyłącznie do przodu. Gdy nowsza wersja serwera zaktualizuje bazę danych, starsza wersja nie może jej już używać: aby wrócić do poprzedniej wersji, przywróć kopię zapaszą wykonaną przed aktualizacją. To samo dotyczy przechodzenia z antimatter-next z powrotem do antimatter.

Wersje

Serwer Antimatter raportuje wersję linii Mattermost, na której jest oparty (obecnie 12.0.0). Obrazy są odbudowywane z gałęzi main: antimatter-next co noc (tagi nightly-<YYYYMMDD>), a oba obrazy przy każdej zmianie (tagi sha-<commit>). Użyj jednego z tych tagów, aktualizuj świadomie i zapisz poprzedni tag, aby wiedzieć, która kopia zapasowa do niego należy.

Główne wersje PostgreSQL

Plik compose używa postgres:17-alpine. Antimatter wymaga PostgreSQL 15 lub nowszego. Nowa główna wersja PostgreSQL nie może odczytać katalogu danych poprzedniej wersji: aby przejść na nową, wykonaj zrzut bazy danych, uruchom nową wersję na nowym wolumenie i przywróć zrzut do niej.

Przejście z Mattermost

Antimatter używa schematu bazy danych Mattermost i dodaje własne tabele, dzięki czemu może przejąć bazę danych PostgreSQL i pliki serwera Mattermost. Najpierw przetestuj to na kopii:

  1. Wykonaj kopię zapasową bazy danych Mattermost, jego magazynu plików (data/ lub bucket S3) oraz config.json, a następnie zatrzymaj Mattermost.
  2. Przywróć bazę danych do PostgreSQL Antimatter lub wskaż Antimatter na jej kopię (AM_SQLSETTINGS_DATASOURCE).
  3. Skopiuj pliki do magazynu Antimatter, zachowując ich ścieżki: do bucketa antimatter za pomocą narzędzia S3 lub do data/ w przypadku archiwum wydania.
  4. Wydaj użycie z ustawień: skopiuj config.json lub przenieś go do bazy danych za pomocą amctl --local config migrate (patrz Konfiguracja). Twoje zmienne środowiskowe MM_ nadal działają; zmień ich nazwę na AM_, gdy to wygodne.
  5. Uruchom Antimatter i obserwuj dziennik podczas aktualizacji bazy danych. Następnie sprawdź Konsola systemu › Wtyczki › Zarządzanie wtyczkami. Antimatter instaluje własne wersje Rozmów, Playbooków, Tablic Kanban, Agentów oraz integracji, gdy są nowsze niż zainstalowana wersja. Jeśli Mattermost miał nowszą wersję jednej z nich, usuń tę aplikację i uruchom ponownie Antimatter, aby zainstalować jego własną wersję.
  6. Skonfiguruj ponownie powiadomienia push, używając własnego serwera pośredniczącego: Antimatter nigdy nie wysyła powiadomień do usług push Mattermost (testowych ani hostowanych), które dostarczają je wyłącznie do własnych aplikacji Mattermost. Dopóki nie zmienisz Serwera powiadomień Push, serwer nie wysyła żadnych powiadomień push (patrz Powiadomienia push).

Antimatter nie kontaktuje się z żadną usługą prowadzoną przez Mattermost, Inc. (zobacz Połączenia z zewnętrznymi usługami), nawet jeśli konfiguracja nadal wskazuje na taką usługę:

  • serwer powiadomień push Mattermost jest przechowywany w ustawieniach, ale nigdy nie jest używany;
  • Adresy Mattermost dla sklepu z aplikacjami (Adres URL sklepu z wtyczkami) oraz dla powiadomień produktowych są wyczyszczone;
  • aplikacja Rozmowy używa publicznego serwera STUN firmy Cloudflare zamiast serwera Mattermost, bez zmiany zapisanego ustawienia (zobacz Rozmowy);
  • sprawdzanie aktualizacji bezpieczeństwa i raportowanie awarii zostały usunięte, wraz z ich ustawieniami w Konsoli systemu (Włącz alerty bezpieczeństwa, Włącz diagnostykę i raportowanie błędów) oraz stroną Powiadomienia.

Gniazdo trybu lokalnego to teraz /var/tmp/antimatter_local.socket; amctl próbuje również starego /var/tmp/mattermost_local.socket. Mattermost wspiera w ostatnich wersjach tylko PostgreSQL, podobnie jak Antimatter: najpierw przenieś bazę danych MySQL do PostgreSQL. Powrót do Mattermost po aktualizacji bazy danych przez Antimatter oznacza przywrócenie kopii zapasowej Mattermost.

Eksport i import danych

Format masowego eksportu przenosi dane między serwerami: cały serwer, niektóre społeczności lub niektóre kanały, wraz z załącznikami, zdjęciami profilowymi i niestandardowymi emoji, jeśli tego chcesz.

# on the source server
amctl export create --team-name design --include-profile-pictures
amctl export list
amctl export download <export file> design.zip
# on the destination server
amctl import upload design.zip
amctl import list available
amctl import process <uploaded file> --imported-users active

Obserwuj zadania za pomocą amctl export job list i amctl import job list. W przypadku eksportu przestrzeni roboczej lub kanału wymagana jest opcja --imported-users: active, gdy użytkownicy przechodzą na ten serwer, oraz inactive, gdy importujesz dane na serwer, na którym już posiadają konta, dzięki czemu konta utworzone z niepewnych dopasowań pozostaną nieaktywne, aż administrator je zweryfikuje. Opcja --destination-team-name umożliwia import do istniejącej przestrzeni roboczej. Eksporty i importy są przechowywane na dysku serwera (ExportSettings.Directory, ImportSettings.Directory) domyślnie przez 30 dni.

Bezpośrednio na serwerze polecenia antimatter export bulk i antimatter import bulk --apply wykonują te same operacje z plików, bez użycia API.
