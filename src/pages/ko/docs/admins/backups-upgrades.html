백업 대상

항목사이트의 compose 파일 사용 시릴리스 아카이브 사용 시
데이터베이스: 메시지, 사용자, 커뮤니티, 채널 및 사이트의 compose 파일 사용 시 설정antimatter_postgres 볼륨, pg_dump를 통해PostgreSQL 데이터베이스
업로드된 파일, 이미지, 설치된 앱antimatter_files 볼륨 (S3 저장소)FileSettings.Directory, 기본값은 ./data/
설정 파일(데이터베이스 내)config/config.json
GIF 및 스티커antimatter_gifs 볼륨GIF 서비스의 데이터 디렉터리
비밀 정보(Secrets).env (및 compose.override.yaml)환경 파일

데이터베이스와 파일은 함께 묶여 있습니다: 동시에 백업하고, 서버 외부에 사본을 보관하세요. 볼륨 이름은 compose 프로젝트 이름인 antimatter로 시작합니다 (docker volume ls로 목록을 볼 수 있습니다).

백업

compose.yaml가 있는 디렉터리에서 실행하세요. Antimatter를 먼저 중지하면 완전히 일관된 사본을 얻을 수 있습니다. 실행 중에 백업하는 것도 일반적으로 문제없지만, 백업 중에 업로드된 파일이 백업에 포함되지 않을 수 있습니다.

stamp=$(date +%Y%m%d-%H%M%S)
mkdir -p backups
docker compose stop antimatter
# Database
docker compose exec -T postgres pg_dump -U antimatter -d antimatter -Fc \
    > "backups/antimatter-db-$stamp.dump"
# File storage and GIF service
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data:ro" -v "$PWD/backups:/backup" \
        alpine tar -czf "/backup/antimatter-$v-$stamp.tar.gz" -C /data .
done
docker compose start antimatter
# Secrets
cp .env "backups/env-$stamp"

cron을 통해 매일 백업하도록 설정하고, backups/ 디렉터리를 다른 기계로 복사하세요. .env의 사본은 서버만큼 안전하게 보관하세요: 비밀번호가 포함되어 있기 때문입니다.

업로드된 파일을 개별로 복사하려면(예: 다른 S3 저장소로), bucket 서비스의 AWS 명령줄 도구를 사용하세요:

docker compose run --rm -v "$PWD/backups/files:/backup" bucket \
    "aws --endpoint-url http://files:9000 s3 sync s3://antimatter /backup"

릴리스 아카이브를 사용하는 경우, 데이터베이스는 pg_dump -Fc로, data/와 config/ 디렉터리는 일반 도구를 사용하여 백업하세요.

새 호스트에 복원

compose.yaml, 저장된 .env 및 백업 파일을 새 디렉터리에 배치한 다음:

stamp=20261016-030000          # the backup to restore
docker compose create           # creates the volumes, starts nothing
docker compose up -d postgres
docker compose exec -T postgres pg_restore -U antimatter -d antimatter --no-owner \
    < "backups/antimatter-db-$stamp.dump"
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data" -v "$PWD/backups:/backup" \
        alpine tar -xzf "/backup/antimatter-$v-$stamp.tar.gz" -C /data
done
docker compose up -d

동일한 .env를 사용하세요: 저장소와 데이터베이스는 이전 비밀번호를 유지해야 합니다. 새 호스트의 주소가 다른 경우 SITE_URL(및 DOMAIN)을 업데이트하세요.

가끔 다른 기계에 백업을 복원하여 백업이 정상 작동하는지 테스트하세요.

업그레이드

  1. 백업을 수행하세요.
  2. 고정(pinned)하는 경우, 권장 사항에 따라 .env의 이미지 태그(ANTIMATTER_IMAGE)를 변경하세요.
  3. 이미지를 가져오고 다시 시작하세요: 
    docker compose pull
docker compose up -d
docker compose logs -f antimatter

시작 시 서버는 데이터베이스 스키마를 업그레이드합니다(로그에서 진행 상황을 확인할 수 있으며, 규모가 큰 서버의 경우 몇 분 정도 소요될 수 있습니다) 그리고 이미지에서 번들된 앱의 최신 버전을 설치합니다. 릴리스 아카이브를 사용하는 경우: 서버를 중지하고, config/, data/, logs/, plugins/, client/plugins/를 제외한 모든 내용을 새 아카이브의 내용으로 교체한 후 다시 시작합니다.

업그레이드는 오직 앞으로만 진행됩니다. 새 버전의 서버가 데이터베이스를 업그레이드한 후에는 이전 버전이 이를 사용할 수 없습니다. 이전 버전으로 되돌리려면 업그레이드 전에 만든 백업을 복원해야 합니다. antimatter-next에서 antimatter로 되돌리는 경우에도 마찬가지입니다.

버전

Antimatter 서버는 기반이 되는 Mattermost 라인(현재 12.0.0)의 버전을 보고합니다. 이미지는 main 브랜치에서 다시 빌드됩니다: antimatter-next는 매일 밤(태그 nightly-<YYYYMMDD>), 두 이미지 모두 변경 사항이 있을 때마다(태그 sha-<commit>). 이러한 태그 중 하나를 고정하고, 의도적으로 업그레이드하며, 어떤 백업이 해당되는지 알 수 있도록 이전 태그를 기록해 두세요.

PostgreSQL 주요 버전

컴포즈 파일은 postgres:17-alpine를 사용합니다. Antimatter에는 PostgreSQL 15 이상이 필요합니다. PostgreSQL의 새 주요 버전은 이전 버전의 데이터 디렉터리를 읽을 수 없습니다. 새 버전으로 이동하려면 데이터베이스를 덤프하고, 새 볼륨에서 새 버전을 시작한 후 덤프를 복원해야 합니다.

Mattermost에서 이동

Antimatter는 Mattermost의 데이터베이스 스키마를 사용하면서 자체 테이블을 추가하므로, Mattermost 서버의 PostgreSQL 데이터베이스와 파일을 인수할 수 있습니다. 먼저 복사본에서 시도해 보세요:

  1. Mattermost 데이터베이스, 파일 저장소(data/ 또는 S3 버킷) 및 config.json를 백업한 후 Mattermost를 중지합니다.
  2. 데이터베이스를 Antimatter의 PostgreSQL로 복원하거나, Antimatter를 해당 데이터베이스의 복사본을 가리키도록 설정합니다(AM_SQLSETTINGS_DATASOURCE).
  3. 파일을 Antimatter의 저장소로 복사하되, 경로를 유지합니다: S3 도구를 사용하여 antimatter 버킷으로, 또는 릴리스 아카이브를 사용하여 data/로 복사합니다.
  4. 설정을 재사용합니다: config.json를 복사하거나, amctl --local config migrate를 사용하여 데이터베이스로 이동합니다(자세한 내용은 설정 참고). MM_ 환경 변수는 계속 작동하며, 편리할 때 AM_으로 이름을 변경할 수 있습니다.
  5. Antimatter를 시작하고 데이터베이스가 업그레이드되는 동안 로그를 확인하세요. 그런 다음 관리자 도구 › 플러그인 › 플러그인 관리를 확인합니다. Antimatter는 설치된 버전보다 새 버전인 경우 Calls, Playbooks, Kanban (Boards), Agents 및 통합 기능의 자체 빌드를 설치합니다. Mattermost에 해당 앱의 더 새 버전이 설치되어 있다면, 해당 앱을 제거하고 Antimatter를 다시 시작하여 Antimatter의 자체 빌드가 설치되도록 하세요.
  6. 자체 푸시 프록시를 사용하여 푸시 알림을 다시 설정하세요. Antimatter는 Mattermost의 푸시 서비스(테스트 또는 호스팅)에 알림을 보내지 않으며, 이 서비스는 Mattermost의 자체 앱에만 전달됩니다. 푸시 알림 서버를 변경할 때까지 서버는 푸시 알림을 보내지 않습니다(자세한 내용은 푸시 알림 참고).

Antimatter는 Mattermost, Inc.가 운영하는 어떤 서비스에도 연결하지 않습니다(자세한 내용은 Connections to outside services 참고). 설정에 해당 서비스가 명시되어 있더라도 마찬가지입니다:

  • Mattermost의 푸시 알림 서버는 설정에 남아있지만 사용되지 않습니다;
  • 앱 마켓플레이스(마켓플레이스 URL) 및 제품 공지사항의 Mattermost 주소가 비워집니다.
  • Calls 앱은 Mattermost의 서버 대신 Cloudflare의 공개 STUN 서버를 사용하며, 저장된 설정은 변경되지 않습니다(자세한 내용은 Calls 참고);
  • 보안 업데이트 확인 및 충돌 보고 기능이 제거되며, 이에 따른 시스템 콘솔 설정(보안 알림 사용, 진단 및 오류 보고 사용)과 공지사항 페이지도 함께 제거됩니다.

로컬 모드 소켓은 이제 /var/tmp/antimatter_local.socket입니다. amctl은 이전의 /var/tmp/mattermost_local.socket도 시도합니다. Mattermost의 최신 버전은 PostgreSQL만 지원하며, Antimatter도 마찬가지입니다: MySQL 데이터베이스를 먼저 PostgreSQL로 이관해야 합니다. Antimatter가 데이터베이스를 업그레이드한 후 Mattermost로 돌아가려면 Mattermost 백업을 복원해야 합니다.

데이터 내보내기 및 가져오기

벌크 내보내기 형식은 서버 간 데이터를 이동합니다. 원할 경우 첨부 파일, 프로필 사진 및 사용자 정의 이모지를 포함하여 서버 전체, 일부 커뮤니티 또는 일부 채널의 데이터를 내보낼 수 있습니다.

# on the source server
amctl export create --team-name design --include-profile-pictures
amctl export list
amctl export download <export file> design.zip
# on the destination server
amctl import upload design.zip
amctl import list available
amctl import process <uploaded file> --imported-users active

amctl export job list와 amctl import job list를 사용하여 작업을 확인하세요. 커뮤니티 또는 채널 내보내기의 경우 --imported-users가 필수입니다. 사람들이 이 서버로 이동하는 경우 active, 이미 계정이 있는 서버로 가져오는 경우 inactive를 사용하세요. 이렇게 하면 불확실한 일치 항목에서 생성된 계정은 관리자가 확인하기 전까지 비활성 상태로 유지됩니다. --destination-team-name를 사용하면 기존 커뮤니티로 가져올 수 있습니다. 내보내기 및 가져오기는 기본적으로 서버 저장소(ExportSettings.Directory, ImportSettings.Directory)에 30일간 보관됩니다.

서버 자체에서는 antimatter export bulk와 antimatter import bulk --apply를 사용하여 API 없이 파일에서 동일한 작업을 수행할 수 있습니다.
