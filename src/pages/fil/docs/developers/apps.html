Paano gumagana ang isang app

  • Ang server part ay isang Go program. Ipinapalaganap nito ng server bilang isang magkakaibang process at nakikipag-usap dito sa pamamagitan ng RPC: tinatawag nito ang mga hooks ng app (may mensahe na magpupost, may binibigay na command…), at tinatawag ng app ang plugin API ng server (gumawa ng post, basahin ang user, i-store ang data…). Maaari rin nitong mag-serve ng mga HTTP routes sa ilalim ng /plugins/<app id>/.
  • Ang web app part ay isang JavaScript bundle na nilalagay sa browser kasama ang web app. Ipinapahanda nito ang mga React components at callbacks sa registry: isang button sa menu, isang panel, o paraan ng pagguhit ng uri ng mensahe.
  • Ang alinman sa bahagi ay opsyonal. Ang isang app ay inii-install bilang .tar.gz bundle, at pinapagana, pinipigil, at pinapaandar nito ng mga system admin.
Ang server part ay tumatatakbo na may buong access sa data ng server. Ituring ang isang app na parang code na idedeploy mo sa server.

Pinapalaganap ng Antimatter ang mga app na nakasulat para sa Mattermost, at sa kabaligtaran, hangga't gumagamit lamang ng mga hooks na mayroon silang pareho. Tingnan ang Mga hooks na Antimatter lang ang mayroon.

Ang layout ng bundle

Wala nang hiwalay na starter template: magsimula mula sa isang maliit na bundled app tulad ng antimatter-plugin-polls o antimatter-plugin-todo, at baguhin ang ID at code nito. Nakalagay ang Polls na ganito:

antimatter-plugin-polls/
├── plugin.json            the manifest
├── Makefile               build, test, bundle, deploy
├── build/                 the manifest and pluginctl helper tools (Go), setup.mk
├── assets/icon.svg        files shipped with the bundle
├── go.mod
├── server/
│   ├── main.go            plugin.ClientMain(&Plugin{})
│   ├── plugin.go          the Plugin type, OnActivate, ServeHTTP
│   ├── manifest.go        generated from plugin.json
│   ├── api.go, command.go, hooks.go, store.go …
│   └── dist/              compiled binaries, one per platform
└── webapp/
    ├── package.json, webpack.config.js, tsconfig.json
    ├── i18n/              en.json and one file per language

    └── dist/main.js       the bundle

Opsyonal: isang public/ folder, na isinaserve nang ganito sa /plugins/<app id>/public/.

  • id: natatangi at permanente; karaniwang reverse domain name. Ito ang nagpapaalam sa mga routes, mga tinatag na setting, at mga WebSocket events.
  • version: semantic version. Ang mga bundled app ay hindi ito ilalagay sa plugin.json; kinukuha nito ng kanilang build tool mula sa pinakabagong v* git tag.
  • min_server_version: Inuulat ng Antimatter ang 12.0.0.
  • settings_schema: ang pahina ng mga setting ng app sa System Console (tingnan ang Mga Setting).

Ang make apply ay kopyahin ang manifest sa server/manifest.go at webapp/src/manifest.ts; ang make manifest-check ay i-verify ito.

Ang bahagi ng server

Ang bahagi ng server ay nag-i-import ng parehong Go module na ginagamit ng mga Mattermost apps, ang github.com/mattermost/mattermost/server/public, mula sa Go module proxy. Ang main nito ay nagpapaanod lamang ng app:

package main

import "github.com/mattermost/mattermost/server/public/plugin"

func main() {
	plugin.ClientMain(&Plugin{})
}

Ang Plugin type ay nag-embed ng plugin.MattermostPlugin, na nagbibigay nito ng p.API, at nag-i-implement ng mga hooks na kailangan nito:

type Plugin struct {
	plugin.MattermostPlugin
	router *mux.Router
}

func (p *Plugin) OnActivate() error {
	p.router = p.newRouter()
	return p.API.RegisterCommand(&model.Command{
		Trigger:          "weather",
		AutoComplete:     true,
		AutoCompleteDesc: "Show the forecast",
		AutoCompleteHint: "[city]",
	})
}

func (p *Plugin) ExecuteCommand(c *plugin.Context, args *model.CommandArgs) (*model.CommandResponse, *model.AppError) {
	city := strings.TrimSpace(strings.TrimPrefix(args.Command, "/weather"))
	return &model.CommandResponse{
		ResponseType: model.CommandResponseTypeEphemeral,
		Text:         "Forecast for " + city + ": sunny",
	}, nil
}

func (p *Plugin) ServeHTTP(c *plugin.Context, w http.ResponseWriter, r *http.Request) {
	p.router.ServeHTTP(w, r)
}

Mga karaniwang hooks

HookKapag tumatakbo
OnActivate, OnDeactivateKapag na-enable o na-disable ang app, at kapag nagpapaanod at nagpapatigil ang server. I-register ang mga command at bot sa OnActivate.
OnConfigurationChangeKapag nagbago ang mga setting nito; i-load ang mga ito gamit ang p.API.LoadPluginConfiguration(&cfg).
ServeHTTPMga request sa /plugins/<app id>/…. I-set ng server ang Mattermost-User-Id header kapag mula sa naka-sign-in na user ang request; tanggihan ang mga request na wala ito maliban kung pampubliko ang layunin nito.
ExecuteCommandIsang command na naka-register ng app ay tinakbo.
MessageWillBePosted, MessageWillBeUpdatedBago ma-save ang mensahe: ibalik ang binagong post, o isang dahilan para itanggihan.
MessageHasBeenPosted, MessageHasBeenUpdated, MessageHasBeenDeletedPagkatapos ng gawa, para sa mga side effects.
ReactionHasBeenAdded, ReactionHasBeenRemovedMga Reaksyon.
UserHasJoinedChannel, UserHasLeftChannel, UserHasJoinedTeam, UserHasLeftTeam, ChannelHasBeenCreatedMga pagbabago sa membership at channel. Ang team ay isang komunidad.
FileWillBeUploadedBago ma-store ang file: baguhin o tanggihan ito.
OnPluginClusterEventMensahe mula sa parehong app sa ibang server ng cluster.

Ang buong listahan, kasama ang eksaktong signatures, ay nasa server/public/plugin/hooks.go; ang API ay nasa server/public/plugin/api.go. Ang pluginapi package (server/public/pluginapi) ay nag-wrap ng API sa mas magaan na mga helper.

Mga kapaki-pakinabang na tawag sa API

  • CreatePost, UpdatePost, SendEphemeralPost: mag-post bilang bot ng app o bilang user.
  • EnsureBotUser(&model.Bot{Username, DisplayName}): gumawa ng bot ng app isang beses at kunin ang ID nito.
  • PublishWebSocketEvent("poll_updated", payload, &model.WebsocketBroadcast{ChannelId: id}): magpadala ng event sa web app. Darating ito bilang custom_<app id>_poll_updated.
  • OpenInteractiveDialog: buksan ang dialog.
  • LogInfo, LogError at mga katulad nito: mag-write sa server log, may tag ng ID ng app.
  • GetUser, GetChannel, HasPermissionToChannel: suriin kung sino ang maaaring gawin bago kumilos para sa isang user.

Ang app ay tumatakbo sa bawat server ng cluster. Iimbak ang state sa key-value store o database, hindi lamang sa memory.

Pag-iimbak ng data

May sariling key-value store ang bawat app sa database ng server:

  • KVSet(key, value), KVGet(key), KVDelete(key): ang mga value ay bytes, karaniwang JSON. Ang mga key ay hindi higit sa 150 character.
  • KVSetWithExpiry(key, value, seconds): nawawala ang value pagkatapos ng oras na iyon.
  • KVCompareAndSet(key, old, new) at KVSetWithOptions na may Atomic: ligtas na pag-update kapag maraming request o server ang sumusulat sa parehong key. Ginagawa ng Polls ang pag-save ng bawat boto gamit ang paraan na ito, at nagre-retry sa pagkakaroon ng conflict.
  • KVList(page, perPage): ang mga key, pahina-pahina.

Ang bahagi ng web app

Nagre-register ang bundle ng isang class gamit ang window.registerPlugin. Ang kanyang initialize ay tumatanggap ng registry at Redux store:

import manifest from './manifest';

class Plugin {
    initialize(registry, store) {
        registry.registerTranslations((locale) => translationsFor(locale));
        registry.registerPostTypeComponent('custom_poll', PollPost);
        registry.registerWebSocketEventHandler(`custom_${manifest.id}_poll_updated`, (msg) => {
            store.dispatch(pollUpdated(JSON.parse(msg.data.poll)));
        });
        registry.registerReconnectHandler(() => store.dispatch(reloadPolls()));
    }
}

window.registerPlugin(manifest.id, new Plugin());
  • Mga shared library. Nagbibigay ang web app ng React, ReactDOM, Redux, React Redux, at React Intl: ilista ang mga ito bilang webpack externals (React, ReactDOM, Redux, ReactRedux, ReactIntl) sa halip na mag-bundle ng sariling kopya. Tingnan ang webpack.config.js ng Polls.
  • Pag-tawag sa iyong bahagi ng server. Gamitin ang ${window.basename}/plugins/<app id>/… kasama ang mga opsyon mula sa Client4.getOptions() (mula sa mattermost-redux/client): dala nila ang mga header na kailangan ng server upang tanggapin ang request mula sa browser.
  • Iyong sariling state. Ang registerReducer ay nagdadagdag ng reducer, na nakaimbak sa ilalim ng state['plugins-<app id>'].
  • Mga type. Ang mga karagdagang registry method ng Antimatter ay wala sa mga published type ng Mattermost: inideklara ng Polls ang registry na ginagamit nito sa webapp/src/types/host.ts.

Ang mga method ng registry at ang kanilang mga parameter ay nakadokumento sa code, sa webapp/fusion/src/plugins/registry.ts (Fusion) at webapp/channels/src/plugins/registry.ts (classic).

Suportahan ang interface ng Fusion

May dalawang web interface ang Antimatter: ang Fusion, na default, at ang classic. Parehong naglo-load ng parehong app bundles at may parehong registry, ngunit ang Fusion ay nagdudraw ng maraming bagay sa sarili at nagpupunta ng plugin components sa kanyang paraan. Subukan ang iyong app sa parehong interface.

Pagtuklas ng interface

Bago mag-load ang anumang app, inilalagay ng parehong interface ang window.antimatterWebUI sa 'fusion' o 'classic', at ang parehong value sa root element ng page bilang data-am-web-ui. Sa Mattermost, wala sa dalawa ang inilalagay.

export function isFusionUI(): boolean {
    return window.antimatterWebUI === 'fusion' || document.documentElement.dataset.amWebUi === 'fusion';
}

Ginagamit ng mga bundled na app ang ito upang mag-iba sa pagguhit. Ang Polls ay nagguhit ng mga poll card nito at ng dialog ng paglikha nito sa estilo ng Fusion, at binubuksan ang sariling dialog para sa /poll sa loob ng Fusion. Ang mga Call at Voice channel ay iniiwasan ang sidebar at toast components na pinapalit ng Fusion sa sariling call interface nito. Ang Agents app ay inilalagay ang mga AI action nito sa isang submenu ng menu ng mensahe, sa halip sa hover toolbar. Ang mga sariling CSS class ng Fusion (may prefix na am-) at ang dialog layer nito (ang am-layer element) ang ginagamit ng mga app na ito upang tumugma sa interface; hindi ito isang naka-document at stable na API.

Ang hindi ipinapakita o binubuhos ng Fusion

  • Ang registerPostDropdownMenuComponent (isang component sa menu ng mensahe), registerPostCardTypeComponent (isang card ng post sa kanang panel) at registerProductSwitcherMenuItem ay hindi ipinapakita sa mga pangunahing view ng Fusion. Gamitin ang registerPostDropdownMenuAction sa halip ng unang bahagi.
  • Ang registerMessageWillBeUpdatedHook ay hindi gumagana kapag na-edit ang mensahe sa Fusion. Suriin ang mga edit sa server gamit ang MessageWillBeUpdated hook sa halip.
  • Ang registerActionAfterChannelCreation ay tumatakbo lamang mula sa klasikong channel creation dialog, na binubuksan ng Fusion mula sa Iba pang opsyon… sa kanyang Gumawa ng channel dialog.
  • Ipinapakita ang mga component ng app bar kahit anong supportedProductIds nila.
  • Ang mga route mula sa registerNeedsTeamRoute at registerCustomRoute ay pananatili ang klasikong frame ng pahina, tulad ng mga produkto.

Mga hook na Antimatter lamang ang mayroon

Ang mga registry method na ito ay wala sa Mattermost. Siguraduhing mayroon ang method bago ito tumawag, upang gumana rin ang app doon:

Mga Setting

Ang settings_schema sa plugin.json ay naglalarawan ng pahina ng app sa System Console › Mga Plugin:

"settings_schema": {
  "header": "Forecasts come from the weather service below.",
  "settings": [
    {"key": "ServiceURL", "display_name": "Service URL", "type": "text", "default": "https://api.example.com"},
    {"key": "Units", "display_name": "Units", "type": "dropdown", "default": "metric",
     "options": [{"display_name": "Celsius", "value": "metric"}, {"display_name": "Fahrenheit", "value": "imperial"}]},
    {"key": "EnableAlerts", "display_name": "Severe weather alerts", "type": "bool", "default": false,
     "help_text": "Post alerts in the channels that follow a city."}
  ]
}

Mga uri ng setting: bool, text, longtext, number, dropdown, radio, generated (isang random secret), username, at custom (ginagawa ng isang component na narehistro ng web app part gamit ang registerAdminConsoleCustomSetting). Maaaring i-group ang mga setting sa mga sections.

Binabasa ng server part ang mga ito sa isang struct na ang mga field ay tumutugma sa mga key:

type configuration struct {
	ServiceURL   string
	Units        string
	EnableAlerts bool
}

func (p *Plugin) OnConfigurationChange() error {
	var cfg configuration
	if err := p.API.LoadPluginConfiguration(&cfg); err != nil {
		return err
	}
	p.setConfiguration(&cfg)
	return nil
}

Maaari ring itakda ng mga Admin ang mga ito sa configuration, sa ilalim ng PluginSettings.Plugins.<app id>, na may mga key na nasa lower case (tingnan ang admin guide).

Mga Pagsasalin

Isinalin ang Antimatter sa 37 wika, pati na rin ang mga bundled apps. Ginagawa ito ng web app part sa ganitong paraan:

  1. Isulat ang bawat string gamit ang React Intl, na may ID at kanyang English text: <FormattedMessage id='polls.create' defaultMessage='Create a poll'/> o defineMessages. Ilagay ang pangalan ng app sa simula ng mga ID.
  2. I-extract ang mga English string sa webapp/i18n/en.json (gamit ng mga bundled apps ang formatjs extract).
  3. Magdagdag ng isang file bawat wika sa tabi nito, na may parehong mga ID: fr.json, de.json, pt-BR.json, zh-CN.json…
  4. Ibigay ito sa web app, na humihingi ng wika ng user: 
    import fr from '../i18n/fr.json';
import ptBR from '../i18n/pt-BR.json';

const catalogs = {fr, 'pt-BR': ptBR};

export function translationsFor(locale) {
    return catalogs[locale] || catalogs[locale.split('-')[0]] || {};
}

registry.registerTranslations(translationsFor);

Ang nawawalang string ay bumabalik sa English defaultMessage. Para sa mga string na ipinapadala ng server part (mga sagot ng command, mga mensahe ng bot), ang pluginapi/i18n package ay naglo-load ng mga translation file na kasama sa bundle (halimbawa, assets/i18n) at nagbibigay ng localizer sa wika ng bawat user.

Pagbuo, pag-install, at pag-debug

Kailangan mo ng Go at Node.js (ang bersyon sa .nvmrc ng app). Sa folder ng app:

CommandGinagawa nito
make distNagbu-build ng server part para sa bawat platform at ng web app part, at isinusulat ang bundle sa dist/<app id>-<version>.tar.gz.
make testNagpapatakbo ng mga Go at JavaScript tests.
make check-styleNag-lint ng code (golangci-lint, ESLint) at tinutukoy ang mga TypeScript types.
make deployNagbu-build, tapos nag-install at nag-activate ng bundle sa server.
make watch, make deploy-from-watchAng unang nagbu-build ng web app part bawat pag-save; ang pangalawa ay nag-bundle ng nabuo at nag-install nito sa server.
make enable, make disable, make resetI-activate, i-disable, o i-restart ang app sa server.
make logs, make logs-watchIpakita ang mga linya ng app sa server log.
make attachNakakabit ng Delve debugger sa tumatakbo na server part (buuin muna gamit ang AM_DEBUG=1).

Ang make deploy at ang ibang server commands ay gumagamit ng local mode socket kapag may natagpuan (/var/tmp/antimatter_local.socket, o AM_LOCALSOCKETPATH): itakbo ito sa makina ng server na may local mode. Kung wala, mag-sign-in sila sa server na ibinigay ng MM_SERVICESETTINGS_SITEURL gamit ang AM_ADMIN_TOKEN, o AM_ADMIN_USERNAME at AM_ADMIN_PASSWORD. Hindi pa binabasa ng mga build tools ang AM_ name para sa site URL.

Mag-install ng bundle sa pamamagitan ng kamay

  • Pinapayagan ng system admin ang mga upload gamit ang AM_PLUGINSETTINGS_ENABLEUPLOADS=true (naka-off sa default; wala itong System Console switch).
  • Pagkatapos ay System Console › Mga Plugin › Pamamahala ng Plugin › Mag-upload ng Plugin, o amctl plugin add weather.tar.gz na sinundan ng amctl plugin enable com.example.weather.
  • Kung naka-on ang Kinakailangan ng Plugin Signature sa server, tinatanggap nito lamang ang mga bundle na firmahan ng isang key na pinagkakatiwalaan nito; tingnan ang Pag-install ng ibang mga app.
Para sa mabilis na pag-iterate sa development server, itakda ang AM_SERVICESETTINGS_ENABLEDEVELOPER=true sa server: ang mga error ay may kasamang detalye. Ang mga Makefile ng mga bundled apps ay nagbu-build ng server part para sa iyong platform lamang kapag naka-set ang MM_SERVICESETTINGS_ENABLEDEVELOPER sa iyong shell.
