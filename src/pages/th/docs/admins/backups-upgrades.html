สิ่งที่ต้องสำรอง

รายการด้วยไฟล์ compose ของไซต์ด้วยอาร์ไคฟ์เวอร์ชันโดยใชแพ็กเกจ .deb หรือ .rpm
ฐานข้อมูล: ข้อความ, ผู้ใช้, ชุมชน, ช่อง และ (เมื่อใช้ไฟล์ compose ของไซต์) การตั้งค่าโวลุ่ม antimatter_postgres ผ่าน pg_dumpฐานข้อมูล PostgreSQL ของคุณฐานข้อมูล PostgreSQL ของคุณ
ไฟล์ที่อัปโหลด, รูปภาพ และแอปที่ติดตั้งโวลุ่ม antimatter_files (ที่เก็บข้อมูล S3)FileSettings.Directory, ค่าเริ่มต้นคือ ./data//var/lib/antimatter
ไฟล์การตั้งค่า(ในฐานข้อมูล)config/config.json/etc/antimatter/config/config.json
GIF และสติ๊กเกอร์โวลุ่ม antimatter_gifsไดเรกทอรีข้อมูลของบริการ GIF/var/lib/gifs-server
ข้อมูลลับ (Secrets).env (และ compose.override.yaml)ไฟล์ environment ของคุณ/etc/antimatter/antimatter.env, /etc/gifs-server
คีย์การเข้ารหัส AI ซึ่งใช้เข้ารหัสคีย์ของโมเดลที่เชื่อมต่อAM_AI_ENCRYPTION_KEY ใน .env (แนะนำ) หรือไฟล์ ai-encryption.key ในโวลุ่ม antimatter_dataAM_AI_ENCRYPTION_KEY หรือ data/ai-encryption.keyAM_AI_ENCRYPTION_KEY ใน antimatter.env หรือ /var/lib/antimatter/data/ai-encryption.key

หากไม่มีคีย์การเข้ารหัส AI เซิร์ฟเวอร์ที่กู้คืนมาจะไม่สามารถอ่านคีย์ API ของโมเดลที่เชื่อมต่อได้ และต้องพิมพ์คีย์เหล่านั้นใหม่อีกครั้ง จดสำเนาคีย์ไว้แยกต่างหากจากแบ็กอัพของฐานข้อมูล เพื่อไม่ให้แบ็กอัพที่ถูกขโมยเพียงชุดเดียวมีทั้งฐานข้อมูลและคีย์การเข้ารหัส ดู คีย์การเข้ารหัส

ฐานข้อมูลและไฟล์ต้องไปด้วยกัน: สำรองพร้อมกัน และเก็บสำเนาไว้ภายนอกเซิร์ฟเวอร์ ชื่อโวลุ่มขึ้นต้นด้วยชื่อโปรเจกต์ compose, antimatter (ดูรายการด้วย docker volume ls)

สำรองข้อมูล

จากไดเรกทอรีของ compose.yaml การหยุด Antimatter ก่อนจะให้สำเนาที่สอดคล้องกันสมบูรณ์; การสำรองขณะทำงานมักไม่เป็นไร แต่ไฟล์ที่อัปโหลดระหว่างสำรองอาจขาดหาย

stamp=$(date +%Y%m%d-%H%M%S)
mkdir -p backups
docker compose stop antimatter
# Database
docker compose exec -T postgres pg_dump -U antimatter -d antimatter -Fc \
    > "backups/antimatter-db-$stamp.dump"
# File storage, GIF service and the data directory (the AI key file)
for v in files gifs data; do
    docker run --rm -v "antimatter_$v:/data:ro" -v "$PWD/backups:/backup" \
        alpine tar -czf "/backup/antimatter-$v-$stamp.tar.gz" -C /data .
done
docker compose start antimatter
# Secrets
cp .env "backups/env-$stamp"

หากคุณยังไม่ได้ตั้งค่า AM_AI_ENCRYPTION_KEY ไฟล์คีย์ของเซิร์ฟเวอร์จะอยู่ในโวลุ่ม data ซึ่งลูปด้านบนจะบันทึกไว้พร้อมกับไฟล์อื่นๆ วิธีที่ดีกว่าคือ นำเนื้อหาของมันไปใส่ใน .env ตามที่อธิบายไว้ใน คีย์การเข้ารหัส และจดสำเนาไว้แยกต่างหากจากแบ็กอัพของฐานข้อมูล

รันผ่าน cron เพื่อสำรองรายวัน และคัดลอกไดเรกทอรี backups/ ไปยังเครื่องอื่น เก็บสำเนาของ .env ให้ปลอดภัยเท่าเซิร์ฟเวอร์: เพราะมีรหัสผ่านอยู่ในนั้น

หากต้องการคัดลอกไฟล์ที่อัปโหลดเป็นรายอ็อบเจกต์ (เช่น ไปยังที่เก็บ S3 อื่น) ใช้เครื่องมือ command-line ของ AWS ของบริการ bucket:

docker compose run --rm -v "$PWD/backups/files:/backup" bucket \
    "aws --endpoint-url http://files:9000 s3 sync s3://antimatter /backup"

เมื่อใช้อาร์ไคฟ์ของเวอร์ชันที่เผยแพร่ ให้สำรองฐานข้อมูลด้วย pg_dump -Fc และไดเรกทอรี data/ และ config/ ด้วยเครื่องมือที่คุณใช้เป็นประจำ (data/ มีไฟล์คีย์ AI) เมื่อใช้แพ็กเกจ ให้สำรองฐานข้อมูลด้วยวิธีเดียวกัน และ /etc/antimatter, /var/lib/antimatter, /etc/gifs-server และ /var/lib/gifs-server

กู้คืนบนโฮสต์ใหม่

วาง compose.yaml, .env ที่บันทึกไว้ และไฟล์สำรองในไดเรกทอรีใหม่ จากนั้น:

stamp=20261016-030000          # the backup to restore
docker compose create           # creates the volumes, starts nothing
docker compose up -d postgres
docker compose exec -T postgres pg_restore -U antimatter -d antimatter --no-owner \
    < "backups/antimatter-db-$stamp.dump"
for v in files gifs data; do
    docker run --rm -v "antimatter_$v:/data" -v "$PWD/backups:/backup" \
        alpine tar -xzf "/backup/antimatter-$v-$stamp.tar.gz" -C /data
done
docker compose up -d

ใช้ .env เดิม: การเก็บข้อมูลและฐานข้อมูลต้องยังคงรหัสผ่านที่มีอยู่ และโมเดลที่เชื่อมต่อต้องการคีย์การเข้ารหัส AI เดิม หากโฮสต์ใหม่มีที่อยู่ (address) ที่ต่างออกไป ให้ปรับปรุง SITE_URL (และ DOMAIN)

ทดสอบการสำรองข้อมูลของคุณโดยกู้คืนบนเครื่องอื่นเป็นครั้งคราว

อัปเกรด

ไฟล์ Compose ที่ดาวน์โหลดก่อนวันที่ 17 ตุลาคม 2026 ไม่มีโวลุ่ม data: ไฟล์คีย์ AI อยู่ในคอนเทนเนอร์ ก่อนที่คุณจะใช้ compose.yaml ใหม่ และหาก .env ไม่มี AM_AI_ENCRYPTION_KEY ให้บันทึกคีย์ที่เซิร์ฟเวอร์สร้างไว้: echo "AM_AI_ENCRYPTION_KEY=$(docker compose exec -T antimatter cat /antimatter/data/ai-encryption.key)" >> .env หากคำสั่งไม่พบไฟล์ แสดงว่ายังไม่มีโมเดลที่เชื่อมต่อใดบันทึกคีย์ไว้
  1. สำรองข้อมูล
  2. เปลี่ยนแท็กของ image ใน .env (ANTIMATTER_IMAGE) หากคุณตรึงเวอร์ชันไว้ ตามคำแนะนำ
  3. ดึงและรีสตาร์ท: 
    docker compose pull
docker compose up -d
docker compose logs -f antimatter

เมื่อเริ่มทำงาน เซิร์ฟเวอร์จะอัปเกรดโครงสร้างฐานข้อมูล (ติดตามความคืบหน้าในบันทึก; เซิร์ฟเวอร์ขนาดใหญ่อาจใช้เวลาหลายนาที) และติดตั้งเวอร์ชันใหม่กว่าของแอปที่รวมอยู่ในภาพ (image) สำหรับอาร์ไคฟ์ของเวอร์ชัน: หยุดเซิร์ฟเวอร์ แทนที่ทุกอย่างยกเว้น config/, data/, logs/, plugins/ และ client/plugins/ ด้วยเนื้อหาจากอาร์ไคฟ์ใหม่ จากนั้นเริ่มเซิร์ฟเวอร์อีกครั้ง สำหรับแพ็กเกจ .deb หรือ .rpm ให้ติดตั้งแพ็กเกจใหม่ตามที่อธิบายไว้ใน การอัปเกรดแพ็กเกจ

การอัปเกรดทำได้เฉพาะไปข้างหน้าเท่านั้น เมื่อเซิร์ฟเวอร์เวอร์ชันใหม่กว่าอัปเกรดฐานข้อมูลแล้ว เวอร์ชันเก่าจะไม่สามารถใช้งานฐานข้อมูลนั้นได้: หากต้องการย้อนกลับ ให้กู้คืนแบ็กอัพที่สร้างไว้ก่อนการอัปเกรด ข้อนี้ใช้กับการย้ายจาก antimatter-next กลับไป antimatter เช่นกัน

เวอร์ชัน

เซิร์ฟเวอร์ของ Antimatter จะรายงานเวอร์ชันของสาย Mattermost ที่ใช้เป็นฐาน (ปัจจุบันคือ 12.0.0) การเผยแพร่บน GitHub ซึ่งประกอบด้วยอาร์ไคฟ์และแพ็กเกจ จะมีหมายเลขเวอร์ชันของตัวเอง ในซีรีส์ 0.9.0 ในช่วงเบต้า: antimatter version จะแสดงเป็น เลขที่บิลด์ ภาพ (images) จะถูกสร้างใหม่จากสาขา main: antimatter-next ทุกคืน (แท็ก nightly-<YYYYMMDD>) และทั้งสองภาพเมื่อมีการเปลี่ยนแปลง (แท็ก sha-<commit>) กำหนด (pin) แท็กเหล่านี้ไว้ อัปเกรดอย่างมีเจตนา และจดบันทึกแท็กเวอร์ชันก่อนหน้าไว้เพื่อให้ทราบว่าการสำรองข้อมูล (backup) ตัวใดตรงกับเวอร์ชันนั้น

เวอร์ชันหลักของ PostgreSQL

ไฟล์ compose ใช้ postgres:17-alpine Antimatter ต้องการ PostgreSQL 15 หรือใหม่กว่า เวอร์ชันหลักใหม่ของ PostgreSQL ไม่สามารถอ่านไดเรกทอรีข้อมูลของเวอร์ชันก่อนหน้าได้: หากต้องการย้ายไปเวอร์ชันใหม่ ให้ทำ dump ฐานข้อมูล เริ่มเวอร์ชันใหม่บนโวลุ่มใหม่ และกู้คืน dump เข้าไป

การอัปเกรดเป็น 0.9.0

การเริ่มทำงานครั้งแรกของเวอร์ชัน 0.9.0 (หรือของภาพที่สร้างจากวันที่ 17 ตุลาคม 2026 เป็นต้นไป) จะทำการเปลี่ยนแปลงครั้งเดียว (one-time) กับข้อมูลหลายอย่าง แต่ละขั้นตอนจะทำงานเพียงครั้งเดียว และถูกบันทึกไว้ในฐานข้อมูล การเปลี่ยนแปลงเหล่านี้จะนำค่าที่ตั้งค่าเริ่มต้นไว้เดิมมาปรับเป็นค่าเริ่มต้นใหม่ และจะไม่แตะต้องค่าที่ผู้ดูแลระบบได้เลือกไว้ ติดตามความคืบหน้าในบันทึก (log)

หาก Antimatter ใช้สำหรับบริษัทหรือองค์กร ให้ตั้งค่า ประเภทของชุมชนใหม่ เป็น ที่ทำงาน ก่อนที่คุณจะอัปเกรด: AM_TEAMSETTINGS_DEFAULTCOMMUNITYKIND=workplace การอัปเกรดจะกำหนดประเภทนี้ให้กับทุกชุมชนตามค่าของตัวแปรนี้ ณ ขณะนั้น และการโทร (calls) จะถูกปิดไว้โดยค่าเริ่มต้นในช่องของชุมชนที่มีประเภทเป็น ชุมชน ดู ที่ทำงานหรือชุมชน
รายการการเปลี่ยนแปลง
ประเภทของชุมชนทุกชุมชนจะมีประเภท ชุมชน หรือ ที่ทำงาน: ค่านั้นคือค่าของ ประเภทของชุมชนใหม่ (TeamSettings.DefaultCommunityKind) ณ การเริ่มทำงานครั้งแรก ประเภทที่ตั้งไว้แล้วจะถูกรักษาไว้ ผู้ดูแลชุมชนสามารถเปลี่ยนประเภทของชุมชนของตนได้ภายหลัง ใน การตั้้งค่าทีม › ช่อง › ประเภทของชุมชน
ใครเป็นผู้เก็บถาวรช่องสมาชิกรวมถึงผู้ดูแลระบบของชุมชน (community) ไม่สามารถเก็บถาวร (archive) ช่อง (channel) ที่ตนเองเป็นสมาชิกได้อีกต่อไป แต่ผู้ดูแลระบบของชุมชน (community admin) สามารถทำได้ ในสภาพแวดล้อมการทำงาน (workplace) ผู้ดูแลระบบของช่อง (channel admin) (ผู้ที่สร้างช่อง และผู้ที่ถูกแต่งตั้งเป็นผู้ดูแลระบบ) สามารถเก็บถาวรช่องนั้นได้เช่นกัน การเปลี่ยนแปลงนี้ส่งผลต่อบทบาท (role) ของระบบ (system scheme) แต่สคีมาการอนุญาต (permission scheme) ที่ผู้ดูแลระบบของระบบ (system administrator) สร้างไว้สำหรับชุมชนบางชุมชนยังคงเหมือนเดิม
บทบาท (role) ผู้ดูแล (Moderators) ของชุดค่าเริ่มต้นของเลย์เอาต์ (layout preset)บทบาท (role) ผู้ดูแล (Moderators) ที่ชุมชน (community) ได้รับจากชุดค่าเริ่มต้นของเลย์เอาต์ (layout preset) จะได้รับสิทธิ์ นำคนออก (Remove people) ซึ่งจำเป็นสำหรับการบังคับให้คนออกและนำคนออก เฉพาะบทบาท (role) ที่ยังคงเหมือนเดิมตามที่ชุดค่าเริ่มต้นของเลย์เอาต์ (layout preset) กำหนดไว้เท่านั้นที่จะมีการเปลี่ยนแปลง ส่วนบทบาท (role) ที่บุคคลอื่นแก้ไขไปแล้วจะไม่มีการเปลี่ยนแปลง
บทบาท (role) ที่มี ผู้ดูแลระบบ (Administrator)บทบาท (role) ของชุมชน (community) ที่เปิดสวิตช์ ผู้ดูแลระบบ (Administrator) ไว้ จะสามารถทำได้ทุกอย่างที่ผู้ดูแลระบบของชุมชน (community admin) สามารถทำได้ ตามที่สวิตช์ระบุ ไม่ใช่แค่การตั้งค่าของชุมชน (community) เท่านั้น
ขีดจำกัดจำนวนสมาชิกสมาชิกรวมที่มากที่สุดต่อชุมชน (Max Members Per Community) (TeamSettings.MaxUsersPerTeam) เปลี่ยนจาก 50 ซึ่งเป็นค่าเริ่มต้นเดิม เป็น 0 (ไม่จำกัด) ค่าอื่นๆ ที่ตั้งไว้จะยังคงอยู่ รวมถึงขีดจำกัดที่ตั้งไว้ด้วย AM_TEAMSETTINGS_MAXUSERSPERTEAM
การเชื่อมต่อโมเดล (model connections)ผู้ดูแลระบบของระบบ (system administrator) จะเป็นผู้จัดการการเชื่อมต่อโมเดล (model connections) และผู้ดูแลระบบของชุมชน (community admin) (รวมถึงบทบาท (role) ที่มี ผู้ดูแลระบบ (Administrator)) จะเป็นผู้จัดการการเชื่อมต่อโมเดลของชุมชน (community) ของตนเอง บริการ AI ของแอป Agents กลายเป็น การเชื่อมต่อโมเดล (model connections) ระดับเซิร์ฟเวอร์ทั้งหมด ดูรายละเอียดด้านล่าง
Town Square กลายเป็น Generalช่องเริ่มต้นของทุกชุมชนจะถูกเปลี่ยนชื่อจาก town-square (Town Square) เป็น general (General) โดยยังคง ID, สมาชิกรายการ, ข้อความ และการตั้งค่าไว้ รวมถึงชื่อที่แสดงซึ่งผู้ดูแลระบบเป็นผู้เลือก ลิงก์เก่าและการค้นหาโดย town-square ยังคงนำไปยังช่องดังกล่าว ชุมชนที่มีช่องชื่อ general อยู่แล้ว แม้จะถูกล็อกไว้ก็ตาม จะยังคงใช้ town-square เป็นช่องเริ่มต้น เช่นเดียวกับชุมชนที่ town-square ถูกล็อกไว้: บันทึกจะระบุชื่อของช่องเหล่านี้ และผู้ดูแลระบบสามารถเปลี่ยนชื่อของช่องเหล่านั้นได้
รายการโปรด (Favourites)หมวดหมู่ (category) รายการโปรด (Favorites) ในแถบด้านข้าง (sidebar) ของทุกคนจะถูกเปลี่ยนชื่อเป็น Favourites ตามที่อินเทอร์เฟซ (interface) แสดงอยู่ตอนนี้ หมวดหมู่ (category) ที่บุคคลสร้างไว้ด้วยชื่อนั้นจะยังคงเหมือนเดิม

บริการของแอป Agents

การอัปเกรดจะคัดลอกบริการ AI แต่ละตัวของแอป Agents ไปเป็นการเชื่อมต่อโมเดลระดับเซิร์ฟเวอร์ ซึ่งชุมชนทุกชุมชนสามารถใช้งานร่วมกันได้ และทุกคนยกเว้นแขก (เปิด รวมแขกด้วย เพื่ออนุญาตให้พวกเขาใช้) คีย์จะถูกเข้ารหัสระหว่างทาง ดังนั้นเซิร์ฟเวอร์จึงต้องมีคีย์การเข้ารหัส AI: สำหรับคลัสเตอร์ที่ไฟล์อยู่ใน S3 ให้ตั้งค่า AM_AI_ENCRYPTION_KEY ก่อน ไม่งั้นการคัดลอกจะรอจนกว่าจะรีสตาร์ทครั้งถัดไป จากนั้นตรวจสอบ คอนโซลระบบ › AI › การเชื่อมต่อโมเดล:

  • แต่ละการเชื่อมต่อจะเก็บ ID ของบริการไว้ เพื่อให้เอเจนต์ของแอปและการแปลอัตโนมัติที่ตั้งไว้กับบริการ Agents ยังสามารถค้นหาบริการนั้นได้
  • บริการ OpenAI, OpenAI-compatible, Anthropic, Mistral, Cohere และ Gemini จะกลายเป็นการเชื่อมต่อไปยังปลายทาง OpenAI-compatible (หรือ Anthropic) ของแต่ละผู้ให้บริการ บริการ Azure จะกลายเป็นการเชื่อมต่อไปยังปลายทาง OpenAI-compatible ของทรัพยากร: ทดสอบดู
  • บริการ AWS Bedrock, Google Vertex AI และ Cohere North รวมถึงประเภทที่ไม่รู้จัก จะถูกทำเครื่องหมายว่า ต้องดำเนินการ พร้อมเหตุผล ข้อมูลประจำตัวบนคลาวด์ของพวกนั้นจะไม่ถูกคัดลอก: ให้ชี้ไปยังปลายทาง OpenAI-compatible ของผู้ให้บริการหรือเกตเวย์เช่น LiteLLM จากนั้นบันทึก
  • บริการ embedding จะกลายเป็นโมเดล Embeddings ของการเชื่อมต่อที่มีที่อยู่และคีย์เดียวกัน หรือจะเป็นการเชื่อมต่อแยกต่างหาก บริการถอดเสียงจะได้โมเดล whisper-1
  • เมื่อการเขียนใหม่และสรุปยังไม่มีเชื่อมต่ออยู่ พวกนั้นจะได้บริการและโมเดลของเอเจนต์เริ่มต้นของแอป

การตั้งค่าและข้อมูลของแอป Agents เองยังคงเป็นเหมือนเดิม: เอเจนต์ของแอปยังคงใช้บริการของมัน

การเปลี่ยนแปลงค่าเริ่มต้นอื่นๆ

  • การโทร: โหมดทดสอบ ปิดอยู่ และ เปิดใช้วิดีโอ เปิดอยู่โดยค่าเริ่มต้น ตัวเลือกที่บันทึกไว้ในค่ากำหนดจะยังคงอยู่ การโทรยังปฏิบัติตามประเภทของชุมชน (ดู การโทรและเสียง)
  • การปักหมุดข้อความไว้บนสุดเป็นหน้าที่ของผู้ดูลระบบของช่อง ผู้ดูลระบบและผู้ดูแลของชุมชน (พร้อม จัดการข้อความ); สมาชิกของข้อความส่วนตัวหรือข้อความกลุ่มยังคงทำได้
  • ช่องที่เก็บถาวรสามารถรับสมาชิกใหม่ได้ ซึ่งพวกเขาสามารถอ่านประวัติได้ ไม่มีใครโพสต์ ตอบกลับ หรือเปลี่ยนแปลงสิ่งใดในนั้น

การย้ายจาก Mattermost

Antimatter ใช้โครงสร้างฐานข้อมูลของ Mattermost และเพิ่มตารางของตัวเอง จึงสามารถรับช่วงต่อฐานข้อมูล PostgreSQL และไฟล์ของเซิร์ฟเวอร์ Mattermost ได้ ลองทำกับสำเนาข้อมูลก่อน:

  1. สำรองข้อมูลฐานข้อมูล Mattermost, ที่เก็บไฟล์ (data/ หรือ S3 bucket) และ config.json จากนั้นหยุด Mattermost
  2. กู้คืนฐานข้อมูลเข้าสู่ PostgreSQL ของ Antimatter หรือชี้ Antimatter ไปยังสำเนาของฐานข้อมูลนั้น (AM_SQLSETTINGS_DATASOURCE)
  3. คัดลอกไฟล์เข้าสู่ที่เก็บของ Antimatter โดยรักษาเส้นทางเดิม: ไปยัง S3 bucket ของ antimatter ด้วยเครื่องมือ S3 หรือไปยัง data/ ด้วยอาร์ไคฟ์การปล่อยเวอร์ชัน
  4. นำการตั้งค่าของคุณกลับมาใช้: คัดลอก config.json หรือย้ายเข้าสู่ฐานข้อมูลด้วย amctl --local config migrate (ดู การตั้งค่า) ตัวแปรสภาพแวดล้อม MM_ ของคุณยังคงทำงานได้; เปลี่ยนชื่อเป็น AM_ เมื่อสะดวก
  5. เริ่ม Antimatter และติดตามบันทึกขณะอัปเกรดฐานข้อมูล จากนั้นตรวจสอบ คอนโซลระบบ › ปลั๊กอิน › การจัดการปลั๊กอิน Antimatter จะติดตั้งการสร้างของตัวเองของ Calls, Playbooks, Kanban (Boards), Agents และอินทิเกรชันเมื่อพวกนั้นใหม่กว่าเวอร์ชันที่ติดตั้งอยู่ หาก Mattermost มีเวอร์ชันที่ใหม่กว่าของหนึ่งในนั้น ให้ลบแอปนั้นและรีสตาร์ท Antimatter เพื่อให้การติดตั้งของตัวเองถูกติดตั้ง
  6. ตั้้งค่าการแจ้งเตือนแบบพุชใหม่อีกครัง ด้วยพร็อกซีพุชของคุนเอง: Antimatter จะไม่ส่่งการแจ้งเตือนไปยงเซิรฟ์เวอรฟ์พุชของ Mattermost ทังท่ีเป็นเซิรฟ์เวอรฟ์เทสหรือโฮสต์ เพราะเซิรฟ์เวอรฟ์เหล่านี้นำส่่งการแจ้งเตือนไปยงแอปของ Mattermost เองเท่านั้้น จนกว่าคุนจะเปลี่นแปลงเซิรฟ์เวอรฟ์การแจ้งเตือนแบบพุช เซิรฟ์เวอรฟ์จะไม่ส่่งการแจ้งเตือนแบบพุชเลย (ดูการแจ้งเตือนแบบพุช)

Antimatter ไม่ติดต่อใช้บริการใด ๆ ที่ดำเนินการโดย Mattermost, Inc. (ดู การเชื่อมต่อไปยังบริการภายนอก) แม้การตั้งค่าของคุณจะยังระบุไว้ก็ตาม:

  • เซิร์ฟเวอร์การแจ้งเตือนแบบ push ของ Mattermost ยังคงถูกเก็บไว้ในตั้งค่า แต่จะไม่ถูกใช้งาน;
  • ที่อยู่ของ Mattermost สำหรับ Marketplace (URL ของ Marketplace) และสำหรับการแจ้งเตือนเกี่ยวกับผลิตภัณฑ์ถูกล้าง;
  • ลิงก์ดาวน์โหลดแอปท่ีเคยเป็นค่าเริ่มต้นของ Mattermost (Antimatter Apps Download Page Link, ลิงก์ดาวน์โหลดแอป Android และ ลิงก์ดาวน์โหลดแอป iOS) จะถูกเปล่ียนไปเป็นหน้่าดาวน์โหลดแอปของ Antimatter บน GitHub; ลิงก์ท่ีคุณตั้้งเองจะยังคงอยู้
  • แอป Calls ใช้เซิร์ฟเวอร์ STUN สาธารณะของ Cloudflare แทนที่จะใช้ของ Mattermost โดยไม่มีการเปลี่ยนแปลงค่าที่ตั้งไว้ (ดู การโทร);
  • การตรวจสอบอัปเดตความปลอดภัยและการรายงานข้อผิดพลาดหายไป รวมถึงการตั้งค่าในคอนโซลระบบ (เปิดใช้งานการแจ้งเตือนความปลอดภัย, เปิดใช้งานการวินิจฉัยและการรายงานข้อผิดพลาด) และหน้า ประกาศ

ซ็อกเก็ตสำหรับโหมดท้องถิ่นตอนนี้คือ /var/tmp/antimatter_local.socket; amctl จะลองใช้ /var/tmp/mattermost_local.socket เดิมด้วย Mattermost รองรับเฉพาะ PostgreSQL ในเวอร์ชันล่าสุด และ Antimatter ก็เช่นกัน: ย้ายฐานข้อมูล MySQL ไปยัง PostgreSQL ก่อน หากต้องการกลับไปใช้ Mattermost หลังจาก Antimatter อัปเกรดฐานข้อมูลแล้ว คุณต้องกู้คืนข้อมูลสำรอง (backup) ของ Mattermost ของคุณ

ส่งออกและนำเข้าข้อมูล

รูปแบบการส่งออกข้อมูลจำนวนมาก (bulk export) ช่วยย้ายข้อมูลระหว่างเซิร์ฟเวอร์: ทั้งเซิร์ฟเวอร์, ชุมชนบางส่วน หรือช่องบางส่วน พร้อมไฟล์แนบ รูปภาพโปรไฟล์ และอิโมจิกำหนดเอง หากคุณต้องการ

# on the source server
amctl export create --team-name design --include-profile-pictures
amctl export list
amctl export download <export file> design.zip
# on the destination server
amctl import upload design.zip
amctl import list available
amctl import process <uploaded file> --imported-users active

ดูสถานะของงานด้วย amctl export job list และ amctl import job list สำหรับงานส่งออกชุมชนหรือช่อง จำเป็นต้องใช้ --imported-users: ใช้ active เมื่อผู้ใช้ย้ายมาที่เซิร์ฟเวอร์นี้ และ inactive เมื่อนำเข้าข้อมูลไปยังเซิร์ฟเวอร์ที่ผู้ใช้เหล่านั้นมีบัญชีอยู่แล้ว เพื่อให้บัญชีที่สร้างขึ้นจากการจับคู่ที่ไม่ชัดเจนยังคงถูกปิดอยู่จนกว่าผู้ดูแลระบบจะตรวจสอบ --destination-team-name ใช้สำหรับนำเข้าข้อมูลไปยังชุมชนที่มีอยู่แล้ว การส่งออกและนำเข้าข้อมูลจะถูกเก็บไว้ในพื้นที่จัดเก็บของเซิร์ฟเวอร์ (ExportSettings.Directory, ImportSettings.Directory) เป็นเวลา 30 วันโดยค่าเริ่มต้น

บนเซิร์ฟเวอร์เอง คำสั่ง antimatter export bulk และ antimatter import bulk --apply ทำหน้าที่เดียวกันจากไฟล์ โดยไม่ต้องใช้ API
