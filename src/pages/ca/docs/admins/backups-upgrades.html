La base de dades i els fitxers van junts: fes-ne còpia de seguretat al mateix temps i mantén còpies fora del servidor. Els noms dels volums comencen pel nom del projecte compose, antimatter (docker volume ls els llista).

Còpia de seguretat

Des del directori de compose.yaml. Aturar Antimatter primer dóna una còpia completament coherent; una còpia feta mentre funciona sol anar bé, però els fitxers penjats durant la còpia poden estar-ne absents.

stamp=$(date +%Y%m%d-%H%M%S)
mkdir -p backups
docker compose stop antimatter
# Database
docker compose exec -T postgres pg_dump -U antimatter -d antimatter -Fc \
    > "backups/antimatter-db-$stamp.dump"
# File storage and GIF service
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data:ro" -v "$PWD/backups:/backup" \
        alpine tar -czf "/backup/antimatter-$v-$stamp.tar.gz" -C /data .
done
docker compose start antimatter
# Secrets
cp .env "backups/env-$stamp"

Executa-la des de cron per a còpies diàries i copia el directori backups/ a una altra màquina. Mantén les còpies de .env tan segures com el servidor: contenen les seves contrasenyes.

Per copiar els fitxers penjats objecte per objecte (per exemple, a un altre emmagatzematge S3), utilitza l'eina de línia d'ordres d'AWS del servei bucket:

docker compose run --rm -v "$PWD/backups/files:/backup" bucket \
    "aws --endpoint-url http://files:9000 s3 sync s3://antimatter /backup"

Amb un arxiu de publicació, fes còpia de seguretat de la base de dades amb pg_dump -Fc i dels directoris data/ i config/ amb les teves eines habituals.

Restauració en un nou host

Posa compose.yaml, el .env desat i les còpies de seguretat en un directori nou, i després:

stamp=20261016-030000          # the backup to restore
docker compose create           # creates the volumes, starts nothing
docker compose up -d postgres
docker compose exec -T postgres pg_restore -U antimatter -d antimatter --no-owner \
    < "backups/antimatter-db-$stamp.dump"
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data" -v "$PWD/backups:/backup" \
        alpine tar -xzf "/backup/antimatter-$v-$stamp.tar.gz" -C /data
done
docker compose up -d

Utilitza el mateix .env: l'emmagatzematge i la base de dades han de mantenir les contrasenyes que tenien. Si el nou host té una altra adreça, actualitza SITE_URL (i DOMAIN).

Prova les teves còpies de seguretat restablint-les en una altra màquina de tant en tant.

Actualització

  1. Fes una còpia de seguretat.
  2. Canvia l'etiqueta de la imatge a .env (ANTIMATTER_IMAGE), si en fixes una, com es recomana.
  3. Treu-la i reinicia: 
    docker compose pull
docker compose up -d
docker compose logs -f antimatter

En arrencar, el servidor actualitza l'esquema de la base de dades (pots seguir-ho al registre; en un servidor gran pot trigar diversos minuts) i instal·la les versions més recents de les aplicacions integrades de la imatge. Amb un arxiu de publicació: atura el servidor, substitueix-ho tot excepte config/, data/, logs/, plugins/ i client/plugins/ pel contingut de l'arxiu nou, i torna a arrencar-lo.

Les actualitzacions només es fan endavant. Un cop un servidor més nou ha actualitzat la base de dades, una versió anterior no pot utilitzar-la: per tornar enrere, restaura la còpia de seguretat feta abans de l'actualització. El mateix aplica per tornar de antimatter-next a antimatter.

Versions

El servidor d'Antimatter informa de la versió de la línia de Mattermost en què es basa (actualment 12.0.0). Les imatges es reconstrueixen des de les branques main: antimatter-next cada nit (etiquetes nightly-<YYYYMMDD>), i ambdues imatges en cada canvi (etiquetes sha-<commit>). Fixa't en una d'aquestes etiquetes, actualitza de manera intencional i guarda l'anterior anotada per saber amb quina còpia de seguretat correspon.

Versions principals de PostgreSQL

El fitxer compose utilitza postgres:17-alpine. Antimatter necessita PostgreSQL 15 o superior. Una versió principal nova de PostgreSQL no pot llegir el directori de dades de l'anterior: per passar-hi, fes un volcat de la base de dades, arrenca la versió nova en un volum nou i restaura-hi el volcat.

Migració des de Mattermost

Antimatter utilitza l'esquema de base de dades de Mattermost i hi afegeix les seves pròpies taules, de manera que pot prendre el relleu de la base de dades PostgreSQL i els fitxers d'un servidor de Mattermost. Prova-ho primer en una còpia:

  1. Fes una còpia de seguretat de la base de dades de Mattermost, el seu emmagatzematge de fitxers (data/ o balde S3) i config.json, i després atura Mattermost.
  2. Restaura la base de dades a PostgreSQL d'Antimatter, o apuntes Antimatter a una còpia d'aquesta (AM_SQLSETTINGS_DATASOURCE).
  3. Copia els fitxers a l'emmagatzematge d'Antimatter, mantenint-ne les rutes: al balde antimatter amb una eina S3, o a data/ amb un arxiu de publicació.
  4. Reutilitza la teva configuració: copia config.json, o mou-lo a la base de dades amb amctl --local config migrate (vegeu Configuració). Les teves variables d'entorn MM_ continuen funcionant; canvia-les per AM_ quan et convé.
  5. Inicia Antimatter i segueix el registre mentre actualitza la base de dades. Després, consulta Consola del sistema › Connectors › Gestió de plugins. Antimatter instal·la les seves pròpies versions de Trucades, Guies d'actuació, Taulers (Kanban), Agents i integracions quan són més recents que la versió instal·lada. Si Mattermost tenia una versió més recent d'una d'aquestes aplicacions, elimina-la i reinicia Antimatter perquè s'instal·li la seva pròpia versió.
  6. Configura de nou les notificacions push amb el teu propi proxy de notificacions: Antimatter mai envia notificacions als serveis de notificacions push de Mattermost, ja sigui de proves o allotjats, que només les lliuren a les pròpies aplicacions de Mattermost. Fins que no canvis el Servidor de notificacions push, el servidor no envia cap notificació push (vegeu Notificacions push).

Antimatter no contacta amb cap servei operat per Mattermost, Inc. (vegeu Connexions amb serveis externs), fins i tot si la teva configuració encara en menciona un:

  • un serveidor de notificacions push de Mattermost es manté a la configuració però mai s'utilitza;
  • S'han buidat les adreces de Mattermost per al Marketplace d'aplicacions (URL del Marketplace) i per als avisos de producte;
  • l'aplicació de Reunió ràpida utilitza el servidor STUN públic de Cloudflare en lloc del de Mattermost, sense canviar la configuració desada (vegeu Reunió ràpida);
  • s'han eliminat la comprovació d'actualitzacions de seguretat i la informació d'errors, així com la seva configuració a la Consola del sistema (Activa les alertes de seguretat, Activa el diagnòstic i la informació d'errors) i la pàgina Avisos.

El socket del mode local ara és /var/tmp/antimatter_local.socket; amctl també intenta el vell /var/tmp/mattermost_local.socket. Mattermost només admet PostgreSQL en les seves versions recents, i Antimatter també: primer, mou la base de dades de MySQL a PostgreSQL. Tornar a Mattermost després que Antimatter hagi actualitzat la base de dades implica restaurar la còpia de seguretat de Mattermost.

Exporta i importa dades

El format d'exportació massiva mou dades entre servidors: el servidor sencer, algunes comunitats o alguns canals, amb adjunts, fotos de perfil i emojis personalitzats si els vols.

# on the source server
amctl export create --team-name design --include-profile-pictures
amctl export list
amctl export download <export file> design.zip
# on the destination server
amctl import upload design.zip
amctl import list available
amctl import process <uploaded file> --imported-users active

Vigila les tasques amb amctl export job list i amctl import job list. Per a una exportació o importació de comunitat o canal, cal --imported-users: active quan les persones es traslladen a aquest servidor, i inactive quan s'importi en un servidor on ja tinguin comptes, de manera que els comptes creats a partir de coincidències incertes romanguin inactius fins que un administrador els verifiqui. --destination-team-name importa en una comunitat existent. Les exportacions i importacions es conserven a l'emmagatzematge del servidor (ExportSettings.Directory, ImportSettings.Directory) durant 30 dies per defecte.

Al mateix servidor, antimatter export bulk i antimatter import bulk --apply fan el mateix a partir de fitxers, sense utilitzar l'API.
