Backups e atualizações

O que fazer backup, como restaurá-lo em um novo host, como atualizar e como migrar um servidor Mattermost ou uma única comunidade para o Antimatter.

O que fazer backup

O quêCom o arquivo compose do siteCom um arquivo de release
O banco de dados: mensagens, usuários, comunidades, canais e, com o arquivo compose do site, a configuraçãovolume antimatter_postgres, por meio de pg_dumpseu banco de dados PostgreSQL
Arquivos enviados, imagens e aplicativos instaladosvolume antimatter_files (o armazenamento S3)FileSettings.Directory, ./data/ por padrão
O arquivo de configuração(no banco de dados)config/config.json
GIFs e figurinhasvolume antimatter_gifso diretório de dados do serviço de GIFs
Segredos.env (e compose.override.yaml)seu arquivo de ambiente

O banco de dados e os arquivos pertencem juntos: faça backup deles ao mesmo tempo e mantenha cópias fora do servidor. Os nomes dos volumes começam com o nome do projeto compose, antimatter (docker volume ls lista-os).

Fazer backup

A partir do diretório de compose.yaml. Parar o Antimatter primeiro garante uma cópia totalmente consistente; um backup feito enquanto ele está em execução geralmente é suficiente, mas os arquivos enviados durante o backup podem estar ausentes dele.

stamp=$(date +%Y%m%d-%H%M%S)
mkdir -p backups
docker compose stop antimatter
# Database
docker compose exec -T postgres pg_dump -U antimatter -d antimatter -Fc \
    > "backups/antimatter-db-$stamp.dump"
# File storage and GIF service
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data:ro" -v "$PWD/backups:/backup" \
        alpine tar -czf "/backup/antimatter-$v-$stamp.tar.gz" -C /data .
done
docker compose start antimatter
# Secrets
cp .env "backups/env-$stamp"

Execute-o via cron para backups diários e copie o diretório backups/ para outra máquina. Mantenha as cópias de .env tão seguras quanto o servidor: elas contêm suas senhas.

Para copiar os arquivos enviados objeto por objeto (por exemplo, para outro armazenamento S3), use a ferramenta de linha de comando da AWS do serviço bucket:

docker compose run --rm -v "$PWD/backups/files:/backup" bucket \
    "aws --endpoint-url http://files:9000 s3 sync s3://antimatter /backup"

Com um arquivo de release, faça backup do banco de dados com pg_dump -Fc e dos diretórios data/ e config/ com suas ferramentas habituais.

Restaurar em um novo host

Coloque compose.yaml, o .env salvo e os backups em um novo diretório, então:

stamp=20261016-030000          # the backup to restore
docker compose create           # creates the volumes, starts nothing
docker compose up -d postgres
docker compose exec -T postgres pg_restore -U antimatter -d antimatter --no-owner \
    < "backups/antimatter-db-$stamp.dump"
for v in files gifs; do
    docker run --rm -v "antimatter_$v:/data" -v "$PWD/backups:/backup" \
        alpine tar -xzf "/backup/antimatter-$v-$stamp.tar.gz" -C /data
done
docker compose up -d

Use o mesmo .env: o armazenamento e o banco de dados devem manter as senhas que tinham. Se o novo host tiver outro endereço, atualize SITE_URL (e DOMAIN).

Teste seus backups restaurando-os em outra máquina de tempos em tempos.

Atualizar

  1. Faça um backup.
  2. Altere a tag da imagem em .env (ANTIMATTER_IMAGE), se você fixar uma, como recomendado.
  3. Baixe e reinicie: 
    docker compose pull
docker compose up -d
docker compose logs -f antimatter

Na inicialização, o servidor atualiza o esquema do banco de dados (acompanhe o progresso no log; em um servidor grande, isso pode levar vários minutos) e instala as versões mais recentes dos aplicativos incluídos na imagem. Com um arquivo de release: pare o servidor, substitua tudo, exceto config/, data/, logs/, plugins/ e client/plugins/, pelo conteúdo do novo arquivo e inicie-o novamente.

As atualizações só podem ser feitas para frente. Uma vez que um servidor mais recente tenha atualizado o banco de dados, uma versão anterior não poderá usá-lo: para reverter, restaure o backup feito antes da atualização. O mesmo se aplica à mudança de antimatter-next de volta para antimatter.

Versões

O servidor do Antimatter relata a versão da linha Mattermost em que se baseia (atualmente 12.0.0). As imagens são reconstruídas a partir dos ramos main: antimatter-next todas as noites (tags nightly-<YYYYMMDD>) e ambas as imagens a cada alteração (tags sha-<commit>). Fixe uma dessas tags, atualize intencionalmente e mantenha anotada a tag anterior para saber com qual backup ela corresponde.

Versões principais do PostgreSQL

O arquivo compose usa postgres:17-alpine. O Antimatter requer PostgreSQL 15 ou mais recente. Uma nova versão principal do PostgreSQL não consegue ler o diretório de dados da versão anterior: para migrar, faça um despejo (dump) do banco de dados, inicie a nova versão em um novo volume e restaure o despejo nele.

Migração do Mattermost

O Antimatter usa o esquema de banco de dados do Mattermost e adiciona suas próprias tabelas, podendo assim assumir o banco de dados PostgreSQL e os arquivos de um servidor Mattermost. Tente primeiro em uma cópia:

  1. Faça backup do banco de dados do Mattermost, do armazenamento de arquivos (data/ ou bucket S3) e do config.json, e então pare o Mattermost.
  2. Restaure o banco de dados no PostgreSQL do Antimatter, ou aponte o Antimatter para uma cópia dele (AM_SQLSETTINGS_DATASOURCE).
  3. Copie os arquivos para o armazenamento do Antimatter, mantendo seus caminhos: para o bucket antimatter com uma ferramenta S3, ou para data/ com um arquivo de release.
  4. Reutilize suas configurações: copie o config.json ou mova-o para o banco de dados com amctl --local config migrate (veja Configurações). Suas variáveis de ambiente MM_ continuam funcionando; renomeie-as para AM_ quando for conveniente.
  5. Inicie o Antimatter e acompanhe o log enquanto ele atualiza o banco de dados. Em seguida, verifique Console do Sistema › Plugins › Gerenciamento de Plugins. O Antimatter instala suas próprias versões de Chamadas, Playbooks, Kanban (Quadros), Agentes e integrações quando estas são mais novas que a versão instalada. Se o Mattermost tiver uma versão mais nova de um deles, remova esse aplicativo e reinicie o Antimatter, para que sua própria versão seja instalada.
  6. Configure as notificações push novamente, com seu próprio proxy de push: o Antimatter nunca envia notificações para os serviços de push do Mattermost, de teste ou hospedados, que só entregam às aplicações próprias do Mattermost. Até que você altere o Servidor de Notificação Push, o servidor não envia notificações push (veja Notificações push).

O Antimatter não contata nenhum serviço operado pela Mattermost, Inc. (veja Conexões com serviços externos), mesmo quando sua configuração ainda menciona um:

  • um servidor de notificação push da Mattermost é mantido nas configurações, mas nunca é usado;
  • os endereços da Mattermost para o marketplace de aplicativos (URL do Marketplace) e para avisos de produto são esvaziados;
  • o aplicativo de Chamadas usa o servidor STUN público da Cloudflare em vez do da Mattermost, sem alterar a configuração salva (veja Chamadas);
  • a verificação de atualizações de segurança e o relatório de falhas foram removidos, assim como suas configurações no Console do Sistema (Ativar Alertas de Segurança, Ativar Diagnóstico e Relatório de Erros) e a página Avisos.

O socket do modo local agora é /var/tmp/antimatter_local.socket; o amctl também tenta o antigo /var/tmp/mattermost_local.socket. O Mattermost só suporta PostgreSQL em suas versões recentes, e o Antimatter também: primeiro, migre um banco de dados MySQL para PostgreSQL. Voltar ao Mattermost após o Antimatter ter atualizado o banco de dados significa restaurar seu backup do Mattermost.

Exportar e importar dados

O formato de exportação em lote move dados entre servidores: o servidor inteiro, algumas comunidades ou alguns canais, com anexos, fotos de perfil e emojis personalizados, se você quiser.

# on the source server
amctl export create --team-name design --include-profile-pictures
amctl export list
amctl export download <export file> design.zip
# on the destination server
amctl import upload design.zip
amctl import list available
amctl import process <uploaded file> --imported-users active

Acompanhe as tarefas com amctl export job list e amctl import job list. Para uma exportação de comunidade ou canal, --imported-users é obrigatório: active quando as pessoas se mudam para este servidor, inactive quando importando para um servidor onde elas já têm contas, para que as contas criadas a partir de correspondências incertas permaneçam desativadas até que um administrador as verifique. --destination-team-name importa para uma comunidade existente. As exportações e importações são mantidas no armazenamento do servidor (ExportSettings.Directory, ImportSettings.Directory) por 30 dias por padrão.

No próprio servidor, antimatter export bulk e antimatter import bulk --apply fazem o mesmo a partir de arquivos, sem a API.
